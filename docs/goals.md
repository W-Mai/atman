# Managed agent goals

A goal is a persistent objective with `active` or `paused` state. A managed agent completes its current turn normally. An active goal permits another turn; `memory.goal.pause` stops automatic continuation and lets the current turn finish its response. Ordinary custom flows remain single executions unless they declare `contract { invocation { goal: true } }` and run through a goal-aware host.

Managed root and child prompts require every turn to conclude through `final.answer`, including ordinary questions and requests for clarification. The call contains the complete response in `message` and its summary in `_atman_intent`, with no sibling tool calls. When pausing a goal, the agent must receive the pause result before issuing `final.answer` separately; pausing alone does not deliver the final response.

Managed `agent.at` and `subagent.at` explicitly call `final.answer(message: reply)` for a valid final control. A normally completed, non-empty plain-text reply can use the same delivery path only if the model has not called any tools during the current turn. After tool calls, plain text is recorded as an intermediate reply and the flow reminds the model to issue `final.answer`; repeated plain-text replies do not waive this requirement. Failed or invalid tool calls also count, while template initialization does not. This state resets for each turn, independently of retained conversation history. The flows request an unrecorded response through `llm.call(record: false, output: "response")`, inspect its `stop_reason`, and record ordinary tool-call replies before dispatching their tools. `final.answer` accepts a string or an assistant Message, publishes the final response with its activity summary, persists it in the calling context, and returns the answer text. The templates return immediately afterward, and ordinary LLM dispatch never upgrades plain text automatically. This completion ends the current turn without pausing an active goal; notifications arriving afterward can start a separate turn.

A valid `final.answer` is published immediately and ends the current turn. Watcher notifications cannot discard or delay that answer. During an active turn, the next general model call receives queued watcher notifications as a FIFO batch with `watcher` origin. Isolated calls and auxiliary extraction do not consume them. The interactive host, managed `atman run`, and daemon `goal.run` start a new turn only for notifications still pending after the current turn ends. A completed one-shot watcher can still have a pending notification. Watcher turns retain the managed invocation settings and do not resume a paused goal; user, parent, cancellation, and failure pauses prevent background turns. The interactive host handles queued user input before watcher or goal continuation. Root and spawned agents own separate watcher queues; inline flows share their calling agent's queue. Managed child flows that register watchers use the same in-turn pickup and idle wakeup behavior. Existing role tool restrictions still apply.

## Goal tools

`memory.goal.get` returns `{goal, execution, paused_by, running_operations}`. `goal` is null when no objective exists. Records include `id`, `revision`, `objective`, `owner`, `parent_goal_id`, `status`, and `pause`.

`goal.status` controls automatic objective continuation; `execution` describes current activity and execution pauses. A paused goal can have `running` execution during a new user turn, and an active goal can be `idle` between turns. `finishing` identifies an agent acknowledging a user-requested pause while delivering its current final response. A paused goal alone does not imply that the flow has completed.

Goal timestamps remain stored in UTC. Root and child agents receive a runtime clock context record containing the host's local date, time, and UTC offset, refreshed at minute precision before model calls without changing the system prompt. The host timezone can differ from the user's timezone, especially on remote servers; agents are instructed to use the user's timezone when known and otherwise label times with their UTC offset. Pause summaries are model-authored text displayed unchanged; existing summaries are not rewritten by this clock context.

| Tool | Arguments | Effect |
| --- | --- | --- |
| `memory.goal.get` | Optional `target_handle` | Read the current agent or a descendant |
| `memory.goal.set` | `text`; existing goals require `goal_id`, `expected_revision` | Create an objective or edit its text without resuming it |
| `memory.goal.pause` | `goal_id`, `expected_revision`, `reason`, `summary` | Report completion, blocked work, or missing input and stop continuation |
| `memory.goal.resume` | `goal_id`, `expected_revision` | Resume a descendant, or an agent-paused goal after real user input |

Pause reasons accepted from agents are `completed`, `needs_input`, `blocked`, and `user_requested`. All tools accept an optional `target_handle`. A child cannot address its parent or siblings. Stale revisions fail without changing the goal. A new user request can replace an agent-completed goal with a new identity; editing unfinished work preserves its state. User pauses cannot be overridden by agent tools. Managed agents use pause rather than `memory.goal.clear`.

## Execution boundaries

Watcher registration validates its target before adding an active watch. Before returning success, it establishes the source subscription and captures the terminal screen baseline; subsequent screen updates remain available even before the background consumer is first polled. Unwatch stops future results from that registration; notifications already queued remain available. Watcher completion and notification enqueue share one state lock, and changes wake every waiter, including hosts waiting for all watches to finish. Model pickup, background turns, and explicit `wait_for_watcher` compete for the same FIFO queue. A reserved batch remains queued until history accepts it; failed preparation releases it, while model failures after pickup leave it recorded in context. Acknowledged user pauses defer new notifications while allowing the current response to finish. Cancelling a child flow stops its owned watchers.

Reserved watcher and child-result batches count as unfinished delivery but are unavailable to competing consumers. Notification-driven turns wait until a batch is released or committed instead of repeatedly trying to claim it. A completed watcher with a reserved notification is not idle; its owner remains alive until delivery resolves.

Persistent watchers retain their output subscription and consumed position. Flow and background-command matches advance through available output, including patterns split across updates. Terminal watchers report newly visible matching positions; an unchanged match does not repeat on unrelated output, but removing and displaying it again can trigger another notification. A watcher can match existing output at registration. Source exit ends the watch after remaining matches; broadcast lag recovers from the available output snapshot. An empty pattern is rejected. Match notifications contain the matched text rather than a copy of the complete output history. Use the source output tools when more context is needed.

Flow output is cumulative across turns. Final-answer publication appends any answer not already present at the end of that turn's streamed output and signals watchers immediately, including when a managed child has paused its goal without exiting. The same turn's final delivery is idempotent; identical answers in separate turns remain separate output. `flow.stream` cursors remain valid after final delivery, and delayed watcher consumers recover all remaining matches from the cumulative output. Flow exit does not publish an already delivered answer again.

Background readiness checks do not consume notifications. Hosts prepare the invocation before starting a turn through the shared runtime entry point, which waits for context access, rechecks execution pauses and the current turn, then consumes notifications and records the new turn without another await. Cancellation during that wait leaves the notifications queued. Cancellation and runtime failures block automatic wakeups even when no goal exists; clearing an objective preserves execution pauses, and a real user submission can start work again.

User Pause stops new requests and tool starts. An in-flight model request finishes and its reply is recorded before execution waits. Already running tools can finish; undispatched work waits. Resume continues the suspended execution without replaying its reply or completed tools. Pause does not close the current turn or return its pending input to the submission queue. Esc cancels the turn and pauses its goal.

Root and child goals use the same controller. An agent pausing its own goal with `completed`, `needs_input`, or `blocked` stops that goal's automatic continuation without blocking descendants. A new user request and its child tasks can execute while the previous objective remains paused. User pauses, explicit parent controls, runtime failures, and replacement or removal of the parent goal still restrict descendants without changing their own goal states. An agent acknowledging `user_requested` can finish its current response, but descendants and background wakeups wait for explicit input or resume. Resuming an ancestor leaves completed or separately paused children paused. Child goal changes are recorded as revisioned events and delivered through the parent's versioned context records. Child continuation preserves its handle and private context while assigning each execution a distinct run identity. Background execution still requires a live host; this behavior does not detach tasks from session shutdown or restore timers after process exit.

The TUI folds preceding work when a final answer is published, including direct `.at` calls after ordinary text streaming. The answer stays outside the fold. A streamed final-answer tool draft can preview the same fold; publication does not require that draft.

Draft previews, live publication, and history restoration share final-answer presentation, work-range selection, summaries, and per-fold tool/edit statistics. Publication finalizes the preview in place; child streams cannot retract a root preview. Work ranges respect turn boundaries, including Goal resume and background turns without a new user message. Each turn's execution records remain independently expandable, and retries or workflow restarts stay within their own turn; restoring history skips the folding animation.

Message origin and model protocol role are independent. Goal continuation controls carry `internal` origin and remain hidden in the transcript after restoration. Watcher and child-result messages appear as status notes rather than user requests. These messages retain the `user` role when submitted to the model, and hidden controls still establish their turn boundaries during history restoration.

## Child results

Async child agents automatically deliver each published `final.answer` to their direct parent. A running parent receives pending results as a FIFO batch in its next general model call, without cancelling an in-flight request or waiting for another turn. An idle managed parent starts a new `child_result` turn with its retained invocation settings. Nested agents use the same behavior: a grandchild notifies its own parent, which can process the result and deliver its answer upward. No watcher or model polling is required for final results. Child messages are data, not new user instructions or authorization.

Persisted final-answer publication feeds both child-result delivery and flow output observation, regardless of whether the answer originated as text or a model tool call. An explicitly registered watcher is an independent pattern subscription: its match and the child's full answer are each delivered once through their respective channels. Execution pauses retain both kinds of pending notification; they cannot start another turn until the execution gate permits it.

Running-parent and background-turn child-result delivery share one inbox. Reserving a batch does not remove it; history accepts it before consumption commits. If request preparation fails or the parent ends before pickup, the unread batch remains available. A result already picked up is not delivered again; pickup means inclusion in a model request or new-turn history, not successful completion of the parent's work. User, parent, cancellation, and failure gates retain unread results until execution is allowed again. Replacing or clearing the parent's task invalidates queued and late results from the previous task scope. Completing the parent's goal does not activate that goal or prevent result handling.

Synchronous delegation claims its latest finalized answer and enables asynchronous notifications atomically. Earlier unreturned answers remain queued in publication order. A wait that returns before a final answer leaves that answer for notification; cancelling the waiter preserves every finalized answer it did not return. Resuming that retained child instance permits new results to notify the parent. Pending delivery is process-local; consumed messages and original child final answers are recorded in their respective histories. Restart does not replay unconsumed notifications or recreate suspended execution.

The document stream marks consumed batches as **Child results**. Full answers remain available in the child conversations; the parent model receives each batch's complete answers and source identities.

## Persistence and recovery

Managed child agents retain their handle, context, and workspace while paused, including completion pauses, so an explicit Resume can use the same instance. Managed command-line runs confirm that the shared notification revision remains unchanged during an idle scan before exiting, including when a grandchild transfers work to its parent. Clear, `flow.kill`, or session shutdown cancels that instance and releases its live resources. A cancelled child cannot be resumed. Process restart restores goal records, not suspended Rust execution or external side effects.

`goal_turn_started` events associate an agent owner and its current goal identity with each turn and run. The goal identity can be absent when the first user turn has not created an objective yet; subsequent `goal_changed` events identify that objective under the same owner.

Root state is stored in `<session>/goal.json`; child records are stored in `<session>/goals/<goal-id>.json`. Writes are atomic and revision checked. Existing `goal.txt` records load paused. Clearing writes a tombstone so legacy text cannot reappear. Opening a session with an interrupted active goal pauses it; recovery requires explicit control and does not replay past side effects.

No default turn, token, fuel, or time budget is added. Provider retries retain their existing limits; exhausted retries pause the goal instead of silently starting another attempt.

## TUI and CLI controls

Task lists, child details, and Goal controls share execution-state labels. A parent execution pause displays **Paused by parent** and disables the child's toggle until that restriction is lifted. A new user turn under a paused objective displays **Goal paused · running** and offers **Pause** for the running work. Idle paused goals offer **Resume**. Completed, failed, stopped, or interrupted flow instances remain terminal; retained goal records do not expose a resume action for exited children. Returning a spawn handle does not mark its child task complete.

The root Goal section and child flow panels display padded **Pause / Resume** buttons with `Ctrl+Y`. `:goal` or **Manage Goal** in `Ctrl+P` opens the goal panel. Its agent selector addresses the root or an existing managed child; `Tab` / `Shift+Tab`, `Enter`, and mouse clicks operate the same controls. `Space` toggles the selected goal outside editing. **Save** and `Ctrl+S` submit the objective and return to the goal details after persistence succeeds. A pending save displays **Saving…** and prevents duplicate submissions. Failed saves retain the draft and show the error in the panel. `Esc` discards editing when no save is pending. Clear requires a second activation.

The goal panel opens centered. Drag its title area to move it or its bottom-right handle to resize it. Reopening focuses the existing panel without resetting its position, size, or draft; resizing respects the component's minimum dimensions.

The **Agent** selector chooses the root or a managed child, each with one current objective. **New goal** is always visible; click it or press `N` to open a blank draft. Saving creates a fresh active goal with a new identity and replaces the selected agent's current goal only if its revision still matches. The editor labels this replacement before saving; `Esc` cancels without changing the existing goal. **Edit** changes the current objective while preserving its identity and pause state. New child goals continue to respect parent pauses, and replacing a root goal does not automatically resume descendants attached to the previous goal.

The sidebar Goal card highlights on hover. Click its title, objective, or padding to open the goal panel; drag across the objective to select text. The small left arrow only collapses the preview, and the separate Pause / Resume button only changes execution state. The header displays `:goal` as the keyboard entry point.

Plain REPL commands are `:goal`, `:goal set <text>`, `:goal pause`, `:goal resume`, and `:goal clear`. Controls run immediately instead of entering the prompt queue. Managed `atman run` invocations continue while the goal is active, watchers need handling, child results are pending, or active child work can still deliver. A retained, paused child instance alone does not keep the command alive. The command exits on an execution pause or failure, or when no source has work remaining. Interactive REPL and daemon owners remain available for explicit Resume. No entry point adds a default goal budget.

## Daemon methods

`goal.run` accepts the same parameters as `run_flow` and requires a managed invocation contract with a `user_message` string parameter. It creates an active goal from that parameter and returns `session_id`, the initial `run_id`, and `goal_id`. Subsequent turns have separate run IDs in the event stream. The owner stays live while paused so the authenticated client can resume it. `run_flow` retains its single-execution contract.

`goal.get`, `goal.set`, `goal.pause`, `goal.resume`, and `goal.clear` accept `session_id` and optional `target_handle`. Writes to an existing goal also require `goal_id` and `expected_revision`; `goal.set` requires `text`. Responses contain the same snapshot as the goal tools. Only the authenticated owner of the live session can read or control these goals. `cancel_run` stops the owner and its current turn; clearing removes its goal and stops continuation.
