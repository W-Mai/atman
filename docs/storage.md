# Durable fact journals

`atman_runtime::event_log::journal::Journal` commits typed batches of host facts. It is separate from the asynchronous display/event writer: an accepted commit means the entire batch has been written and synchronized. A caller publishes the resulting in-memory projection and receipt only after `commit` succeeds. Streaming previews need no durable commit per chunk.

`Journal::create(path, id)` creates a new file under an existing durable parent directory. `Journal::open(path, expected_id, apply)` holds an exclusive file lock, validates the log identity and format, and replays complete batches into a private projection. The caller must discard that projection if opening fails. These operations use blocking filesystem I/O and belong on a storage worker, outside UI or executor polling.

Each JSONL journal starts with a format/version/identity header. A batch contains a consecutive sequence number, the previous record digest, the exact serialized JSON payload, and its SHA-256 digest. Payloads are nonempty arrays. The hash chain checks integrity and ordering; it does not authenticate the caller or replace host authorization. A `CommitReceipt` identifies the journal and committed sequence/digest.

The writer serializes the complete batch before touching the file. A write or synchronization error prevents further commits through that handle. Reopening can discover a complete batch whose acknowledgement was lost; the host reconciles stable request IDs before retrying effects. A journal receipt alone does not implement request deduplication or prove that a business operation completed.

Recovery preserves an unterminated final record in an adjacent `.incomplete-<uuid>` file before removing it from the active journal. `RecoveredTail` reports the retained path, original offset, and byte count. Complete malformed records, broken digest chains, sequence gaps, unsupported schemas, or projection failures reject opening without skipping history. Recovery never executes flow code.

Existing published session event files continue to use their existing reader and writer. They are not interpreted as fact journals or rewritten by this API. An embedding host must explicitly choose the new format and bind each journal to its session or flow identity.

## Legacy history inspection

`atman migrate inspect <session-id-or-prefix>` prints a JSON ownership report for the original `sessions/<session>/events.jsonl`. `event_log::legacy::inspect` provides the same read-only operation to Rust hosts. Each nonempty physical line retains its byte range, SHA-256 digest, original sequence and timestamp when valid, and any parsing issues. Invalid JSON, unsupported events, and unterminated final lines remain indexed. Missing metadata stays absent; ordering follows byte positions. Whitespace remains covered by the complete source digest. Reports contain metadata and ownership mappings rather than message bodies.

Explicit agent owners join runs across turns. Inline calls inherit their recorded parent's identity; spawned runs without an agent owner retain independent mapping keys. Missing parents, cycles, and conflicting identities remain unassigned. Unscoped legacy session messages retain their default-agent meaning, while diagnostics without a reliable owner remain unassigned. Mapping keys do not grant execution or create new instance addresses.

Inspection reads the initial file length and verifies the source bytes again before returning; it does not keep tailing an active writer. `LegacySource::verify` detects appends, truncations, and same-length replacements before a caller reuses a report. This is a content check, not proof that an old executor has stopped. Inspection does not migrate files, activate flows, or switch catalogs; a migration writer must establish exclusive execution ownership and revalidate its source before committing.

## Offline history migration

Run `atman migrate archive <session-id-or-prefix> --confirm-stopped` after stopping the legacy session executor. The command prints the new session ID and migration receipt as JSON. Repeating the command resumes or verifies the same destination. Use `--into <new-session-uuid>` only when intentionally importing a separate branch. The source remains readable through legacy commands; importing does not change the active session or start execution.

The destination retains the legacy title and recorded project root, with the current Atman configuration source and resolved storage scope. A missing project directory remains a valid historical binding and is not recreated. Missing metadata produces a projectless historical session; malformed metadata is an error. The command bypasses startup configuration migration and does not initialize execution services.

`RuntimeStore::archive_legacy(source, source_session, destination, old_executor_stopped)` imports legacy events into a new session identity. The host authenticates the operator and obtains explicit confirmation that the old executor has stopped. This confirmation does not lock an old binary or prevent it from writing later. Source files remain unchanged. `flow_store::migration::destination_id` provides a stable target for retries; a changed source conflicts with the saved plan instead of silently creating another copy. An operator can explicitly choose another destination for a separate source branch.

The migration retains an exact source copy in the destination session's `artifacts/legacy-events.jsonl`, including whitespace and malformed data. Each owner receives a separate historical flow; uncertain records belong to one unassigned flow. Original lineage stays in the retained events and grants no authority. An explicit default historical flow exists even when the source contains no default-agent records. Historical flows remain closed and cannot start execution or deliver notifications.

Migration work stays under `runtime-v1/.migrations/<destination>/work` until every flow is complete and verified against the source map. Retries resume after committed record batches. Source changes, invalid retained data, and occupied destinations stop publication without overwriting history. A `LegacyImported` session fact records source identity, owner mappings, record counts, and final flow cursors. The source is verified again before the complete directory is atomically published into `runtime-v1/sessions`. Journal handles are closed before the rename. Reading the imported history no longer requires the original source or project directory.

## Session and flow storage

`flow_store::RuntimeStore::open(data_dir)` uses the isolated `runtime-v1` namespace. A `SessionStore` owns its container journal and an exclusive execution lease. Each `FlowStore` retains that lease while owning its independent journal. Another session owner cannot open the same container while any of those handles remain alive.

```text
runtime-v1/sessions/<session-id>/
  events.jsonl
  session.json
  artifacts/
  flows/<flow-instance-id>/
    events.jsonl
    flow.json
    artifacts/
```

Container facts record session creation, instance registration, and default-view selection. Flow facts record the immutable creation request, source bundle, provenance, and lifecycle transitions. `created_by` is audit metadata, not control authority. The default flow is a view binding and has no privileged lifecycle.

Session and flow creation initialize journals in private directories before publishing their final paths. A shared catalog lock serializes session creation with migration publication. Incomplete initialization directories remain outside the registered inventory. A complete but unregistered flow can be reconciled by retrying the same creation request and descriptor; it cannot be opened through the session catalog. Reusing a request with different creation data fails.

Flow transitions validate an expected state revision, apply to a private candidate, and publish that candidate only after the journal commit succeeds. Completing an invocation preserves the instance. Reopening an active invocation records `HostLost` without executing its entry; existing pause keys remain. Closing invocations retain cleanup obligations, and interrupted instances require explicit recovery before another turn can start.

`session.json` and `flow.json` are replaceable projections with a committed source cursor. They are rebuilt from journals on opening, even when missing or malformed. `take_projection_error` reports cache-write failures without withdrawing an already committed fact. Source bodies remain in the creation fact; reading history does not require a reachable project checkout.

Creating or opening storage does not start schedulers or grant permissions. Hosts authorize commands, validate entry programs, and decide when restored instances may execute. Legacy migration requires an explicit `archive_legacy` call.

### Read-only historical flows

`FlowDescriptor.content` distinguishes `FlowContent::Entry(EntrySnapshot)` from `FlowContent::History(LegacyArchive)`. Historical flows have no executable entry. Their instance state is closed from creation, without fabricating a completion or cancellation for any old invocation. Catalog discovery, default-view selection, committed pagination, and subscriptions use the same interfaces as executable flows. Entry preparation explicitly rejects historical flows.

`LegacyArchive` records the original session, file identity, ownership group, and expected record count. `FlowStore::append_legacy_history` commits ordered `LegacyHistoryRecord` batches containing exact original bytes in base64 alongside their source metadata. It validates ownership, byte ranges, per-record digests, ordering, and count before writing. Duplicate, altered, and excess records are rejected without advancing the cursor. Reopening rebuilds only the import position; history pages read record bodies from the journal and remain available without the original file or project directory.

The journal's content boundary rejects execution facts in historical flows and legacy batches in executable flows. `FlowUpdate::Created` exposes the typed content summary; `FlowUpdate::LegacyRecords` preserves complete imported batches through the existing view feed. These records are history, not newly accepted messages or final-answer notifications. Importing records does not replay tools, create watchers, or wake agents.

## Persistent session management over RPC

The daemon exposes persistent catalogs through the authenticated `/rpc` endpoint and Unix socket. Both transports represent the local daemon operator; arbitrary external principal names cannot acquire a catalog. Catalog ownership stays with the daemon after an RPC connection closes. These methods address `runtime-v1` storage; `run_flow`, `list_sessions`, and `/events` without an instance address retain their existing session execution and history format.

CLI `session list` and `session show` also inspect persistent catalogs directly, including while their executor holds the writer lease. `RuntimeStore::session_ids` discovers published directories, and `inspect_session` rebuilds the catalog through the same journal validation and projection reducer used by recovery. Neither operation creates storage, repairs incomplete tails, rewrites caches, opens flows, or restores execution. Inspection reads a fixed-length file prefix and reports trailing bytes separately. Complete corruption is an error; a damaged catalog in a listing is reported without hiding healthy sessions. These are recorded catalog views, not acknowledgements of an active writer's latest commit or live execution status.

Persistent listings include titles, flow counts, and recorded project paths; `show` includes the default flow and registered flow IDs. Missing project directories remain queryable with `--project`. Published flat session history remains visible, and identical IDs in both layouts are shown separately. Read-only CLI catalog commands bypass configuration migration, notifier setup, and execution services.

| --- | --- | --- |

| `session.open` | `session_id` | Recorded session summary and catalog receipt |
| `session.flows` | `session_id`, optional `before` instance UUID, `limit` from 1 to 50 (default 20) | Newest-first membership page, next cursor, total, and catalog receipt |
| `session.select_flow` | `flow: { session_id, instance_id }` | Summary with the selected default view |
| `flow.get` | `flow` | Atomic execution, Goal, latest completion, and journal cursor; independently observed scheduler status |
| `flow.control` | `flow`, `expected_revision`, `action: pause / resume / cancel_turn / recover` | Durable commit receipt |
| `flow.launch` | `flow`, `request_id`, `expected_catalog_sequence`, absolute `path`, `entry`, optional `arguments` and `invocation` maps, optional `user` content | Durable initial input acceptance |
| `flow.bind` | `flow` | Explicit scheduler binding using retained source and current host configuration |
| `flow.invoke` | `flow`, `request_id`, optional `arguments` and `invocation` maps, optional `user` content | Durable next-turn input acceptance |

Create or open a catalog before addressing its flows. Creating the same session identity and descriptor is idempotent; conflicting creation data is rejected. An omitted project explicitly creates a projectless session. Reopening reads its recorded configuration and project binding without requiring either location to exist. Failed instance reads remain visible as unavailable rows in the membership page, preserving pagination and the total count.

View selection changes only the default binding. Opening, listing, selecting, and reading do not install execution schedulers. Pause and resume use a stable operator pause key, so resuming does not clear another controller's pause. Controls check the execution revision inside the instance writer; stale requests fail. Cancelling a turn preserves the instance, and resuming does not recover an interrupted invocation or resume its Goal. The execution readiness field describes the lifecycle gate, not whether a scheduler is installed or a model is running.

`flow.launch` validates and snapshots the named source entry before creating an instance. The daemon retains scheduling independently of the requesting connection and builds execution services from the session's recorded configuration and project binding. Source changes or deletion do not change later invocations. Matching launch retries return the original acceptance with its current consumption disposition, without rereading source files, repeating execution, releasing pauses, or reinstalling scheduling. Conflicting reuse is rejected. `flow.invoke` queues a typed invocation on that same instance; duplicate requests share acceptance and paused input remains pending. Acceptance certifies durable receipt, not successful execution. Invocation settings are explicitly read by the flow and are not added to conversation history.

Both invocation methods accept `user: { text, images?: [{ data_base64, name? }] }` for the authenticated operator's original input. Text and validated image bytes are committed with the invocation and restored as the same user message; entry arguments remain separate. Invalid images reject the request before instance creation or input acceptance. Omitting `user` retains an internal invocation message. Peer invocations cannot claim user provenance. Changing content under an accepted request ID is rejected.

`flow.output` reads the same final-answer publications exposed to peer flows. Ordinary entry returns are available as typed completion records through `flow.get` and do not become final answers implicitly. Prompt requests use the existing daemon prompt transport with invocation-owned context. `DaemonPromptResolver::new(&state)` retains a weak state reference, preventing cached execution services from keeping their daemon alive.

`GET /events?session_id=<session>&instance_id=<flow>` streams the same committed batches as `flow.events`. Each `flow_update` SSE event contains `{ receipt, facts }`, with its complete `journal UUID:sequence:digest` cursor in the event ID. Apply the whole batch before advancing the local cursor. The optional `after` query selects the initial position; `Last-Event-ID` takes precedence during automatic reconnection so an unchanged EventSource URL does not replay its initial range. Without either cursor, the stream begins at creation. The initial read validates the cursor before successful response headers; malformed, altered, foreign, or ahead-of-history cursors are rejected instead of silently restarting. Legacy `since_seq` is not accepted with `instance_id`.

Instance event streams register for commit notifications before reading history, wait without periodic polling after catching up, and preserve queued changes while consumers are disconnected. A new connection resumes from durable history; retaining a connection is not required for execution. Authentication uses the same daemon bearer token, including the existing GET-only `token` fallback. Read and subscription operations neither install scheduling nor consume inbox input, and disconnecting a view does not cancel a flow. Storage integrity or I/O failures terminate the stream without acknowledging an unread batch; clients retain their last applied cursor for explicit recovery.

`atman logs stream <session-uuid> --instance <flow-uuid>` opens the persistent catalog for reading and prints one JSON batch per SSE event. `--after '<journal-uuid>:<sequence>:<digest>'` resumes after a receipt previously printed in the `receipt` field. The command preserves the same authentication, cursor validation, and read-only execution behavior as the daemon APIs; invalid cursors report the server's reason. Use `--port` to select the daemon port. Stream interruption exits the command; rerun with the last fully processed cursor to resume.

Permission listing, grouping, and resolution reuse `list_permission_requests`, `create_permission_group`, and `resolve_permission_requests` with explicit top-level `session_id` and `instance_id`. Each flow retains its own broker independently of the default view. The daemon registers its approval endpoint before a direct or spawned instance can execute. Pending user approvals are cancelled when the endpoint disappears or their requesting execution terminates; stale or cross-instance decisions cannot authorize effects. See [permission control](permission-control.md) for authentication and embedded endpoint ownership.

After reopening, `flow.bind` attaches scheduling through `SessionHandle::bind_entry`. Launching and binding share source, tool, and configuration validation; the recorded configuration source is used even if the new daemon has no launcher configuration. Invalid configuration leaves the instance available for inspection without installing scheduling. A live scheduler rejects replacement. Binding can admit pending input on an idle instance, but preserves all pause keys and interruption state. `flow.control` with `recover` explicitly changes an interrupted instance to idle under its expected revision; it neither releases pauses nor replays the interrupted invocation. Pending input runs only after scheduling is bound and every execution gate permits admission. Use `resume` separately to remove the operator's pause. Catalog reads and matching launch retries perform neither operation.

## Instance activation

`RuntimeHost::launch_flow` owns creation, result registration, and initial activation across the participating storage owners. The caller supplies a stable creation descriptor and `LaunchInput`, authenticates its sender and inherited context, and supplies authorization for new effects. The host creates or resolves the canonical Prepared instance, obtains a source cursor, commits the requested continuing result subscription at its recipient, and only then activates the source. Current watch grants are checked at registration and activation. The recipient confirmation is an opaque owner-issued proof, not model-provided JSON. No owner lock is held while awaiting another owner.

`FlowStore::activate_with_input` commits activation, the exact initial invocation, inherited context, and result-subscription evidence in one source fact. Before this commit the flow stays Prepared and cannot accept arbitrary input or execute. After it, the common inbox contains the initial invocation and an installed host scheduler can admit it normally. Activation does not itself grant execution authority or install a controller. An incomplete activation restores neither an Open instance nor a pending initial input; complete activation restores both.

The initial request ID equals the immutable creation request ID. Identical retries recover the original acceptance receipt and current consumption disposition, including after restart, pause, or close. Changed launch data is rejected. A failure before activation preserves Prepared state and any already registered result subscription; retrying retains that subscription's original cursor. Concurrent attempts reconcile the authoritative source activation instead of repeating effects. Dropping the waiting caller does not cancel an owned launch attempt.

`RuntimeHost::launch_entry` combines this protocol with retained entry scheduling for trusted host callers. `EntryExecution` supplies the executor, current authority ceiling, trust, cooperative yield interval, and expected catalog cursor. Entry preparation completes before catalog mutation. Direct host launches and `flow.spawn` use this same path; successful activation transfers the controller to the session catalog. Returning or dropping the launch result does not stop subsequent turns. A matching retry returns the original receipt with its current consumption disposition, without releasing pause keys or reinstalling a stopped controller; restoring scheduling remains an explicit `SessionHandle::bind_entry` operation.

Concurrent activation attempts for the same instance serialize scheduler adoption and reconcile the committed launch input; different instances retain independent launch ownership. `SessionDescriptor::source_roots()` supplies recorded `project:` and `user:` namespaces for entry preparation, rebinding, and each admitted invocation. Compilation reads retained source bundles, so removing the original source files does not change subsequent turns. Resolving these namespace paths does not read configuration credentials or authorize execution.

`FlowWorker::status()` reads execution state, Goal, latest completion, and journal cursor atomically. Host views use this projection instead of combining independently sampled completion and execution reads. Scheduling ownership remains a separate catalog observation and does not imply that a turn is currently executing.

`RuntimeHost::wait_quiescent()` lets batch hosts wait for owned turns, scheduler preparation, and notification handoffs without shutting down instances. A scheduler acknowledges the journal cursor it has inspected, so the host does not duplicate entry input selection. Source facts remain outstanding until their observers commit delivery; unrelated journal writes do not count as observable output. Explicit watchers keep a runnable, scheduled recipient alive, while idle spawn result routes do not. Paused, unbound, and policy-ineligible input remains recorded. The wait subscribes before reading and checks for intervening changes before returning; it uses notifications rather than polling. Scheduler and observation failures are reported. Cancelling this wait leaves execution and subscriptions intact.

`RuntimeHost::shutdown()` stops new instance attachment and turn admission, stops catalog-owned schedulers and observers, cancels active execution even when paused, waits for completion facts, and releases journals and process resources. Queued catalog requests without effects fail when their owner stops. Unread inputs, subscriptions, Goal records, and independent pause keys remain stored. Idle instances remain idle; cancelled invocations remain interrupted and require explicit recovery. Shutdown does not close instances or fabricate final answers. Cancelling the caller's wait does not abandon an accepted shutdown; repeated calls observe its original result. Frontend disconnection must not invoke host shutdown.

Daemon SIGINT and SIGTERM close request admission, end SSE streams and accepted Unix connections, and run this shutdown alongside cancellation and cleanup of registered legacy executions. The process marker is removed after cleanup finishes. Event clients can reconnect with their committed cursor; ending the stream does not claim delivery of the remaining shutdown facts. `DaemonState::shutdown()` exposes the same cleanup for embedded hosts and retains ownership when its awaiting caller is cancelled. `register_live` rejects registrations after stopping begins.

`InboxPayload::Invocation` carries typed entry arguments, an invocation configuration snapshot, and optional `UserContent`. It requires uncorrelated `NextTurn` delivery and cannot enter a running model call as a text interjection. `UserContent` shares text, images, and optional quote presentation with `UserSubmission`; only an authenticated user sender can supply it. Both inputs use the same message projection, with the admitted turn identity and user origin assigned by the host. Without user content, invocations project internal sender and argument data. Invocation settings never enter this message. Inherited context seeds the new instance once, survives reopening, and does not become newly published output for result subscriptions. Host preparation selects compatible input and supplies the execution authority.

For an invocation already bound to a persistent instance, `flow.spawn` uses this launch protocol and the common instance scheduler. Source snapshots, declared arguments and defaults, invocation settings, and optional complete conversation history retain their existing contracts. Effective execution authority cannot exceed the caller's ceiling. The caller-bound inventory token also identifies the catalog revision; another registration after inspection rejects new creation before writing it. The launch attempt holds scheduling ownership until activation commits, then transfers it to the session catalog. Failed activation releases that ownership before returning; the prepared record remains available for reconciliation.

`async=true` returns the stable instance address and initial acceptance. `async=false` registers a correlated continuation before launch, subscribes to the exact initial completion before activation, and waits through the common inbox. The caller commits `WaitingContinuation` before returning the saved typed value or error. Both modes leave the instance available after the invocation; later applicable input uses the same scheduler and entry snapshot, even if the source file disappears. The creator's continuing answer subscription excludes only the synchronous initial turn; other subscribers still receive its answers, and subsequent turns notify the creator normally. Ordinary returns do not become final answers.

Cancelling the synchronous caller releases its continuation ownership without cancelling the spawned instance. An unconsumed completion remains in the same inbox, including when it arrives after cancellation. Applicable input can start another turn after explicit interruption recovery; it cannot bypass execution pauses. A completion matching both a watcher and a continuation produces one envelope with both reasons. Consuming that envelope through the continuation does not also schedule model work.

The shared `flow_runtime::entry::EntryRecipe` preparation adapter maps later text to the declared `contract { invocation { user_message: parameter } }` string parameter. Directly bound entries and spawned instances use the same adapter. It preserves message provenance and batches compatible input; an explicit invocation or different invocation settings starts a separate batch. Entries without this mapping retain ordinary text input and accept subsequent typed invocations instead of guessing a parameter. Explicit goal continuations can use the recorded arguments without a parameter mapping. Automatic scheduling after host restart still requires an explicit host binding. Persistent spawning requires `workspace=none`; workspace allocation, durable ownership, and CLI/daemon bootstrap are outside this adapter.

`LaunchInput.execution` can retain an `EntryBinding` with the initial turn/run identities and structural authority ceilings. Persistent `flow.spawn` records this binding with activation. The initial parameters and invocation configuration remain in the launch input; the parameter mapping is validated from the recorded source bundle. Empty identities and a synchronous reply route targeting a different first turn are rejected before activation. A later input with the same request UUID from another sender still receives a new turn/run identity.

`FlowWorker::entry_recipe` reconstructs this entry under the current host's authority; `SessionHandle::bind_entry` explicitly installs the shared catalog-owned scheduler. Recorded and current ceilings are intersected, including shell, permission management, tool tiers, risks, and workspace limits. Incompatible workspace limits reject binding. The host supplies current trust, the executor, and the cooperative scheduling interval. Entry validation and executor scope checks precede trust installation. Binding, initial activation, and generic host scheduling share the instance activation lock; a competing binding cannot replace a live controller or change its trust. Only open instances accept a binding. Attaching a catalog or reading an instance does not install a scheduler; binding does not release pauses, recover interrupted turns, or replay consumed input. Instances created through lower-level storage APIs without a recorded binding remain readable and report that binding is unavailable.

Persistent execution binds relative tool paths and default cwd to the instance's authorized workspace root, including inline function calls. The filesystem policy uses that same root while retaining its access mode; an explicit session mode change still applies. File-tool approval and installed flow discovery resolve against the same project rather than the host process directory. Unrelated checkout metadata supplied by the host is removed; an ordinary project directory does not become a registered worktree. An instance without a project root requires explicit absolute paths rather than borrowing the host process's cwd. Named user-installed and bundled flows remain available, while relative file references require a bound directory. Missing project paths do not prevent history access or binding; tools report unavailable paths when performing actual I/O. Unbound non-instance calls retain process-cwd path resolution.

## Project knowledge

Project knowledge is registered separately through `tools::register_project_memory`, using an explicit storage root, optional index, and confession redactor. `AtmanRuntime` supplies its bound `ProjectContext::storage_root()` and configuration source; projectless runtimes do not expose these project tools. Confessions and specs are shared by sessions and peers in that project and remain available after rebuilding the runtime. Registration itself does not create directories. CLI and daemon setup reuse this factory with their existing indexes. File-backed non-instance Goal, Plan, and Todo registration is available independently through `tools::register_file_memory`.

## Instance plans and todos

`AtmanRuntime::build` registers flow memory tools directly; embedded hosts can also call `tools::register_flow_memory`. Instance calls need an admitted `FlowClient`, with no temporary session directory or file store required. An instance context without its host binding fails before accessing legacy controllers or stores. `tools::register_memory` retains explicit file-backed registration for existing non-instance sessions. The Goal, Todo, and Plan tool structs accept optional legacy stores, with `Default` providing no file fallback.

`flow_store::planning` records plans and todos in the instance journal through `PlanningRequest` and `PlanningEdit`. The storage owner selects the latest plan, assigns new todo IDs and timestamps, and commits each mutation before returning its `CommitReceipt`. An optional planning revision rejects stale interactive edits. Matching sender/request-ID retries return the original result and receipt, including after closure, without rolling back subsequent changes; conflicting payloads fail. New writes require an open instance and host authorization.

`FlowWorker::planning` and the existing Session plan/todo subscriptions project the same committed records. `plan.write/read/tick` and `memory.todo.*` resolve the admitted invocation's `FlowClient`, so a shared tool registry does not share planning data between instances. Inline calls use their owning instance; spawned peers have independent plans and todos. Missing instance bindings fail rather than falling back to a captured legacy store. Ordinary file-backed stores remain available for existing session readers and use the same entry reducers. Plan changes do not modify the Goal or execution state, and reopening restores the recorded timestamps and completion markers without replaying tools.

## Durable input acceptance

`FlowStore::publish_message` commits an exact message with its owning turn lease, producing invocation, and stable publication ID. An identical retry returns the original receipt without appending or republishing; conflicting content fails. New publication requires a live matching turn, rejects cancellation and stale epochs, and permits delivery while a paused turn finishes. Message origin and role remain separate. Final-answer recognition stays in the existing message protocol rather than a second storage-specific classifier.

`context_messages` restores the latest committed model window and merges subsequent shared input and output in journal order. `history_messages` retains the complete shared conversation independently of that window. Reopening does not invoke tools, replay notifications, or execute the entry. Publications do not end the turn or change Goal state.

## Model-window checkpoints

`FlowStore::checkpoint_context` commits a replacement model window without changing original messages, entry results, or lifecycle state. `ContextCheckpoint` carries a stable identity, the digest of the exact prior window, the replacement messages, and compaction metadata. Matching retries return the original receipt without resetting later messages. Conflicting identities and stale windows fail before writing. Inbox acceptance and unrelated controls do not invalidate a checkpoint; newly committed context does.

Session compaction calculates a replacement using the existing summary and review policy, then awaits the instance's serialized writer before updating the model handle, message projection, cache epoch, or completion frame. An accepted write survives caller cancellation. A failed or unavailable writer leaves the window unchanged and reports the failure. The weak writer binding does not retain the storage owner.

Reopening seeds the model window and full history separately, preserves messages appended after the checkpoint, and restores the cache epoch from the checkpoint itself. An incomplete checkpoint retains the previous committed window and its tail. Compaction does not publish another final answer or create another notification. Persistent spawned peers use the same path as other instances; isolated inline fanout contexts remain invocation-local and are not resumable instances.

## Persistent goals

Each instance journal retains goal creation, text edits, pause, resume, and clearing as `GoalUpdated` facts. Requests carry an authenticated sender, a request UUID, and the expected goal identity and revision; an absent expected version explicitly means that no goal may exist. The shared `memory::goal::GoalEdit` operations validate changes. Committed timestamps and generated identities replay exactly, including clearing the current record, without a separate authoritative goal file.

`FlowWorker::edit_goal` serializes the write, updates the live goal projection and subscribers after commitment, and returns the recorded goal with its commit receipt. Matching request retries return the original result without replacing newer projected state. Conflicting requests, stale revisions, and new edits after close fail. Accepted writes survive caller cancellation. Restoration retains the saved goal status; interrupted execution is represented by the instance lifecycle instead of rewriting the objective.

`FlowClient::read_goal` requires context-read or goal-management access; editing another instance requires an explicit goal-management grant. Checks run again inside the target owner, and peer callers cannot impersonate user or runtime actors. Creation relationships grant no additional authority. Goal changes do not remove execution pauses, invalidate unrelated inbox messages, or control peers. Automatic continuation remains an entry policy admitted by the host scheduler.

## Input acceptance

`GoalContinuation` is an entry-authored next-turn input tied to the active turn lease and an exact active goal version. `FlowStore::schedule_goal` creates one stable request identity for that pair; retries retain the original receipt and conflicting text is rejected. A goal changed or paused after preparation returns no acceptance without failing the entry; invalid identity, authorization, or storage still returns an error. The proposal shares the ordinary inbox and cannot enter an active model context. It does not start execution until the proposing turn has completed and ordinary execution gates permit admission.

Goal edits, pauses, replacement, or clearing cancel proposals whose acknowledged goal is no longer active and current. Cancellation, failed execution, and host loss invalidate the proposing turn's continuation without discarding unrelated messages. Admitting another invocation consumes its selected input and cancels unselected continuation proposals in the same commit. Original request bodies and cancelled receipts remain available after reopening. Execution pause alone retains proposals; resume does not change goal state or authorize interrupted work.

`memory.goal.schedule` uses the caller-bound `FlowClient` to submit this proposal. The shared entry adapter selects ordinary eligible input first, or one continuation when none is available. A continuation uses the source turn's committed entry arguments and invocation configuration rather than creation defaults. `last_invocation_input` and the scheduling snapshot expose that exact admitted configuration through an index rebuilt during journal replay. Continuation text has internal origin and user protocol role; it is neither a new user request nor new authorization. The scheduler only admits prepared inbox input and never infers another turn from an active goal.

`FlowStore::accept_input` persists a typed delivery request before returning `Acceptance`. User submissions retain text, images, invocation configuration, and presentation data. Interjections, flow events, watcher notifications, timers, and internal controls remain distinct payload variants with sender, recipient, correlation, cause, scope, and delivery mode. A protocol message role is not used as a provenance label.

The host authenticates the sender before calling storage. A matching sender/request ID retry returns the original acceptance receipt and current disposition, including after restart, revocation, or closure. Reusing that identity with different content fails. New inputs additionally require an open instance, consistent source/payload categories, and a successful `authorize_new` callback. Host-only delivery types cannot be accepted as user or peer-authored controls.

Paused and interrupted flows retain accepted inputs in FIFO order without resuming execution. A durable close transition cancels the pending inputs in the same replayable state change, preserving their bodies and original acceptance receipts. New requests to a closing or closed instance fail; already accepted requests remain accepted facts with a cancelled disposition. Acceptance does not mean an input has reached a model or completed business work.

## Atomic input admission

`reserve_context_input` reserves eligible `AtBoundary` messages for a running turn. `reserve_invocation_input` reserves an idle instance's inputs against a candidate turn lease without starting that turn. Both use the same inbox ownership primitive. The host chooses compatible submission configurations and prepares the actual input; storage does not infer model settings, user authority, or agent policy from message text.

`commit_input` validates reservation ownership, state revision, turn lease, target, and FIFO membership. A context commit records the exact messages and consumed envelope IDs together. An invocation commit additionally records `TurnStarted`, entry arguments, and invocation configuration in that same journal batch. An entry or model request must not execute before this commit succeeds. Context messages must belong to the admitted turn, and `NextTurn` messages cannot be consumed at an active-turn boundary.

Execution state changes revoke outstanding reservations. Releasing or dropping a receipt retains pending messages; late commits and releases cannot consume or release a newer batch. Finishing, cancelling, paused, interrupted, and closed instances cannot admit ordinary context input. A failed validation leaves the queue and journal unchanged; a failed journal write requires reopening and reconciliation.

`committed_inputs` exposes durable input records with their commit receipts. Replay restores the exact input instead of preparing it again, and committed messages do not return to the pending queue after interruption or closure. Acceptance retries retain their original receipt and report `InputCommitted` once consumed. This state does not assert model inclusion or business completion. Incomplete invocation batches restore neither a turn nor consumption; accepted inputs remain pending.

## Correlated continuation input

`register_reply_waiter` durably binds a correlation ID to a turn lease and expected authenticated sender before the corresponding request is sent. Identical registration retries return the existing record; conflicting reuse and registration after matching replies have arrived fail. Multiple independent waits can belong to one turn. Correlation IDs are not authorization credentials.

`reserve_reply_input` selects the oldest matching `AtBoundary` reply from the existing inbox while the turn is running or waiting for replies or effects and all execution pauses are released. Reply ownership belongs to the registered continuation, so other branches need not stop running. Execution-gate waits, finishing, cancellation, and closure prevent delivery. Ordinary context and invocation reservations exclude replies owned by live waiters. Every consumer uses the same opaque batch ownership; there is no parallel reply queue. `commit_input` with `WaitingContinuation` persists the actual continuation value, consumed message ID, and delivered waiter status in one fact. It does not change other branches' progress, create a turn, wake a Rust future, or claim that the continuation executed; the host resumes execution only after successful commit and execution admission.

Pausing retains registrations and accepted replies while revoking reservations. `cancel_reply_waiter` releases unconsumed replies to ordinary input without discarding them or releasing execution pauses. Finishing, cancelling, ending, closing, and lost turns cancel their outstanding waits as part of the same durable lifecycle transition. Restart does not reconstruct suspended Rust futures: uncommitted replies remain pending behind interruption recovery, while delivered replies retain their committed input and are not delivered twice. Reply records remain available through `reply_waiters`, including cancelled and delivered states.

`FlowClient::prepare_reply` establishes an owned `ReplyWait` before a request is published. Its completion wait subscribes to committed changes before inspecting the inbox, validates the source turn, and commits consumption through the recipient owner. Concurrent continuations retain independent ownership without changing the whole flow's phase. Dropping an unfinished guard cancels only that waiter; lifecycle recovery also releases abandoned waits. Retrying a delivered wait reads the committed continuation value without consuming another envelope.

## Durable sends

`queue_send` records a flow-owned delivery request before contacting its recipient. New sends require execution admission, consistent sender provenance, and successful host authorization. Matching request ID retries return the original record before applying new-send gates; conflicting reuse fails. An optional reply waiter must name the same correlation, current turn, and target flow. A new waiter and its send intent are committed together; an identical pending registration may also be reused.

The transport copies a recorded request to the addressed flow's `accept_input`, then passes its authenticated `DeliveryReceipt` to the sender's `confirm_delivery`. Same-session and cross-session delivery use these same storage APIs. Recipient acceptance and sender confirmation are separate commits; no cross-journal atomicity is implied. Delivery does not wait for recipient execution, and a scheduler must not hold a session-wide lock while contacting another flow.

`pending_sends` exposes unconfirmed intents in recorded order. Lost acknowledgements remain pending across restart and closure until reconciled against the recipient's idempotent acceptance. A retry can therefore recover an existing receipt after revocation or closure without authorizing a new delivery. The host must still enforce current delivery scope for previously unaccepted requests; storage does not automatically resend or bypass authorization. `confirm_delivery` accepts reconciliation after the sender has stopped, rejects conflicting confirmations, and validates the recipient journal identity. The transport authenticates the peer and binds the acknowledgement to the full address and request; a journal digest is not a signature.

An accepted send records receiver acceptance only. It does not assert that a model read the input, that a continuation executed, or that business work completed. Sender history retains the send intent, queued receipt, and receiver acknowledgement, while receiver history retains the accepted envelope and subsequent input disposition.

## Instance execution bindings

`Executor::run_linked_with_invocation` accepts `RootInvocation.instance`, an `InstanceInvocation` containing the host-admitted turn lease, explicit authority ceiling, and cancellation token. The executor registers an instance identity in the existing permission pipeline and uses the recorded turn and run IDs. It does not derive an authority ceiling from root status. Entry capability declarations may narrow the supplied ceiling but cannot broaden it. Inline calls retain the instance address and inherited restrictions.

`Session::open_instance_context(address)` creates an isolated in-memory execution context for one instance, with its own messages, Goal controller, watcher state, and interaction services. Its session ID identifies the container; its flow address identifies the context owner. Passing this context without an explicit matching instance binding fails before execution. A mismatched context, turn, or initial run also fails. Clones of an execution binding share one consumption flag, preventing reuse of the same binding for another execution attempt.

The host compiles the recorded source bundle, commits invocation input, and constructs a binding only after durable admission. It then runs the existing executor and commits the lifecycle outcome after invocation cleanup. These APIs do not themselves schedule pending inputs or revalidate pause changes during a running invocation; those responsibilities remain with the owning host. Creating a context does not create another on-disk session or replay unknown effects.

## Instance storage worker

Journal history supports bounded `read_after` pages using a complete `CommitReceipt`. Cursor validation checks the journal identity, sequence, and digest; foreign, altered, and ahead-of-history cursors are rejected. Pages preserve whole commit batches and resume after the last returned receipt. A metadata index rebuilt during recovery locates each committed file range without rescanning earlier records or cloning cumulative history. Reading a page does not move the next append position or consume flow input.

`FlowStore::read_updates` projects these batches into typed `FlowUpdate` records. Conversation publications preserve message origins and isolated context identities; input acceptance, input consumption, final answers, execution diagnostics, and turn completion remain separate facts. Creation updates omit retained source bundles, and activation updates omit execution authority. Readers receive complete committed batches in their original order rather than reconstructing history from display diagnostics.

`FlowWorker::read_updates` and `subscribe_updates` share the same cursor and projection. Subscription registration and initial cursor validation finish before the stream is returned. Committed changes between registration and the first consumer poll are recovered through paged history; coalesced notifications never substitute for reading that history. Idle streams wait for commits without polling or emitting empty pages. Reconnection resumes after the last applied batch, and dropping a view does not pause or cancel execution. This feed contains committed state, not speculative streaming text.

`flow_runtime::FlowWorker::start` takes exclusive ownership of a `FlowStore` and restores its conversation through the existing message projection. Commands are serialized per instance; blocking journal work runs on the blocking pool, and an idle worker does not occupy a thread. Accepted commands complete even when their awaiting caller is cancelled. `shutdown` drains accepted work and hands the store back without changing the recorded execution lifecycle. Hosts stop active execution before handing off storage; an unexpected loss of storage cancels bound execution and leaves recovery to reconcile the recorded lifecycle.

`InstanceInvocation::with_storage` binds the executor to the worker's exact context and validates its admitted lease. `session.push`, `final.answer`, recorded model responses, and context records commit before updating context or publishing complete-message frames. The worker performs projection before acknowledging, so losing the acknowledgement does not suppress a committed reply. The same final-answer normalization and publication path serves stored and ephemeral execution. Draft streaming remains transient.

Inline calls share the instance context. Fanout calls retain isolated invocation contexts: their publications remain in the owning instance journal with `context_run`, and recovery does not merge them into the shared conversation. Message scheduling claims use the instance address rather than serializing every flow in a session.

Worker binding covers message publication, model-window checkpoints, persistent spawn execution, and process resources. Process watcher tools use the instance inbox; generic flow watcher tool routing and product scheduling still require integration. Existing CLI run and REPL dispatch remain on the legacy path, while instance-addressed daemon operations use the persistent host.

### Flow process resources

Each persistent `FlowWorker` owns an `InstanceResources` group containing its `BgRegistry`, `TermRegistry`, and `TaskRegistry`. Bound executor invocations use that group across turns; inline calls share it, and persistent peers use their own worker's group. Handles and task operations cannot access a sibling's registry, even within the same session. Instance invocations without storage do not inherit a runtime's process registries implicitly.

Background processes use the resource owner's cancellation lifetime. Completing or cancelling a turn and pausing execution do not close that group. Explicit process/task termination still stops the selected process. `CloseRequested` commits before closing process admission and requesting cleanup; the worker publishes the state and acknowledgement only after admission is closed. A terminal created concurrently with closure is terminated before it can be registered. `Closed` rejects unfinished process cleanup.

`FlowWorker::shutdown` drains accepted storage commands, stops process resources, waits for their output readers to finish, and returns the journal. Retained context or resource readers do not keep those processes alive. Unexpected owner loss requests cleanup without inventing a durable terminal state. Reopening creates empty live registries and does not recreate processes from history.

Process logs, attachments, and large tool output use the owning `FlowStore` directory under `sessions/<session>/flows/<flow>`. Legacy Plan/Todo refresh entry points leave journal-backed projections intact. Legacy invocations retain their existing turn cancellation behavior and process registration APIs.

### Invocation-owned interactions

`ToolCtx::prompt_resolver()` binds the configured host transport to the calling invocation. `PromptResolver::register_in_context` receives the original event sink, owning context, run identity, and tool-call identity. The daemon bridge retains only shared transport state; it no longer captures one session or event sink at construction. Inline and fanout calls retain their owning instance even when a branch isolates its model context.

`ToolCtx::form_resolver()` selects that transport or the attached form registry through `FormPromptResolver`. The TUI uses the same runtime adapter. VM entry binds interaction context for language intrinsics and registered tools, so parallel context isolation does not bypass confirmation. Both paths share prompt wait ownership: cancelling or dropping execution removes waiting forms; `form.ask` retains a reply route after a normal timeout, while `user_confirm` closes its confirmation request.

Form, approval, and compaction-review registries publish their current records within a serialized snapshot update. Snapshots retain changes while views are detached, so reopening a view shows pending interactions without restoring cancelled records. This live-view contract does not persist unresolved prompts across process restarts.

Pending and resolved daemon events use the same captured sink, including cancellation and late responses. Registration publishes the pending event before concurrent resolution can publish its answer. Prompt waits release their registration when their future is dropped, even if their own cancellation branch never runs. Expired forms intentionally retain their late-answer route.

The TUI can display forms from multiple flows through one registry. Each record retains its originating run, tool call, and deferred-answer inbox independently of the current view. `FormRegistry::request_with_inbox` makes that destination explicit; ordinary `request` uses the registry's default inbox.

For persistent instances, late answers use the owning flow's durable inbox as `FormReply` envelopes. The host validates the original form and destination before submitting; prompt identity determines a stable request ID. Matching retries reuse acceptance, including after consumption, while conflicting answers are rejected. Accepted answers survive reopening, obey execution pauses, and use the same input reservation and commit path as other boundary messages. Their model-facing role is `user`, with `Interjection` origin; they do not grant permission or resume paused work. Legacy sessions retain their deferred-form event path.

`FormRegistry::submit`, `DeferredFormInbox::record`, and daemon prompt resolution are asynchronous and return storage errors. Late-answer routes remain available until acceptance succeeds. Concurrent submissions serialize per prompt without holding the registry lock during storage I/O. The TUI retains drafts until acknowledgement, reports failures in the form, and ignores receipts from earlier submission attempts. Configuration forms follow the same acknowledgement contract. Accepted-answer recovery does not restore unanswered prompt registrations or suspended tool futures across process restarts.

Registered transports return `FormSubmission` for both `form.ask` and language-level `user_confirm`. The latter shares its decision check with the in-process registry: one positive confirmation returns `true`; rejection, malformed submissions, and transport failure return `false`.

## Execution diagnostics

Persistent instance execution sends node, tool, model-usage, and resource diagnostics to the owning flow's event sink. Inline calls and fanout retain that instance binding; peer instances use separate sinks. Concurrent producers allocate sequence positions, forward, and update the live projection in one order.

`ExecutionEvent` records an `ExecutionScope`, instance-local sequence, timestamp, and typed event. Invocation scope retains the producing turn lease. Instance scope accepts permission-service diagnostics independently of the active turn; audit payloads retain their original requesting run, group, and decision identities. `FlowStore::execution_events` and `FlowWorker::execution_events` return both scopes through the same batches and journal receipts. Conversation messages, Goal changes, lifecycle transitions, and model-window checkpoints remain in their existing facts; execution batches cannot substitute for those records. Sequence positions identify local event order, while journal receipts identify durable commit order.

`RuntimeHost::with_redactor` or standalone `FlowWorker::start_with_redactor` binds diagnostic redaction for the writer's lifetime. That policy applies to service events during execution and idle periods. An invocation can supply a separate execution policy through its source event sink; otherwise it retains the writer's policy. Audit capture is installed before context services are constructed and never switches to a newly active turn. Reading saved audit events does not restore pending approvals or replay permission decisions.

The existing flow writer drains captured diagnostics before applying commands, including message publication and turn completion. Redaction and disk writes run on the storage worker. Diagnostics from a completed turn's retained resources keep their original lease and can arrive during a later turn. Storage handoff drains resources and remaining diagnostics before returning ownership. Reopening restores the committed batches and advances new event positions beyond their recorded high-water mark without reexecuting work. A failed journal write stops that writer and prevents acknowledgement of later commands.

Diagnostic backlog applies backpressure at invocation suspension boundaries. The executor waits for the writer when a transport batch is pending, while pause and cancellation remain observable. This preserves diagnostics without allowing a CPU loop to continually grow pending writes; it does not set an operation budget or drop events. A cooperative quantum and independently running resource callbacks can still emit events before reaching that boundary.

## Owned instance turns

General model calls using shared session context claim compatible `AtBoundary` inbox messages before reading that context. The storage worker reserves, commits consumption and exact messages, and updates the conversation projection as one owned command. Auxiliary extraction, explicit message overrides, context-free calls, and isolated fanout branches do not claim shared input. Inline calls use the same instance inbox.

Submission settings must match the current invocation snapshot, and image submissions remain pending when the selected model cannot accept images. `NextTurn` input and replies owned by continuation waiters stay queued. Scoped input remains pending until a host scope resolver is bound. Paused and finishing turns do not claim new input. Peer deliveries retain sender metadata and a non-user origin even though the model protocol role is user. Committing context does not certify that a model received or handled it; model failures and process recovery retain the committed context without requeuing those envelopes.

`FlowWorker::start_turn` receives an explicit `TurnRequest`: ordered accepted envelope IDs, turn/run IDs, arguments, invocation configuration, context messages, authority ceiling, and cooperative yield interval. It compiles the recorded source bundle before admission, validates the selection, and commits input consumption and turn startup together. Invalid source or stale selection leaves input pending. Actual entry execution uses the existing executor and never holds the journal owner across a model call or tool wait.

The worker starts and owns the execution task before returning a `TurnTicket`. Dropping the ticket or its waiter does not cancel the task or its terminal commit. The worker permits only one execution claim for a live lease, including when callers construct separate execution bindings. Completion is acknowledged after invocation cleanup and one durable fact containing the exact entry result and terminal state. Failure and cancellation become explicit interruptions; cancellation cannot be reported as successful completion. Unknown effects are not retried.

`FlowStore::finish_turn` retains a `CommittedCompletion` with the turn lease, finish timestamp, execution outcome, typed result, and commit receipt. Identical retries return that receipt, including after reopening; a different result for the same lease is rejected. Execution controls can force a cancelled outcome even when the entry returned a value. Recovered host loss and explicit lifecycle completion without a return are recorded as `unobserved`, never as an invented value. An incomplete terminal write restores neither its result nor a successful terminal state; normal abandoned-turn recovery records the interruption.

`StoredValue` preserves primitive types, field order and duplicate field names, list nesting, floating-point bits, supported host payloads, and returned error values. Floating-point bits use eight big-endian bytes so JSON adapters preserve negative values, signed zero, and NaN payloads without converting an unsigned 64-bit integer to an imprecise number. A returned error value remains distinct from a failed invocation. Process-local closures and pending calls are marked unavailable for restoration, as are host payloads that cannot be serialized; they are not replaced with null or executed during recovery. A direct `TurnTicket` observer can receive the original in-memory value; persistent synchronous spawning restores the recorded value and reports unavailable results explicitly. Reading a saved return does not append it to conversation history or publish `final.answer`.

`FlowWorker::completion` reads a saved result by turn, or the latest completion when the turn is omitted. `FlowClient::read_result` applies current output-read grants at the target owner. The shared `flow.result(handle, turn?)` tool returns `{ completion: ... }`, with null for an absent record. Its stored result uses tagged types, such as `{ kind: "returned", value: { type: "int", value: 42 } }`; the completion also identifies the producing lease and outcome. Reading the latest completion does not imply that the currently active turn has finished. This tool requires a persistent instance binding and does not fabricate results for legacy run handles.

`subscribe_state` provides the committed lifecycle snapshot, updated before a command acknowledgement. The executor waits at suspension boundaries while independent execution pauses remain, continues cleanup during cancellation, and permits finishing work to settle. Resuming one pause key does not remove others. Host-selected `yield_interval` makes CPU-only code reach suspension boundaries without an operation limit or a language-level default budget. A closing instance cancels its active turn and remains closing until the host completes resource cleanup.

`subscribe_commits` also observes inbox delivery and other durable changes that leave lifecycle state unchanged. Subscribe first, call `borrow_and_update` before `snapshot`, and await `changed` only after finding no admissible work. This order retains arrivals between an empty scan and the wait. `snapshot` reads lifecycle, journal cursor, and pending input in one serialized command. Commit notifications coalesce and wake all subscribers; readers must recheck eligibility rather than treating a notification as an execution grant. Reads, rejected writes, and idempotent retries do not emit notifications. Reopened workers expose their restored cursor and pending input immediately.

`FlowWorker::schedule` owns one event-driven admission loop per instance. A host preparation callback chooses the ordered input IDs, invocation arguments, context, and authority from a committed snapshot; it can decline input without consuming it. The callback performs local preparation, not external I/O. Admission verifies that the snapshot cursor is still current before compiling and committing the turn. A concurrent input or control change causes a fresh scan. Idle, paused, active, or interrupted instances wait for committed changes instead of polling.

After a completed turn, the scheduler rechecks pending input and can start another turn on the same instance. Interrupted execution requires explicit recovery. Preparation or storage failures stop the scheduler and remain observable through `FlowScheduler::wait`. `stop` or dropping the scheduler handle prevents further scheduling; already queued admission commands settle, and admitted turns retain their execution and terminal commit obligations. Explicit execution controls pause or cancel a turn. A stopped scheduler releases its ownership so another host controller can attach.

`SessionHandle::schedule_flow` installs this same controller under catalog ownership. Views and requesting invocations receive a status stream; dropping it does not stop admission. `scheduling_status` reports Running, Stopped, or Failed independently of the flow's execution state. Preparation panics become observable scheduling failures and retain unconsumed input. A live controller rejects replacement; `stop_scheduling` relinquishes admission without cancelling an admitted turn. A failed controller can be explicitly replaced, and reopening a stopped storage worker releases its previous controller before binding another writer. Catalog shutdown stops owned controllers. Recovered instances require a fresh trusted executor and preparation policy; reading history does not grant execution authority.

Input policy, instance directory ownership, management authorization, and CLI/daemon integration remain host responsibilities. Automatic admission does not assign root privileges or infer a goal from message text.

## Host directory

Session journals retain explicit peer access grants and revocations. Grants name a registered source flow, a target flow/session or all sessions in the same host, and a set of actions. Same-session discovery, sending, watching public output, and reading public output are default capabilities. Full context reads, peer execution control, Goal management, and delegation require explicit authority; default-view selection and creation provenance do not supply it.

`SessionStore::grant_access` and `revoke_access` require the expected catalog cursor for new changes. Repeating an unchanged grant or revocation does not write another fact. A revoked grant identity cannot be reused to restore permission; renewed authority uses a new grant identity. Recovery rebuilds policy from the journal, ignoring disposable metadata. These storage operations are trusted-host primitives, not direct peer commands; callers still authenticate sources and enforce the resulting policy at operation admission.

`flow_runtime::host::RuntimeHost` attaches exclusively owned session catalogs. Each `SessionHandle` serializes catalog creation and default-view changes on a bounded command queue. Accepted catalog operations finish even if their waiting caller disappears. Disk work runs on the blocking pool; idle catalog owners do not occupy threads.

Repeated `open_flow` and matching `create_flow` calls return the same live `FlowWorker` and conversation context. Opening another view does not reopen its journal or interrupt execution. Creation payload conflicts fail. After explicit worker handoff, reopening still requires exclusive journal ownership and reconciles an unfinished recorded turn as `HostLost`; it does not replay execution.

The host routes both same-session and cross-session delivery by complete `FlowRef`. Known instance handles are looked up without entering the catalog command queue, so unrelated catalog writes do not serialize their input or execution. Callers authenticate senders before routing, including retries, and provide authorization for new deliveries at the receiver's commit boundary. Routing does not grant authority, start a flow, or couple the recipient to its creator's lifecycle. Accepted retries retain their original receipts.

`select_default` changes only the session's view binding. It does not change execution state or permissions. Dropping catalog handles does not cancel instance handles held elsewhere. Host policies prepare eligible input using `flow_runtime::input::context_message` to retain message provenance; projection itself does not authenticate, consume, or authorize input.

`RuntimeHost::bind_invocation` issues an opaque `FlowClient` for an authenticated admitted turn. Its operations derive the sender from that binding and check current grants before target lookup and again inside the target worker. Stale, paused, finishing, or unavailable source invocations cannot initiate peer operations. Catalog grant changes become visible only after their journal commit; already queued reads and controls recheck revocation before acting.

The client exposes execution inspection, public final-answer reads, authorized private context reads, reliable interjections, and revision-checked execution controls. Public output excludes isolated branch publications. Each controller owns a distinct persistent pause key, so its resume cannot remove a user pause or another flow's pause. Cancellation requests cleanup without forging completion. A committed send may finish delivery after its source turn ends, but new receiver admission still checks current grants.

Host-owned workers automatically bind this client into the executor's `ToolCtx`; inline calls and fanout branches retain the originating instance identity. Separate spawned agents cannot inherit that client as their own identity. Workers hold a weak directory reference, avoiding an ownership cycle. A persistent invocation without its host binding fails peer operations instead of consulting the legacy run registry.

The shared `flow.status`, `flow.output`, `flow.interject`, and `flow.kill` tools use the invocation's instance binding. A target handle is an instance UUID within the same session, or `session-uuid/instance-uuid` across sessions. Status returns execution state, revision, and pause state separately. Output retains character-based cursor pagination over committed public answers. Interjection returns a durable delivery status and supports `at_boundary` or `next_turn`; an optional stable UUID `request_id` reconciles identical sends without duplicate input. Cancellation requires `expected_revision` from status and explicit control authority; it requests turn cleanup and preserves the instance. Persistent interjection rejects legacy L2/L3 redirect controls. Legacy session invocations continue using their run handles until their entry points switch storage.

`flow.instances` uses the bound client's session catalog rather than the transient execution registry. It includes the default flow and prepared, idle, interrupted, paused, and closed peers. `limit` bounds a page to 1–50 entries; `next_cursor` can be passed as `before` for older registrations. Registrations added between pages do not repeat previously listed instances. A missing cursor is rejected instead of silently restarting pagination. State fields share the `flow.status` projection, and the response identifies the catalog revision; individual execution states are read independently, not as a cross-flow atomic snapshot.

Discovery reads only summaries and does not grant context or control access. Unavailable journals remain listed with an explicit error. `SessionHandle::describe_flow` reuses live writers; inactive journals are recovered and released without retaining conversation contexts, installing observers, or scheduling execution. Recovery marks an abandoned active invocation interrupted, as normal owner recovery does. Persistent instance listing requires a live host binding and cannot fall back to the legacy run registry. Existing session invocations also support bounded cursor pagination over their registered run handles.

The directory does not yet replace CLI/daemon session ownership. Grant management, outbound retry policy, managed Goal continuation, resource ownership, and legacy history migration require the same host integration before those entry points switch storage. Discovery retains the caller-bound spawn permit and records its catalog cursor; that permit alone is neither a durable instance creation request nor an execution grant.

## Flow event subscriptions

Flow event subscriptions belong to the receiving flow's journal. Registration records a source-owner cursor, an event filter, one-shot behavior, the notification purpose, and registration time. Watchers may specify an absolute deadline; internal result routes and correlated reply subscriptions cannot expire. A source can remain Prepared while a creator records its result subscription; activation is a separate authorized operation. Repeating an identical registration is idempotent, and cancellation never reactivates its identity. Closing a recipient cancels active subscriptions while preserving their history.

`FlowSubscription` selects events with `FlowEventFilter`: all final answers, answers containing text, answers outside a specified turn, entry completions for all turns or one exact turn, or instance closure. `events_after` merges committed final answers, entry completions, and closure in source journal order and returns bounded pages; private branch output is excluded. Completion notifications carry the saved typed result, execution outcome, lease, and receipt. An entry completion is distinct from a final answer; observing an ordinary return or interruption does not publish a reply.

The closure event uses the receipt of the committed `Closed` transition, rebuilt from that transition on reopening. Capturing an anchor from a closed source rejects new registrations; a closure after anchor capture remains observable. After observing closure, matching subscriptions become `Matched` even in persistent mode, and other unexpired active subscriptions become `SourceClosed`. Only selected event types enter the inbox. Accepted replies remain queued; pending correlated waits without an accepted reply or an active route are cancelled in the same observation commit. A deadline that elapsed before observation still produces its expiry notification.

`observe_events` evaluates all active subscriptions to that source together and commits cursor updates and inbox acceptance in one receiver transaction. A source fact matching multiple subscriptions produces one inbox item with all matching reasons. Delivery identity derives from the source address and journal position, independently of subscription IDs. A repeated page cannot create another input, including after that item has been consumed or the process has restarted. A page containing only unmatched event types still advances its cursor so later matching events remain reachable. Cancellation before observation excludes the cancelled subscription; cancellation after acceptance does not remove queued work.

Only observable event positions advance the cursor. Unrelated commits do not generate cursor-only work, including for self-subscriptions. A page that skips an unobserved source position is rejected. Torn receiver transactions recover neither consumption position nor accepted input; the original source page can be observed again. These storage operations require trusted source handles and host authorization.

An exact one-shot completion subscription can carry a `ReplyWaiter`. A new waiter and subscription commit together; an existing identical pending waiter can also be bound. Conflicting correlations for the same source completion are rejected. All subscriptions matching one completion share its reply ownership. Cancelling the last active subscription for a pending correlation cancels its waiter in the same commit if no accepted reply remains; cancelling an already matched subscription preserves the queued reply.

Each opened host-owned worker has an observation task owned by its session catalog. `FlowClient::watch_events` records registration before acknowledgement; an identical retry preserves the original position and never reactivates a cancelled or matched subscription. `unwatch_events` cancels the caller's subscription without removing previously accepted input. These operations require an admitted invocation; existing subscriptions continue after its turn ends and while execution is paused. Answer and completion subscriptions use the same observer, authorization checks, commit notifications, cursor recovery, and inbox.

The observer establishes change receivers before scanning source events and advances bounded pages through the receiving worker's single writer. Watch authority is checked before source reads and again at receiver admission. Revocation retains the subscription and cursor without delivering new content; granting access again wakes observation and permits catch-up. Source commits, recipient commits, session attachment, and access changes drive scans without a polling timer. A newly attached source session also wakes retained subscriptions. Catalog ownership uses weak host references, so idle observers do not keep the directory alive.

`FlowWorker::subscribe_observation_issues` exposes blocked sources and their reasons. Storage failures retain progress and can be retried with `retry_observations`; no empty turn is started to retry delivery. Reopening a worker restores its subscriptions, while a catalog attachment alone does not eagerly open every recorded flow.

`expire_flow_watches` commits expiry and its timer notification together. Matching uses the receiver's observation time: an answer accepted before the deadline remains queued, and an answer observed at or after the deadline does not match that registration. The host observer handles deadlines independently of source access, source availability, or execution pauses. Expired, matched one-shot, and cancelled registrations do not produce another deadline notification after reopening. Flow and process watchers share one identity namespace within their owner.

## Process watch storage

`FlowStore::register_process_watch` records a process incarnation, handle, pattern, source position, one-shot behavior, and optional absolute expiry. Bash and terminal sources have distinct types. Reusing a handle for a different process requires a new incarnation. Identical registration retries preserve the original position and terminal status; they do not restart observation or extend the deadline.

The trusted resource owner establishes the source stream before registration and submits one `ProcessReport` containing all matches at a source position. `observe_process` rechecks active registrations and commits their status changes with a single `ProcessEvent` inbox envelope. An identical report returns its original receipt, including after consumption or closure; a conflicting report at that position is rejected. Source positions are monotonic within an incarnation. Matching belongs to the resource adapter, while acceptance, cancellation, expiry, and consumption belong to the receiving journal.

`expire_process_watches` commits expiration and timer input together. No timeout is imposed when `expires_at` is absent. The resource owner serializes source reports and expiry commands; an accepted expiry or cancellation excludes a subsequently submitted match. Cancelling a registration preserves already accepted input. Closing the instance cancels outstanding registrations and pending input through the existing lifecycle transition while retaining both in history.

Starting a new `FlowWorker` creates a new process-resource owner. Outstanding registrations for old process incarnations become `SourceLost`, or `Expired` if their recorded deadline has passed, and their notifications enter the same durable inbox. Reopening does not restart a process or generate a second loss notification. Execution pauses retain those inputs without granting permission to run. Storage-only inspection and recovery do not declare source loss; ownership startup does.

## Instance watcher tools

For persistent invocations, `watch`, `watcher.list`, and `watcher.unwatch` address process registrations owned by the invoking instance. Resource identities come from the actual Bash or Terminal task, and registration rechecks the invocation's authority at the journal owner. Each process has one observer holding its source subscription and match cursors across turns. Registration captures the initial source state before acknowledgement. Bash output changes and terminal screen revisions drive matching without polling; all matching registrations at one observed position share one inbox input. An optional `timeout_ms` becomes an absolute deadline without a default limit. A Bash output cursor that falls behind retained history produces `HistoryGap` and retires its registrations; a fresh registration can observe the same live process.

The same tools accept a persistent flow instance UUID, or `session UUID/instance UUID` across sessions. For Flow sources, `event` selects `final_answer` (default), `turn_completed`, or `instance_closed`. An optional `pattern` filters final-answer text; an optional `turn_id` selects one completion. Invalid combinations are rejected. Structured events require a persistent Flow source, while process and legacy task output require a pattern. Peer invocations use `FlowClient::watch_events` in either direction with the same source cursor and grants as native subscriptions. A final answer matching both a spawn-result route and watchers produces one input with all reasons. `watcher.list` returns active process and Flow watcher registrations in registration order, including filters, deadlines, and source identities. Internal result routes are excluded from the list and cannot be cancelled through `watcher.unwatch`.

The `watch` tool requires a flow contract with `capabilities { shell: true }`. A persistent invocation can register these independent observations:

```at
answer = watch(handle: peer)
completion = watch(handle: peer, event: "turn_completed")
closure = watch(handle: peer, event: "instance_closed")
```

`wait_for_watcher` and the next general model call consume the same durable inbox. Explicit waiting takes the context compaction lock before reservation, commits accepted notifications and their context representation together, and returns a count acknowledgement without duplicating the body in a tool result. Timeout, cancellation before pickup, execution pause, and turn finishing leave unread input pending. Once queued at the owner, context commit and projection retain lock ownership even if the waiting caller disappears. Notification messages preserve watcher provenance and do not grant user authority.

Unwatch cancels the owned Flow or process registration while retaining accepted input, and refreshes the process observer at the successful storage commit independently of the caller awaiting its reply. Instance shutdown cancels and joins observers together with process resources. Legacy invocations retain their existing watcher hub.

## Owned send attempts

`RuntimeHost::send` uses the sender's admitted lease to commit an outbox intent, routes its recorded request to the receiver, and commits the authenticated acceptance receipt back to the sender. A reply waiter, when supplied, is registered with the intent before receiver contact. Send admission and new receiver delivery have separate authorization callbacks. The caller authenticates the invoking flow before entering this host API.

The host owns the delivery task once started. Cancelling its waiting caller does not discard the intent or stop that attempt. Same-session, cross-session, reverse, and self-directed sends release each storage owner before contacting the other endpoint. Concurrent retries use the same sender request ID and receiver acceptance identity, so they do not create additional input or confirmation records.

`SendAttempt` returns the authoritative sender record and an optional pending reason. A failed attempt leaves `PendingDelivery`; this may include an accepted receiver message whose sender acknowledgement could not be committed. `retry_send` reads the original intent from the sender journal and reconciles that request. It can confirm prior receiver acceptance after interruption, revocation, or closure without treating the retry as new work. A confirmed send returns its existing record without contacting the receiver again. Accepted means received, not executed or successfully handled.

`FlowWorker::pending_sends` and `send_record` expose durable reconciliation work. Failed attempts do not busy-loop or silently discard intent. Automatic retry policy, terminal rejection/cancellation decisions, and product-facing send tools remain host integration work.

## Scoped model directories

`model_registry::ModelRegistry` owns model configuration, aliases, provider catalogs, transaction serialization, and catalog notifications. Separate registries can use the same model and provider names without sharing protocol selection, capabilities, budgets, or revisions. Request snapshots remain unchanged after later directory updates. Auth-aware projections take explicit auth data and optional cache sources; management views do not install callable models.

Prepared configuration and catalog updates retain a borrow of their originating registry and hold its transaction until commit or drop. Commit uses that owner, and dropping an update leaves the published state unchanged. Existing module-level model functions delegate to the process-default registry. Product callers using those functions still share the default directory; explicit directory isolation requires retaining and using a scoped registry.

`ProviderRegistry::with_models(Arc<ModelRegistry>)` binds connections to their directory. LLM tools retain the requested alias until dispatch creates one scope-bound `ModelCallConfig`; provider resolution rejects snapshots from a different registry. Direct calls, structured extraction, compaction, MCP sampling, suggestions, and model connection tests obtain snapshots from the connection registry. Disabled configured providers cannot resolve through either direct or prefixed connection names.

Executor entry binds its Session context to the same directory. Repeated binding to the same owner is valid; replacing it with another owner fails before executing the entry. Model-list context records and budget projections use this binding. Unbound persistent contexts do not read the default directory; unbound legacy contexts retain their existing default behavior.

`ConfigHub::models()` identifies the directory for its normalized configuration and authentication source paths. Hubs for the same source pair share ownership; different authentication files keep separate dynamic catalogs even when they share `config.toml`. Configuration reload and edits validate all live directories for that configuration source before publishing any update. Validation or write failure preserves the previous projections. The process default source uses the default registry; constructing a hub does not read its configuration until reload or lifecycle attachment.

`AtmanRuntime::build` creates provider connections with the selected hub's directory. Embedded hosts construct `ProviderRegistry::with_models(hub.models().clone())` before calling `ProviderLifecycle::new(hub, providers)` or attaching the lifecycle to an executor. These constructors return `ProviderLifecycleError` for mismatched scopes, repeated executor attachment, or configuration errors. Lifecycle setup loads configuration and registers connections; catalog refresh, removal, and notifications remain within the same authentication scope. Provider reconciliation and replaced-adapter destruction run outside the lifecycle owner lock.

`SessionDescriptor::configuration` records either `HostProvided` effects or an `Atman(ConfigSource)` binding in the session creation journal. `ConfigSource` contains normalized configuration and authentication paths, without credentials. Each flow inherits this immutable session binding when its context is restored. History replay validates the recorded shape without opening the configuration or project directory. Reopening an execution source through `ConfigHub::from_source` rejects changed filesystem aliases instead of selecting another directory.

`AtmanRuntimeOptions::config` takes an explicit `ConfigHub`; CLI and daemon entry points resolve their default before constructing the runtime. A restored host can pass `ConfigHub::from_source` to retain a selected authentication file. Scheduling, direct turn admission, executor entry, and model-context operations share the context's provider binding check. A source mismatch fails before pending input is consumed or execution ownership is claimed. Custom embedded executors use `HostProvided`; attaching an Atman lifecycle requires a matching recorded source. Attaching a correct host does not resume paused work or create a turn.

`SessionDescriptor::project` explicitly records an optional `ProjectContext`. The binding retains a normalized project root, local/global scope, and knowledge storage root. `ProjectContext::resolve` reads the selected hub and project preferences without creating directories; invalid or unreadable preferences fail instead of selecting a different store. Session and flow journals remain under the runtime data root. Changing storage preferences does not rewrite an existing session binding, and reading history does not require the original directories.

`AtmanRuntimeOptions::project` receives that binding, including explicit `None` for a projectless runtime. `Session::bind_executor` checks project identity before model binding, scheduling ownership, or input consumption. CLI and daemon memory setup use the same resolved storage root as runtime construction. This resource binding does not grant filesystem access: persistent execution uses its invocation authority and may select a permitted worktree independently. Restoring a runtime validates directory aliases without recomputing storage preferences.

`ToolCtx::for_project` creates a fresh resource context with an explicit project binding before attaching services; it does not relabel an existing context containing workspace, sandbox, or index references. An explicit projectless host cannot resolve a relative path from the process directory. Rule discovery scans only the supplied project and home sources; omitting a project keeps global rules available without loading rules from the current directory. `SandboxExec::without_project` renders project placeholders from each operation's supplied working directory, preserving configured sandbox restrictions without adding an unrelated checkout.

## MCP resource ownership

`AtmanRuntime::build` attaches an `McpService` to the executor's resource context. Cloned executors, inline calls, and spawned flows retain that owner. Separately constructed runtimes use independent connection groups, even when servers have identical names. Stdio connections use the bound project root or, for a projectless runtime, its configuration directory. Sampling uses the owner's provider registry and model directory.

The service retains configuration, tool and provider registries, and connection tasks without retaining a Session. `Session::bind_executor` installs a weakly held status projection; dropping a view does not close connections, and retaining a view does not keep the service alive. A live projection cannot be rebound to another service. After its service closes, a context can bind a replacement with the same validated project and provider scope. MCP readiness and status tools read the service directly, including when no Session view is attached.

Reload serializes generation changes with adapter and status publication. Removed adapters disappear before reload returns, cancelled initialization and refresh tasks release their clients, and stale producers cannot publish into a later generation. Explicit server waits retain the requested server identity and fail if it is removed. `McpService::shutdown` waits for its worker runtime to release resources; dropping the last owner requests the same cleanup without blocking. Connection status is a live resource projection, not durable flow execution state.
