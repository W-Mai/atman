# Durable fact journals

Flow directory activity is derived from timestamped facts and retains the source commit receipt. Live writers and read-only replay use the same reducer. Unobserved completion recovery, untimed state changes, and filesystem modification times do not advance activity; late older timestamps cannot move it backwards. This derived metadata does not replace the journal cursor or indicate a live execution owner.

`atman_runtime::event_log::journal::Journal` commits typed batches of host facts. It is separate from the asynchronous display/event writer: an accepted commit means the entire batch has been written and synchronized. A caller publishes the resulting in-memory projection and receipt only after `commit` succeeds. Streaming previews need no durable commit per chunk.

`Journal::create(path, id)` creates a new file under an existing durable parent directory. `Journal::open(path, expected_id, apply)` holds an exclusive file lock, validates the log identity and format, and replays complete batches into a private projection. The caller must discard that projection if opening fails. These operations use blocking filesystem I/O and belong on a storage worker, outside UI or executor polling.

Storage lock guards explicitly unlock before closing their file descriptors. On Unix, a subprocess can temporarily inherit the same open-file description before exec; that inherited descriptor does not extend the lifetime of the original writer or prevent another owner from reopening after handoff. The exclusive lock still spans the entire active writer lifetime. Session, profile, catalog, and temporary archival locks use the same ownership guard.


Each JSONL journal starts with a format/version/identity header. A batch contains a consecutive sequence number, the previous record digest, the exact serialized JSON payload, and its SHA-256 digest. Payloads are nonempty arrays. The hash chain checks integrity and ordering; it does not authenticate the caller or replace host authorization. A `CommitReceipt` identifies the journal and committed sequence/digest.

The writer serializes the complete batch before touching the file. A write or synchronization error prevents further commits through that handle. Reopening can discover a complete batch whose acknowledgement was lost; the host reconciles stable request IDs before retrying effects. A journal receipt alone does not implement request deduplication or prove that a business operation completed.

Recovery preserves an unterminated final record in an adjacent `.incomplete-<uuid>` file before removing it from the active journal. `RecoveredTail` reports the retained path, original offset, and byte count. Complete malformed records, broken digest chains, sequence gaps, unsupported schemas, or projection failures reject opening without skipping history. Recovery never executes flow code.

Existing published session event files retain their legacy reader and embedded writer APIs. They are not interpreted as fact journals or rewritten by this API. CLI and daemon session execution use persistent instances; opening original histories in the TUI is read-only. Embedding hosts explicitly choose a storage format and bind each journal to its Session or Flow identity. `flow test` runs isolated mock snapshot cases without creating a Session.

`atman run` and `atman flow run` create a persistent session and default flow under `runtime-v1/sessions/<session>/flows/<flow>`. Entry source, typed arguments, explicit invocation settings, user content, and image bytes are recorded before scheduling. Batch execution uses `RuntimeHost::launch_entry` and waits for peer execution and notification handoffs before shutting down; the default flow's final entry result is printed. `--ephemeral` uses the same execution and storage protocol in a temporary directory, removed after host shutdown. The session title is the selected entry name. Goals are created and continued by explicit flow policy, independently of entry return.

`logs tail` reads the default flow's typed updates with their flow identity and commit cursor. `logs stream` selects the persistent default flow unless `--instance` chooses another one. `cost` sums recorded execution usage across the session's flows, and `cost --all` includes persistent and legacy execution logs. The file-backed monitor lists both layouts. `SessionInspection::inspect_flow_updates` is the shared read-only journal reader: inspection does not install scheduling, interrupt an active turn, repair trailing bytes, or expose retained source bundles as view metadata. Published flat session histories retain their existing readers.

WatchHub reads `FlowInspection.watchers` through `SessionCatalog::inspect_flow` using the requesting view's complete Session/Flow address. The directory, search, refresh, navigation tickets, and return state share FlowHub's existing paths. Details retain the inspected journal cursor, report incomplete trailing bytes, and distinguish input commitment from completed processing. Source and recipient buttons use the same focus/window actions as other flow records. Inspection does not attach an execution owner or consume notifications; Esc only returns to the directory. Refresh is explicit, and the displayed data is a recorded snapshot.

The details view submits cancellation through a separate `CancelWatcher` control containing the recorded owner and registration ID. The authenticated workspace routes it to the owner's `FlowWorker::unwatch`, then reads the updated directory. It does not create a model invocation or borrow the viewed flow's turn. Replies retain the originating view and request ticket; leaving the page cannot redirect a reply or cancel an accepted mutation. Duplicate clicks are suppressed while waiting, and storage errors leave the recorded state visible for retry. A successful cancellation followed by a failed refresh is reported as a committed change with a read failure.

WatchHub creation keeps its recipient and draft while browsing the shared Session/Flow directory. A separate `RegisterWatcher` control carries the chosen source, filter, registration UUID, and absolute expiry. Retries retain this identity and deadline; only authored registration edits invalidate them. The workspace attaches source storage with its configured redactor without building a model runtime, then delegates to `RuntimeHost::watch_events` for authorization and durable registration. Existing registrations remain retryable after access revocation, cancellation, or source loss. A matching host acknowledgement returns the original view to its subscription directory; stale replies cannot close another draft.

## Legacy history inspection

`atman migrate inspect <session-id-or-prefix>` prints a JSON ownership report for the original `sessions/<session>/events.jsonl`. `event_log::legacy::inspect` provides the same read-only operation to Rust hosts. Each nonempty physical line retains its byte range, SHA-256 digest, original sequence and timestamp when valid, and any parsing issues. Invalid JSON, unsupported events, and unterminated final lines remain indexed. Missing metadata stays absent; ordering follows byte positions. Whitespace remains covered by the complete source digest. Reports contain metadata and ownership mappings rather than message bodies.

Explicit agent owners join runs across turns. Inline calls inherit their recorded parent's identity; spawned runs without an agent owner retain independent mapping keys. Missing parents, cycles, and conflicting identities remain unassigned. Unscoped legacy session messages retain their default-agent meaning, while diagnostics without a reliable owner remain unassigned. Mapping keys do not grant execution or create new instance addresses.

Inspection reads the initial file length and verifies the source bytes again before returning; it does not keep tailing an active writer. `LegacySource::verify` detects appends, truncations, and same-length replacements before a caller reuses a report. This is a content check, not proof that an old executor has stopped. Inspection does not migrate files, activate flows, or switch catalogs; a migration writer must establish exclusive execution ownership and revalidate its source before committing.

## Offline history migration

Run `atman migrate archive <session-id-or-prefix> --confirm-stopped` after stopping the legacy session executor. The command prints the new session ID and migration receipt as JSON. Repeating the command resumes or verifies the same destination. Use `--into <new-session-uuid>` only when intentionally importing a separate branch. The source remains readable through legacy commands; importing does not change the active session or start execution.

The destination retains the legacy title and recorded project root, with the current Atman configuration source and resolved storage scope. A missing project directory remains a valid historical binding and is not recreated. Missing metadata produces a projectless historical session; malformed metadata is an error. The command bypasses startup configuration migration and does not initialize execution services.

`RuntimeStore::archive_legacy(source, source_session, destination, old_executor_stopped)` imports legacy events into a new session identity. The host authenticates the operator and obtains explicit confirmation that the old executor has stopped. This confirmation does not lock an old binary or prevent it from writing later. Source files remain unchanged. `flow_store::migration::destination_id` provides a stable target for retries; a changed source conflicts with the saved plan instead of silently creating another copy. An operator can explicitly choose another destination for a separate source branch.

The migration retains an exact source copy in the destination session's `artifacts/legacy-events.jsonl`, including whitespace and malformed data. Each owner receives a separate historical flow; uncertain records belong to one unassigned flow. Original lineage stays in the retained events and grants no authority. An explicit default historical flow exists even when the source contains no default-agent records. Historical flows remain closed and cannot start execution or deliver notifications.

Migration work stays under `runtime-v1/.migrations/<destination>/work` until every flow is complete and verified against the source map. Retries resume after committed record batches. Source changes, invalid retained data, and occupied destinations stop publication without overwriting history. A `LegacyImported` session fact records source identity, owner mappings, record counts, and final flow cursors. The source is verified again before the complete directory is atomically published into `runtime-v1/sessions`. Journal handles are closed before the rename. Reading the imported history no longer requires the original source or project directory.

## External transcript import

`atman migrate import <source-session> --from opencode|kiro-cli --storage <source-directory> --into new` publishes the source adapter’s text transcript as a new read-only Session and History Flow under `runtime-v1/sessions`. Each invocation requests a separate destination. Open its printed Session ID with `atman --continue <id>` through the same history view used by native archives. `--out <path>` writes a normalized JSONL transcript instead of creating a Session.

Import converts loaded messages into a private immutable event snapshot and uses the archive transaction to retain and atomically publish it. User messages start new historical turn groups; subsequent assistant, tool, and system records preserve their order and roles. Message text remains unchanged. Separate `imported_from` fields retain the source kind, external Session ID, agent, model, and source timestamp. Known timestamps retain their original value; missing timestamps remain absent. These are retained historical records, not live input, tool execution, or final-answer notifications.

The published archive includes the complete normalized snapshot and does not require the external storage or temporary file for reading. The adapters currently import text and message metadata; they do not preserve unparsed non-text parts or claim a byte-for-byte copy of external source storage. Conversion failures do not publish a partial Session. Import does not load execution configuration, create project authority, or migrate unrelated user configuration. Stopped-source confirmation and asset retention for original Atman archives remain part of the separate `migrate archive` command.

Flow focus changes retain the destination view in the workspace until its committed state and live preview have refreshed successfully. A failed refresh leaves the current view selected and preserves the destination's draft, reading position, and original reply mailbox for retry. Main and floating views use the same ownership path.

Durable subscription failures stop automatic reads for the affected view and display a disconnected status above its last committed content. The reader, draft, attachment identity, and control mailbox remain available; other views continue updating. Selecting the view again from FlowHub explicitly refreshes the retained reader, including when it is already focused. Successful refresh restores normal updates without creating a new flow or rerunning work. A live-preview failure disables only that preview source and does not disable committed updates.

Compact workflow cards and full graphs share each view's node disclosure state. Clicking a node reveals its arguments and recorded output and stops automatic tail following. Explicitly expanded details can enlarge the compact card; automatic summaries retain their height limit, and each detail section retains its preview limit. Reading details does not consume inbox messages or change execution.

Focused and background views share permission-stream handling. A lagged subscription rereads the broker snapshot; closing one subscription disables that event source without exiting the workspace, cancelling execution, or continuously scheduling redraws. Durable view updates and control replies retain their independent channels.

Terminal panel resizing resolves the terminal registry from the requesting view's `FlowWorker`. The same `term.resize` operation serializes PTY and parser changes with other terminal actions. Resize work retains the original view reply ticket and runs independently of the UI control loop; it does not start a turn, borrow another flow's terminal registry, or wait for child output before returning.

## Session and flow storage

### Project discovery and deletion

`ProjectCatalogStore::reconcile_sessions` discovers projects from both flat legacy metadata and persistent session journals, including projects whose source directories no longer exist. Pin and archive settings remain unchanged. Persistent session discovery reads recorded bindings without opening execution owners or repairing logs; filesystem activity times are display hints, not execution facts.

`ProjectCatalogStore::load` is read-only. A missing catalog returns an empty directory; read and parse failures remain errors instead of appearing as an empty project list. Reading does not create the catalog or its lock file.

An archived project can be deleted only when its persistent sessions have no attached writer and every executable flow is explicitly closed. Idle, paused, and interrupted flows still retain their resources and history. The selected management session must be replaced before its project can be deleted. Incomplete or corrupt journals reject deletion without repair. Hosts must close flows through their resource owner and detach sessions before requesting deletion; project deletion does not perform lifecycle transitions itself.

Session creation, opening, migration publication, management selection, and project deletion share the runtime catalog lock. Deletion validates all matching sessions before removing any project data and retains that lock through shared-data cleanup and catalog persistence. Project deletion uses the same per-Session deletion receipts and delivery tombstones as individual removal. Validated directories move to `runtime-v1/.deletions/sessions/<session-uuid>/data` before cleanup; retired identities stay unavailable. Retrying project deletion finishes staged removals belonging to that project. Cleanup across multiple sessions, legacy history, and shared project files is not atomic; failures retain project registration and report an error. The persistent owner checks do not lock executors from older versions using flat legacy storage.

List and clear operations remain local to the view, and file imports copy into the selected flow's attachment store without accepting input or starting execution. Draft lists are transient; accepted messages retain their captured image references across restart.

Each command uses a separate next-turn invocation in the existing instance. It cannot enter an active model call or change the instance's default entry, identity, permissions, or pause state. Ordinary input and watcher notifications use the default entry. Goal resume and continuation retain the last admitted invocation's source and argument mapping. The committed invocation references its accepted command identity; mismatched references and mixed command batches are rejected during live execution and replay. Read-only updates expose command names and user content without source bundles.

Restoring a Session uses its recorded configuration directory independently of the client's default directory. TUI attachments provide FlowHub relationship graphs, pending-input editing, Session creation and reviewed deletion, and process-terminal controls through the bound host. Main and floating views use the same control dispatch and receive replies through their original view bindings. Read-only history attachments retain navigation and deletion review without acquiring execution services. Plain-terminal attachment supports selecting other instances within its Session with `:focus`; its commands are listed below.

### Plain-terminal attachment

`ATMAN_NO_TUI=1 atman --continue <session-id-or-prefix>` attaches an existing persistent Session to `RuntimeHost`. Open executable entries bind their retained source and current trust configuration to the common scheduler. Binding preserves execution pauses and interruption gates; an unavailable entry is reported independently. The terminal reads committed `FlowUpdate` batches for replies and completion failures, retaining a separate cursor for each selected flow.

Container facts record session creation, instance registration, and default-view selection. Flow facts record the immutable creation request, source bundle, provenance, and lifecycle transitions. `created_by` is audit metadata, not control authority. The default flow is a view binding and has no privileged lifecycle.

`SessionHandle::select_default` and `SessionStore::select_default` require the observed catalog receipt and a registered instance ID. A stale selection cannot replace a different current default; selecting the current default is a no-op. The catalog owner serializes selection with creation and other metadata edits. Selection does not start execution, move focus in connected views, or change permissions.

Session and flow creation initialize journals in private directories before publishing their final paths. A shared catalog lock serializes session creation with migration publication. Incomplete initialization directories remain outside the registered inventory. A complete but unregistered flow can be reconciled by retrying the same creation request and descriptor; it cannot be opened through the session catalog. Reusing a request with different creation data fails.

Flow transitions validate an expected state revision, apply to a private candidate, and publish that candidate only after the journal commit succeeds. Completing an invocation preserves the instance. Reopening an active invocation records `HostLost` without executing its entry; existing pause keys remain. Closing invocations retain cleanup obligations, and interrupted instances require explicit recovery before another turn can start.

`session.json` and `flow.json` are replaceable projections with a committed source cursor. They are rebuilt from journals on opening, even when missing or malformed. `take_projection_error` reports cache-write failures without withdrawing an already committed fact. Source bodies remain in the creation fact; reading history does not require a reachable project checkout.

Creating or opening storage does not start schedulers or grant permissions. Hosts authorize commands, validate entry programs, and decide when restored instances may execute. Legacy migration requires an explicit `archive_legacy` call.

### Read-only historical flows

`FlowDescriptor.content` distinguishes `FlowContent::Entry(EntrySnapshot)` from `FlowContent::History(LegacyArchive)`. Historical flows have no executable entry. Their instance state is closed from creation, without fabricating a completion or cancellation for any old invocation. Catalog discovery, default-view selection, committed pagination, and subscriptions use the same interfaces as executable flows. Entry preparation explicitly rejects historical flows.

`LegacyArchive` records the original session, file identity, ownership group, and expected record count. `FlowStore::append_legacy_history` commits ordered `LegacyHistoryRecord` batches containing exact original bytes in base64 alongside their source metadata. It validates ownership, byte ranges, per-record digests, ordering, and count before writing. Duplicate, altered, and excess records are rejected without advancing the cursor. Reopening rebuilds only the import position; history pages read record bodies from the journal and remain available without the original file or project directory.

Migration retains managed images referenced by message and checkpoint records in the same history batch, keyed by their content ID. Original event bytes remain unchanged; archive projection resolves retained images to inline content without reading the old session directory. Import accepts only regular files in that session's attachment store and verifies the image size, media type, and content digest before publishing the archive. Missing, corrupt, symbolic-link, or external artifact references reject migration. Historical path and URL references remain references; migration does not fetch arbitrary files or network resources. Inline images already belong to their original records.

Registered tool outputs referenced by truncation notices and pagination envelopes are retained alongside their original message records. Import verifies regular source files and their recorded byte counts and pagination metadata; missing or inconsistent contents prevent publication. Conflicting contents for the same output ID are rejected across all imported flows. `ArchiveTranscript.outputs` provides an immutable `OutputStore` for reading, paging, and searching retained results after the old directory is removed. Original tool-result messages retain their excerpts and references; importing full contents does not fabricate a new tool result.

Main and floating archive views use this retained store through their shared history projector. Tool details resolve full contents before selecting the existing typed renderer; unrecognized tools use the text detail renderer. Each view keeps its own collapsed or expanded state, independently of the retained messages.

The journal's content boundary rejects execution facts in historical flows and legacy batches in executable flows. `FlowUpdate::Created` exposes the typed content summary; `FlowUpdate::LegacyRecords` preserves complete imported batches through the existing view feed. These records are history, not newly accepted messages or final-answer notifications. Importing records does not replay tools, create watchers, or wake agents.

`SessionInspection::archived_view` reads a complete archive into a `FlowView` without acquiring a writer or loading execution configuration. It returns `None` for executable flows after fact validation, without constructing a transcript. Archive selection and projection use one journal scan. It uses the same fact validation as `inspect_flow_updates` and `inspect_flow`, rejects incomplete imports and journal tails without repairing them, and remains usable while another holder owns the journals. Its closed state and transcript share one committed cursor. Malformed original source records remain available with their source positions and exact retained bytes.

`FlowTranscript::archived_transcript` adapts the already partitioned archive to the existing historical message and workflow renderer. A spawned run belonging to this archive is displayed as its own conversation; original lineage remains in the retained source record. Missing timestamps remain absent. Unsupported source records are reported separately rather than silently discarded. Native live instances continue through their incremental projection.

`projection::flow::LegacyHistory::inspect` opens an original flat log as a read-only directory. `flows` exposes the same ownership partitions used by migration, including the default partition of an empty session. `read_flow` returns an immutable `LegacyFlowView` identified by its original session, ownership key, and complete source digest. It validates the selected byte ranges and checks the whole source before and after reading; a changed or removed source requires a fresh inspection. Existing snapshots remain readable. Direct and imported history share the same `ArchiveTranscript` projection, preserving unsupported records and absent timestamps. These reads create no files, execution owners, instance addresses, or journal cursors.

## Persistent session management over RPC

The daemon exposes persistent catalogs through the authenticated `/rpc` endpoint and Unix socket. Both transports represent the local daemon operator; arbitrary external principal names cannot acquire a catalog. Catalog ownership stays with the daemon after an RPC connection closes. `run_flow`, `goal.run`, and explicit instance methods use the same `runtime-v1` storage and `RuntimeHost` scheduler. For attached persistent sessions, Goal reads, approvals, and event subscriptions resolve an omitted instance address to the session's default flow.

`run_flow` returns `session_id`, `instance_id`, and the initial `run_id`. Its retained entry includes the source dependency bundle, explicit configuration and project binding, typed arguments, invocation settings, and user attachments. `goal.run` additionally commits the requested initial objective before execution. A completed invocation leaves the instance idle and addressable; subsequent inputs and entry-authored Goal continuations use the same inbox and execution lease. The daemon owns accepted startup work across RPC disconnects and runs startup hooks only for the initial invocation. Host shutdown preserves instances, Goals, pending input, and managed workspace references without treating shutdown as session completion.

`list_sessions` includes both layouts. Persistent rows carry a `persistent` object containing `default_flow`, `flow_count`, `loaded_flows`, `catalog_sequence`, `trailing_bytes`, and `unavailable`; legacy rows omit this object. IDs shared by both layouts remain separate rows. Search, project filtering, and limits apply to the combined list. A missing project directory does not hide its sessions. Unknown event counts are `null` rather than zero. `rename_session` targets existing legacy directories only; a persistent catalog UUID cannot create a legacy directory through this endpoint.

`SessionHandle::observe` reads the catalog and acknowledged statuses of already loaded instances without opening inactive journals or installing execution. A persistent session is `running` when any observed peer has an active turn, `idle` when every instance is loaded and none is active, and `finished` only when all its instances are closed. Idle may include paused or interrupted instances; inspect `flow.get` for their individual states. Catalogs with unobserved instances are `detached` unless an observed peer is running. Fully offline catalogs are also `detached`, with `loaded_flows: null`. Corrupt catalogs remain visible as `unavailable` rows. Instances are observed independently, not in a shared cross-flow transaction; reading the list does not recover interrupted execution or repair incomplete journals.

When the trusted profile owner is attached, relation inspection for the management Session also includes its explicit profile grants. A profile that is unavailable or still validating contributes no relations; ordinary Session inspection remains readable without profile ownership.

CLI `session list` and `session show` also inspect persistent catalogs directly, including while their executor holds the writer lease. `RuntimeStore::session_ids` discovers published directories, and `inspect_session` rebuilds the catalog through the same journal validation and projection reducer used by recovery. Neither operation creates storage, repairs incomplete tails, rewrites caches, opens flows, or restores execution. Inspection reads a fixed-length file prefix and reports trailing bytes separately. Complete corruption is an error; a damaged catalog in a listing is reported without hiding healthy sessions. These are recorded catalog views, not acknowledgements of an active writer's latest commit or live execution status.

Persistent listings include titles, flow counts, and recorded project paths; `show` includes the default flow and registered flow IDs. Missing project directories remain queryable with `--project`. Published flat session history remains visible, and identical IDs in both layouts are shown separately. Read-only CLI catalog commands bypass configuration migration, notifier setup, and execution services.

Create or open a catalog before addressing its flows. Creating the same session identity and descriptor is idempotent; conflicting creation data is rejected. An omitted project explicitly creates a projectless session. Reopening reads its recorded configuration and project binding without requiring either location to exist. Failed instance reads remain visible as unavailable rows in the membership page, preserving pagination and the total count.

View selection changes only the default binding. Opening, listing, selecting, and reading do not install execution schedulers. Pause and resume use a stable operator pause key, so resuming does not clear another controller's pause. Controls check the execution revision inside the instance writer; stale requests fail. Cancelling a turn preserves the instance, and resuming does not recover an interrupted invocation or resume its Goal. The execution readiness field describes the lifecycle gate, not whether a scheduler is installed or a model is running.

For an explicit operator override, read `flow.get.execution.pause_keys` and submit `release_pause` with one selected `pause_key` and the current execution revision. This releases that key alone, including a management flow's self-pause, without replacing the active invocation. Other pauses and the Goal remain unchanged. The action requires a trusted User or Host sender; peer controls cannot invoke it even with Control permission. Unknown keys and stale revisions fail without writing. Retrying an accepted release returns its original receipt and cannot remove a subsequently reacquired pause. Ordinary `resume` still releases only the operator's own key.

`FlowStore::control` accepts a `ControlRequest` containing an authenticated sender, request UUID, target, expected execution revision, controller pause key, and typed action. The host must authenticate and authorize each submission, including retries, before calling storage. A single journal fact retains the request and its state change; read-only inspection, writer recovery, and view updates use the same fact. Identical sender/request pairs return the original `CommittedControl`, while conflicting contents and stale new requests fail without writing. Requests that leave execution unchanged still receive a durable receipt without invalidating reserved input. A retry of an earlier cancel cannot cancel a later turn.

`CommittedControl.execution` describes the state when the request was accepted. Close records `Closing`; resource cleanup and the transition to `Closed` remain separate lifecycle operations. Returning an earlier close receipt does not imply cleanup has completed. Recorded control timestamps contribute to activity; retries do not write another timestamp or change current execution.

`FlowWorker::control` owns authenticated control submission and close cleanup. Peer tools, terminal controls, and daemon RPC use this same path. The RPC requires `request_id`; `flow.kill` and `flow.close` accept an optional request UUID and return the generated identity when omitted. Retrying requires the original target, action, expected revision, and request identity. Reusing an identity with a newly read revision is a conflicting request. Current authorization is checked before returning a recorded receipt.

`flow.control_batch` records all commands before delivery and returns without waiting for execution to stop. Each command includes its target, control request UUID, expected revision, and action. A target appears once per batch. The authenticated operator determines sender identity; request parameters cannot supply it. Ordinary actions use the same operator pause key as individual controls. Only `release_pause` accepts an explicitly selected `pause_key`. Invalid batch structure is rejected before opening storage; missing targets and execution conflicts become per-target failures without rolling back other commands.

The model tools `flow.control_batch(request_id, commands)` and `flow.control_status(request_id)` use the same host service for persistent instances. Tool commands contain `handle`, `expected_revision` from `flow.status`, and `action` (`pause`, `resume`, `cancel_turn`, `recover`, or `close`). Handles accept a local instance UUID or `session-uuid/instance-uuid`. The host binds the invoking Flow as sender, derives its own pause key per target, and uses the batch UUID as each target's control request identity. Model arguments cannot supply another sender or pause key, and cannot invoke the operator-only `release_pause` action. Both tools require named arguments.

Tool status reads are scoped to the calling Flow and remain available from its later admitted turns, including after restart. They require current Control grants for every target, reject expired invocation leases, and do not open target Sessions, start model calls, or repeat effects. An unknown batch reports an error without revealing another actor's record. Preserve the original commands and request UUID for identical retries; changing revisions under an accepted identity conflicts with the recorded request. A caller that pauses itself must be explicitly resumed before querying, while the host continues delivering its already accepted batch.

Both batch RPCs return the persisted `{ id, sender, submitted, items }` record. Each item contains its immutable `request` and `history` of progress with host receipts. An empty history is pending delivery. Progress is `accepted` with the target receipt, then `applied` with completion evidence, or `failed` with a reason. `flow.control_status` is scoped to the authenticated operator and rejects unknown batch IDs. Identical submissions return the same submitted receipt and current progress; changing the commands under that identity is rejected. A new batch may reuse an original command identity to reconcile its receipt without applying it again. Completed batch reads and retries do not reopen target owners or change their current state.

`ProfileStore::submit_controls` records a complete `ControlBatchRequest` in the existing host journal before delivery. A batch has one authenticated actor, a stable UUID, and one immutable control request per target. This storage API does not start delivery or create a management conversation. `pending_controls` returns unfinished batches in acceptance order for host reconciliation. A matching submission returns its original submission receipt and current per-target progress; changing the target snapshot under the same actor and UUID fails.

`ProfileStore::control_batches` and `ProfileHandle::control_batches` read an authorized actor's history in descending submission order. Pages contain batch identities, submission receipts, and the latest per-target outcome counts without copying command histories. The optional `before` cursor names an existing batch for that actor; unknown or other-actor cursors fail. Page sizes range from 1 to 200. New submissions and outcome updates do not reorder older submissions. Reading history does not start delivery, load target Sessions, or mutate the journal.

Each batch item starts in `PendingDelivery`, represented by an empty progress history. `advance_control` records trusted `Accepted` and `Applied` evidence from the target journal, or a `Failed` diagnostic. Application requires prior acceptance and a matching or later target receipt; close acceptance alone does not confirm cleanup. Failure retains any earlier acceptance and does not roll back other targets. Repeating an earlier progress report returns its original host receipt without changing current progress. Both host receipts and target receipts survive recovery; neither receipt is an authorization credential.

`ProfileHandle` serializes batch submission, inspection, and progress through the same profile owner. Submission authenticates the caller at the owner boundary, including retries. Accepted owner work continues if its waiting caller disconnects. Control progress publishes its committed cursor without clearing a diagnostic about an invalid management binding or enabling that binding's grants. Profile write failures disable management authority until recovery. These owner APIs retain work and report evidence; target dispatch belongs to `RuntimeHost`.

`RuntimeHost::start_control_service` reconciles unfinished batches from profile storage. CLI and daemon profile initialization starts this service; embedded hosts may start it explicitly. `RuntimeHost::submit_controls` starts it before admission. `FlowClient::control_batch` binds the invoking actor and controller keys, authenticates the invocation and target permissions at admission, and returns the durable batch receipt. Independent target tasks continue after the invoking flow pauses or closes. New target effects check current grants inside the target writer. Host reconciliation reads an already recorded matching control without applying it again, including after an acknowledgement was lost.

The service opens existing Session and Flow owners as needed, without installing execution schedulers or invoking models. Closing waits for the lifecycle coordinator's cleanup; cancellation waits for the original turn's completion fact. Missing targets, revoked permissions, and revision conflicts become individual failures. Uncertain I/O retains pending work and publishes diagnostics through `subscribe_controls`; profile and directory changes trigger another attempt without periodic polling. `wait_quiescent` accounts for this service and its observed profile cursor. Host shutdown stops and joins reconciliation before releasing execution and storage owners. Completed batches neither reopen their targets nor repeat their effects during recovery.

Application depends on the control action. Pause is applied when its execution gate is committed: the driver stops polling at suspension boundaries while retaining the active turn and executor future. A turn already finishing may finish normally. Resume releases that controller's gate; it does not create another turn. Cancellation waits for the original turn to end, and closure waits for resource cleanup. Batch progress is historical evidence of the operation; read the current flow snapshot for its present execution state.

`ControlServiceProgress.issues` reports transient profile, worker, or target diagnostics separately from durable outcomes. Target issues carry the authenticated sender, batch UUID, complete Flow address, and message so views can associate a pending delivery with its cause without parsing text. Successful reconciliation removes its transient issue; it does not rewrite the batch's earlier receipts. Diagnostic ordering is stable between unchanged observations.

In FlowHub's Flow and Overview directories, **Controls / Ctrl+T** opens a review with the selected Flow. **Targets** opens the shared directory: Enter or a row click toggles an instance, Ctrl+B opens the global Overview, and Ctrl+T or Esc returns to review. Selection persists across pages and Sessions and captures each target's complete address and execution revision. Tab selects a control; Enter or the left/right arrows change its action. **Submit / Ctrl+S** submits the reviewed batch. Pause, Resume, Cancel turn, Recover, and Close accept multiple targets; Release pause selects one recorded pause key on a single Flow. Closing the review does not stop accepted host work.

Control results are explicit snapshots. **Refresh / Ctrl+R** reads the original profile record and current delivery diagnostics; Enter or a row click opens the full receipt or failure reason. Pending delivery, Accepted, Applied, and Failed remain distinct. Main and floating views use the same tracked request path, and late replies cannot replace a closed review. A submission failure retains the draft and request identity for an identical retry. Changing the action, selected pause key, or targets creates a new request; revision conflicts remain visible rather than silently adopting a newer target state.

**History / Ctrl+R** in the control review opens the operator's submitted batches, including after restart. A result page also links to this directory. History uses the same search, paging, and refresh controls as other FlowHub directories; returning from it preserves an unsubmitted review. Select a batch to inspect its original results. **Retry pending delivery** appears only for unfinished batches and resubmits their original stored commands, including each command's identity and revision. It does not retry terminal failures as new operations or undo successful targets. Refresh only reads the stored progress.

`RuntimeHost::open_session` and `create_session` share owner acquisition across control recovery, daemon requests, terminal navigation, and watcher setup. Concurrent callers reuse one catalog writer; creation retries still validate the immutable descriptor. Once storage opening starts, attachment and lock release continue if the caller disconnects. Shutdown waits for that operation to release its writer. `HostServices::session_redactor` resolves the Session's diagnostic policy before attachment; the terminal host derives it from the recorded configuration, including when background control opens the Session before its view.

`close` acknowledges the committed close request. The instance rejects new input and cancels pending input, then remains Closing while the admitted turn and owned processes stop. The host releases its workspace reference and records Closed only after cleanup; shared workspaces remain available to other owners. A disconnected requester or a flow closing itself does not interrupt this cleanup. Reopening a Closing instance continues cleanup without executing its entry. Cleanup errors retain Closing and appear in `flow.get.close_error`; another close request with the current revision retries cleanup. This diagnostic belongs to the current host and is recalculated during recovery. Batch draining waits for closure and its notification handoffs, and returns cleanup errors rather than exiting early or waiting indefinitely. Closed instances retain readable history, output and delivery receipts. Closing one instance does not close its peers or complete their Goals.

`flow.launch` validates and snapshots the named source entry before creating an instance. The daemon retains scheduling independently of the requesting connection and builds execution services from the session's recorded configuration and project binding. Source changes or deletion do not change later invocations. Matching launch retries return the original acceptance with its current consumption disposition, without rereading source files, repeating execution, releasing pauses, or reinstalling scheduling. Conflicting reuse is rejected. `flow.invoke` queues a typed invocation on that same instance; duplicate requests share acceptance and paused input remains pending. Acceptance certifies durable receipt, not successful execution. Invocation settings are explicitly read by the flow and are not added to conversation history.

Both invocation methods accept `user: { text, images?: [{ data_base64, name? }] }` for the authenticated operator's original input. Text and validated image bytes are committed with the invocation and restored as the same user message; entry arguments remain separate. Invalid images reject the request before instance creation or input acceptance. Omitting `user` retains an internal invocation message. Peer invocations cannot claim user provenance. Changing content under an accepted request ID is rejected.

`flow.output` reads the same final-answer publications exposed to peer flows. Ordinary entry returns are available as typed completion records through `flow.get` and do not become final answers implicitly. Prompt requests use the existing daemon prompt transport with invocation-owned context. `DaemonPromptResolver::new(&state)` retains a weak state reference, preventing cached execution services from keeping their daemon alive.

`GET /events?session_id=<session>&instance_id=<flow>` streams the same committed batches as `flow.events`. Each `flow_update` SSE event contains `{ receipt, facts }`, with its complete `journal UUID:sequence:digest` cursor in the event ID. Apply the whole batch before advancing the local cursor. The optional `after` query selects the initial position; `Last-Event-ID` takes precedence during automatic reconnection so an unchanged EventSource URL does not replay its initial range. Without either cursor, the stream begins at creation. The initial read validates the cursor before successful response headers; malformed, altered, foreign, or ahead-of-history cursors are rejected instead of silently restarting. Legacy `since_seq` is not accepted with `instance_id`.

`projection::flow::FlowTranscript` consumes these complete batches for one `FlowRef`. Transcript entries retain their commit, fact, and item positions independently of viewport layout. Applying an existing receipt is idempotent; a conflicting receipt, missing batch, foreign journal, or foreign transcript owner is rejected before exposing new entries. Each document retains original input, publication, execution, checkpoint, completion, and legacy records. `shared_messages()` excludes isolated invocation publications and checkpoint replacement text; message origins remain unchanged. Accepted input and inherited model context do not become new transcript messages. The persistent terminal attachment uses this projection for history, focus changes, and live updates.

`FlowTranscript::turns()` exposes execution graphs in invocation order, keyed by the original turn lease. Recorded execution timestamps and scoped tool results are preserved; messages without timestamps do not acquire artificial durations. An external creator does not hide the instance's own entry. Completion closes unfinished nodes at the recorded invocation boundary, while late diagnostics stay in their original turn and cannot restart its running state. Permission updates retain request ownership across turns, including updates received after completion. Original records remain available alongside these derived graphs.

`atman_tui::flow_view::FlowViewModel` binds a document to one `FlowTranscript` and synchronizes complete committed boundaries. Native records append to the document; tool results and workflow updates change their existing items while retaining local disclosure state. Tool results are scoped by turn epoch, producing run, and call ID. Final-answer work markers stay within their owning turn. Native items retain their source record identity, and unchanged cursors do not invalidate layout. Foreign bindings, replaced histories, and external document replacement require a new view model. Complete archives use the historical renderer through the same model, with independent work-fold disclosure in main and floating views; they cannot acquire further records after binding.

`FlowViewModel::sync_legacy` accepts original-log `LegacyFlowView` snapshots through the same historical rendering and work-fold restoration as imported archives. A model binds to either a persistent instance or an original source, including empty histories. Repeated snapshots preserve disclosure and layout; a different source digest, ownership key, or external document replacement requires a new model. Original-log views expose read-only presentation without an execution snapshot, persistent flow address, or journal cursor.

`control::ViewAddress` distinguishes persistent instance addresses from original session and ownership keys. View lookup, focus, floating windows, commands, and replies retain this typed address; equal session UUIDs from different storage layouts remain separate destinations. `FlowViewSource` supplies live, imported, and original snapshots to the shared view model and interaction loop. Project Hub includes both layouts in persistent workspaces, and original Session rows open a paged ownership directory without leaving the workspace. `SessionStats::inspect` reads counts without creating locks or updating legacy caches. Selecting or closing a historical view does not start execution or alter its source; reopening creates a fresh snapshot.

The TUI Sessions directory merges native catalog addresses and canonical legacy session directories at the operator presentation boundary. ## Instance activation

Launch records without `inherited_outputs` deserialize with an empty source list. Reading and retrying these records preserve the original journal bytes and acceptance receipts. New activations still validate referenced outputs before committing; omitted metadata does not authorize missing output imports.

`SessionHandle::set_project` and `SessionStore::set_project` change the container's current project association under the expected catalog receipt. `SessionProjection.project` supplies discovery and future registrations; `SessionDescriptor.project` remains the original creation value. Existing flow registrations, source namespaces, worktree references, execution state, and journals remain unchanged. The operation changes metadata without moving files or starting execution. Instance hosts must bind execution services to `FlowWorker::project()`, not to the container's current association.

Project reassignment shares the runtime catalog lock with project deletion. Deleting project data is rejected when another container still retains flows bound to it, including closed histories. CLI `session list`, its `--project` filter, and `session show` read the current project association from the Session projection. A removed association is displayed as no project, including when the creation descriptor originally recorded one. These reads retain missing directories and do not load instance execution.

`atman session move <id-or-prefix> <directory>` changes a persistent Session's project association using its recorded configuration and catalog writer. Existing flows retain their project bindings and execution records; new registrations capture the destination. An attached host owns the writer, so use its Move Session action while that host is running. CLI moves require an existing directory. Legacy sessions retain their metadata-based move operation. If identifiers overlap across storage sources, select `--source persistent` or `--source legacy`; ambiguous requests change neither record. Corrupt legacy metadata is reported without replacement.

Retrying an initial Session entry that remains Prepared reuses its recorded source bundle and project binding, including when source files were removed or the Session changed projects. Execution services follow that entry rather than the view's selected project. Before an entry is registered, creation uses current Session membership. Both interactive creation and `RuntimeHost::launch_flow_at` check the observed catalog before a new registration. Startup command input that has not been committed is prepared from the recorded configuration at activation; an accepted activation is returned unchanged without queuing startup again or resuming execution.

Daemon execution services are cached by Session identity and the complete project binding, including its storage scope and storage directory. `flow.launch` uses current membership for new instances and the captured binding for an existing Prepared instance. `flow.bind` restores the instance's recorded project, even after reassignment or a storage configuration change. Source namespace resolution, authority, and tool resources use that same binding; old execution services remain available until host shutdown.

Interactive CLI hosts retain the same complete project binding per flow. Main views, floating views, terminal focus, and restored peers share project-scoped execution services within a Session while keeping their own prompt transports. Command resolution, relative attachments, settings, and knowledge panels use the selected instance's binding. Changing the default flow affects later navigation without retargeting existing views. Read-only archives display the current Session title and the archived instance's captured project without creating execution services.

`SessionHandle::configure_executor` installs a host-owned `ExecutorResolver` once. `executor_for` requests an explicit project binding and validates the returned configuration and project without loading a flow or starting execution. CLI and daemon resolvers use their existing execution caches; daemon callbacks hold a weak service-owner reference. Resolving after owner shutdown fails. Embedded hosts can supply their own resolver; a cross-project spawn without one fails before registration.

Persistent peer creation checks the observed catalog receipt before resolving services and again when registering the instance. Same-project children retain inherited services and managed workspace sharing. After reassignment, new children resolve sources and services from current membership, allocate requested workspaces in that project, and retain inherited capability ceilings. The workspace root comes from the operator-selected project binding. Existing instances retain their recorded source bundles, working directories, and resources. Clearing membership creates projectless children using the recorded user configuration.

Persistent `flow.list`, `flow.search`, and `flow.describe` inspect the creation catalog, so discovered versions match a subsequent named spawn after reassignment. Reading this catalog does not initialize target execution services. Validation of files in the existing flow's workspace through `flow.check` continues to use that flow's execution source roots. Explicitly bound service contexts do not fall back to the process working directory or global user configuration.

The persistent TUI exposes project association through Move Session, `:move-session`, and Flow details. The editor accepts an absolute existing directory or a blank value to remove the association. Saving resolves storage scope from the destination project and the Session's recorded configuration, then checks the reviewed catalog receipt. Save and Ctrl+S share this operation; successful acknowledgement returns to the Session's flow directory, while failure retains the draft. Editing membership does not load or schedule existing flows, and view changes cannot redirect a pending save.

`RuntimeHost::launch_flow` owns creation, result registration, and initial activation across the participating storage owners. The caller supplies a stable creation descriptor and `LaunchInput`, authenticates its sender and inherited context, and supplies authorization for new effects. The host creates or resolves the canonical Prepared instance, obtains a source cursor, commits the requested continuing result subscription at its recipient, and only then activates the source. Current watch grants are checked at registration and activation. The recipient confirmation is an opaque owner-issued proof, not model-provided JSON. No owner lock is held while awaiting another owner.

Inherited tool-result messages can reference registered full outputs through `output_id`. Callers capture their sources with `OutputStore::capture_references(&inherited_context)` and supply them as `LaunchInput.inherited_outputs`; persistent `flow.spawn(inherit_context: true)` performs this capture automatically. Each source binds the original ID, owning directory, byte count, and content digest. After authorization, activation verifies the references and durably copies their full contents into the destination Flow's `tool_outputs` directory before committing. Missing sources, changed contents, and conflicting destination files reject activation without overwriting data. Plain text and arbitrary JSON strings do not request output imports. Identical launch retries and journal replay preserve the original metadata without reopening source files, so the child can read inherited outputs after the source is removed. The journal stores references rather than additional full output bodies; output tools continue to resolve within the receiving Flow's own store.

`FlowStore::activate_entry` commits the entry configuration, optional initial invocation, inherited context, and result-subscription evidence in one source batch. `LaunchInput.request` is an `EntryRequest` with creation identity, default arguments, invocation settings, and an explicit `EntryStart`. `Invoke` accepts one initial input; `Waiting` opens the instance without pending input, a synthetic user message, or an initial turn. Waiting entries require a retained execution binding and cannot promise a synchronous initial result. `LaunchRecord.receipt` identifies activation independently of `acceptance`, which is absent when no input was accepted. Identical retries retain both meanings after later turns, pauses, and restarts.

`LaunchInput.initial_goal` optionally adds the exact Goal creation fact to that same commit; the scheduler and context projection see the objective before admitting the first turn. Empty objectives fail before activation, and replay rejects a missing or mismatched initial Goal fact. Before this commit the flow stays Prepared and cannot accept arbitrary input or execute. After it, initial input, when present, enters the common inbox for normal admission. A waiting entry remains idle until applicable input arrives. Activation does not itself grant execution authority or install a controller. An incomplete activation restores no Open instance, initial input, or initial Goal; a complete activation restores them together. RPC `flow.launch` exposes this choice as `start: "waiting"` or `"invoke"`; waiting with `user` content is rejected rather than discarding that content.

The entry request ID equals the immutable creation request ID. Identical retries recover the original activation receipt and any initial input acceptance with its current consumption disposition, including after restart, pause, or close. Changed launch data is rejected. A failure before activation preserves Prepared state and any already registered result subscription; retrying retains that subscription's original cursor. Concurrent attempts reconcile the authoritative source activation instead of repeating effects. Dropping the awaiting caller does not cancel an owned launch attempt.

`RuntimeHost::launch_entry` combines this protocol with retained entry scheduling for trusted host callers. `EntryExecution` supplies the executor, current authority ceiling, trust, cooperative yield interval, and expected catalog cursor. Entry preparation completes before catalog mutation. Direct host launches and `flow.spawn` use this same path; successful activation transfers the controller to the session catalog. Returning or dropping the launch result does not stop subsequent turns. A matching retry returns the original receipt with its current consumption disposition, without releasing pause keys or reinstalling a stopped controller; restoring scheduling remains an explicit `SessionHandle::bind_entry` operation.

Concurrent activation attempts for the same instance serialize scheduler adoption and reconcile the committed launch input; different instances retain independent launch ownership. Each `FlowRegistration` captures its project binding when the session journal applies registration. `FlowStore::project()`, `FlowWorker::project()`, and read-only `FlowInspection.project` expose that binding without reading live project configuration. Restored context and `FlowStore::source_roots()` use the captured project together with the session's immutable configuration source. Entry preparation, rebinding, and admitted invocations resolve the same `project:` and `user:` namespaces. Compilation reads retained source bundles, so removing the original source files does not change subsequent turns. Resolving these namespace paths does not read configuration credentials or authorize execution.

`FlowWorker::status()` reads execution state, Goal, latest completion, and journal cursor atomically. Host views use this projection instead of combining independently sampled completion and execution reads. Scheduling ownership remains a separate catalog observation and does not imply that a turn is currently executing.

`RuntimeHost::wait_quiescent()` lets batch hosts wait for owned turns, instance closure, scheduler preparation, and notification handoffs without shutting down instances. A scheduler acknowledges the journal cursor it has inspected, so the host does not duplicate entry input selection. Source facts remain outstanding until their observers commit delivery; unrelated journal writes do not count as observable output. Explicit watchers keep a runnable, scheduled recipient alive, while idle spawn result routes do not. Paused, unbound, and policy-ineligible input remains recorded. The wait subscribes before reading and checks for intervening changes before returning; it uses notifications rather than polling. Scheduler, cleanup, and observation failures are reported. Cancelling this wait leaves execution and subscriptions intact.

`RuntimeHost::shutdown()` stops new instance attachment and turn admission, stops catalog-owned schedulers and observers, cancels active execution even when paused, waits for completion facts, and releases journals and process resources. Queued catalog requests without effects fail when their owner stops. Unread inputs, subscriptions, Goal records, and independent pause keys remain stored. Idle instances remain idle; cancelled invocations remain interrupted and require explicit recovery. Shutdown completes already accepted close requests; it does not close other instances or fabricate final answers. Cancelling the caller's wait does not abandon an accepted shutdown; repeated calls observe its original result. Frontend disconnection must not invoke host shutdown.

Daemon SIGINT and SIGTERM close request admission, end SSE streams and accepted Unix connections, and run this shutdown alongside cancellation and cleanup of registered legacy executions. The process marker is removed after cleanup finishes. Event clients can reconnect with their committed cursor; ending the stream does not claim delivery of the remaining shutdown facts. `DaemonState::shutdown()` exposes the same cleanup for embedded hosts and retains ownership when its awaiting caller is cancelled. `register_live` rejects registrations after stopping begins.

`InboxPayload::Invocation` carries typed entry arguments, an invocation configuration snapshot, and optional `UserContent`. It requires uncorrelated `NextTurn` delivery and cannot enter a running model call as a text interjection. `UserContent` shares text, images, and optional quote presentation with `UserSubmission`; only an authenticated user sender can supply it. Both inputs use the same message projection, with the admitted turn identity and user origin assigned by the host. Without user content, invocations project internal sender and argument data. Invocation settings never enter this message. Inherited context seeds the new instance once, survives reopening, and does not become newly published output for result subscriptions. Host preparation selects compatible input and supplies the execution authority.

For an invocation already bound to a persistent instance, `flow.spawn` uses this launch protocol and the common instance scheduler. Source snapshots, declared arguments and defaults, invocation settings, and optional complete conversation history retain their existing contracts. Effective execution authority cannot exceed the caller's ceiling. The caller-bound inventory token also identifies the catalog revision; another registration after inspection rejects new creation before writing it. The launch attempt holds scheduling ownership until activation commits, then transfers it to the session catalog. Failed activation releases that ownership before returning; the prepared record remains available for reconciliation.

`async=true` returns the stable instance address and initial acceptance. `async=false` registers a correlated continuation before launch, subscribes to the exact initial completion before activation, and waits through the common inbox. The caller commits `WaitingContinuation` before returning the saved typed value or error. Both modes leave the instance available after the invocation; later applicable input uses the same scheduler and entry snapshot, even if the source file disappears. The creator's continuing answer subscription excludes only the synchronous initial turn; other subscribers still receive its answers, and subsequent turns notify the creator normally. Ordinary returns do not become final answers.

Cancelling the synchronous caller releases its continuation ownership without cancelling the spawned instance. An unconsumed completion remains in the same inbox, including when it arrives after cancellation. Applicable input can start another turn after explicit interruption recovery; it cannot bypass execution pauses. A completion matching both a watcher and a continuation produces one envelope with both reasons. Consuming that envelope through the continuation does not also schedule model work.

`flow.current()` returns `{instance, turn_id, run_id}` from the invocation binding. `instance` is a full Session/Flow address or null for standalone execution. Inline calls retain their owner and turn while reporting their own run ID. Supplying identifiers as tool arguments cannot change this identity.

The shared `flow_runtime::entry::EntryRecipe` preparation adapter maps later text to the declared `contract { invocation { user_message: parameter } }` string parameter. Directly bound entries and spawned instances use the same adapter. It preserves message provenance and batches compatible input; an explicit invocation or different invocation settings starts a separate batch. Entries without this mapping retain ordinary text input and accept subsequent typed invocations instead of guessing a parameter. Explicit goal continuations can use the recorded arguments without a parameter mapping. Automatic scheduling after host restart still requires an explicit host binding. Persistent spawning supports `workspace=auto`, `retain`, and `none`; the latter shares an existing managed workspace reference when the caller has one.

`LaunchInput.execution` can retain an `EntryBinding` with the initial turn/run identities and structural authority ceilings. Persistent `flow.spawn` records this binding with activation. The default parameters and invocation configuration remain in the entry request; the parameter mapping is validated from the recorded source bundle. Empty identities and a synchronous reply route targeting a different first turn are rejected before activation. The first actual invocation uses the recorded identities, including after a waiting entry is restored; subsequent invocations receive new identities independently of their input request UUIDs. Container startup hooks belong to that first committed invocation and do not run merely because an entry was activated or rebound.

`FlowWorker::entry_recipe` reconstructs this entry under the current host's authority; `SessionHandle::bind_entry` explicitly installs the shared catalog-owned scheduler. Recorded and current ceilings are intersected, including shell, permission management, tool tiers, risks, and workspace limits. Incompatible workspace limits reject binding. The host supplies current trust, the executor, and the cooperative scheduling interval. Entry validation and executor scope checks precede trust installation. Binding, initial activation, and generic host scheduling share the instance activation lock; a competing binding cannot replace a live controller or change its trust. Only open instances accept a binding. Attaching a catalog or reading an instance does not install a scheduler; binding does not release pauses, recover interrupted turns, or replay consumed input. Instances created through lower-level storage APIs without a recorded binding remain readable and report that binding is unavailable.

The interactive CLI restores missing schedulers once when attaching a Session for conversation, including when Switch Session opens it in a main or floating view. The plain REPL uses the same restoration path. Each flow uses its recorded entry and project scope; execution pauses and interrupted turns remain gated. Already attached controllers are retained, and changing views does not restart stopped schedulers. A failed binding is reported without preventing other flows from attaching. Catalog browsing remains read-only.

`EntryStart::Command` atomically accepts a captured startup command with its own arguments and invocation configuration. The default entry and its defaults remain unchanged. A trusted host command has no `UserContent` and projects internal invocation context containing its name and arguments; only authenticated user commands can carry human text, images, or references. Peer messages cannot select command sources. `AcceptedInput` provides the same source-free metadata for activation and subsequent `FlowUpdate::InputAccepted` updates. Startup execution, normal commands, Goal continuation, and subsequent default-entry turns use the same input ownership and retained source checks.

Persistent TUI **New Session** creates a separate container under the requesting view's project and configuration. Its default entry is the configured `agent` command. An optional `on_session_start.at` is captured as the initial command; without it the entry waits for input. Source preparation errors leave the current view and draft intact and do not create a session directory. The creation request owns accepted work independently of the navigation window; closing that window prevents late focus changes, while the created session remains accessible through FlowHub. Matching retries return the created instance without restarting it or releasing its execution gates. Existing sessions keep their own history, Goals, pending input, and execution state.

`atman session new` uses the same creation factory with deferred execution. It records the current project, configuration source, default entry, and optional startup command without building provider or MCP services or installing a scheduler. The session lives under `runtime-v1/sessions/<session-id>/flows/<flow-id>`. A subsequent `--continue` attachment binds execution explicitly; the stored startup source remains valid if its original file changes, and consumed startup input is not replayed. The factory accepts configuration and project bindings without requiring another session, and reuses an existing host-owned journal when execution services are attached later.

Persistent TUI attachment loads services before binding schedulers, installs the shared form transport before startup work can execute, and passes the boot terminal into the interactive view. The outer terminal guard and notification sink cover host shutdown, including setup failure. Boot and interactive input readers have a single lifetime owner that stops and joins the thread on normal exit, error, or cancellation before another reader starts. Setup eligibility reads the attached session's model and authentication source; it does not use the client's global model directory.

`EntryBinding.user_routes` selects configured interactive routing. When enabled, the shared terminal input adapter resolves human text with that Session's `routes.at` and captures the selected command before acceptance; unconfigured or unmatched routes return an error. Slash commands bypass route selection. Original user content remains distinct from parsed command arguments. Direct-entry instances retain their declared `invocation.user_message` mapping, and runtime notifications continue through the instance's default entry.

Persistent execution binds relative tool paths and default cwd to the instance's authorized workspace root, including inline function calls. The filesystem policy uses that same root while retaining its access mode; an explicit session mode change still applies. File-tool approval and installed flow discovery resolve against the same project rather than the host process directory. Unrelated checkout metadata supplied by the host is removed; an ordinary project directory does not become a registered worktree. An instance without a project root requires explicit absolute paths rather than borrowing the host process's cwd. Named user-installed and bundled flows remain available, while relative file references require a bound directory. Missing project paths do not prevent history access or binding; tools report unavailable paths when performing actual I/O. Unbound non-instance calls retain process-cwd path resolution.

## Instance plans and todos

`AtmanRuntime::build` registers flow memory tools directly; embedded hosts can also call `tools::register_flow_memory`. Instance calls need an admitted `FlowClient`, with no temporary session directory or file store required. An instance context without its host binding fails before accessing legacy controllers or stores. `tools::register_memory` retains explicit file-backed registration for existing non-instance sessions. The Goal, Todo, and Plan tool structs accept optional legacy stores, with `Default` providing no file fallback.

`flow_store::planning` records plans and todos in the instance journal through `PlanningRequest` and `PlanningEdit`. The storage owner selects the latest plan, assigns new todo IDs and timestamps, and commits each mutation before returning its `CommitReceipt`. An optional planning revision rejects stale interactive edits. Matching sender/request-ID retries return the original result and receipt, including after closure, without rolling back subsequent changes; conflicting payloads fail. New writes require an open instance and host authorization.

`FlowWorker::planning` and the existing Session plan/todo subscriptions project the same committed records. `plan.write/read/tick` and `memory.todo.*` resolve the admitted invocation's `FlowClient`, so a shared tool registry does not share planning data between instances. Inline calls use their owning instance; spawned peers have independent plans and todos. Missing instance bindings fail rather than falling back to a captured legacy store. Ordinary file-backed stores remain available for existing session readers and use the same entry reducers. Plan changes do not modify the Goal or execution state, and reopening restores the recorded timestamps and completion markers without replaying tools.

Persistent terminal and TUI views support `:todo list`, `:todo done <id>`, `:todo cancel <id>`, and `:todo clear` for the focused flow. IDs may be UUIDs or zero-based list indices. ## Managed image files

`AttachmentStore` publishes content-addressed images without replacing an existing file. Successful imports verify the stored bytes and synchronize the file and its directory before returning an artifact reference. A damaged or non-regular destination fails without being overwritten; concurrent imports of identical bytes share the same verified artifact. Temporary files are removed after publication or write failure.

File-backed image reads stop at the existing 20 MiB limit plus one byte. Base64 inputs are checked against the corresponding encoded limit before allocation. Format, declared media type, and artifact hash validation remain shared by image consumers.

## Durable input acceptance

`FlowStore::publish_message` commits an exact message with its owning turn lease, producing invocation, and stable publication ID. An identical retry returns the original receipt without appending or republishing; conflicting content fails. New publication requires a live matching turn, rejects cancellation and stale epochs, and permits delivery while a paused turn finishes. Message origin and role remain separate. Final-answer recognition stays in the existing message protocol rather than a second storage-specific classifier.

`published_messages` exposes lightweight `PublicationRef` records containing identity, origin, invocation scope, and the original receipt. `published_message(id)` reads the complete message from its verified journal position. Publication retries use that same reader and compare the complete saved value. `context_messages` and `history_messages` return explicit I/O errors when required bodies cannot be read; a checkpointed model window does not read publications preceding its checkpoint. Replay validates checkpoints against a temporary current window and discards it after scanning. This index avoids retaining every published body in storage; active execution contexts have separate lifetimes.

Watcher pages select final-answer references and completion records in journal order before loading the selected answer bodies. A damaged body fails the page without advancing an observation cursor. Private branch publications remain excluded from shared context and watcher output.

`context_messages` restores the latest committed model window and merges subsequent shared input and output in journal order. `history_messages` retains the complete shared conversation independently of that window. Reopening does not invoke tools, replay notifications, or execute the entry. Publications do not end the turn or change Goal state.

## Model-window checkpoints

`FlowStore::checkpoint_context` commits a replacement model window without changing original messages, entry results, or lifecycle state. `ContextCheckpoint` carries a stable identity, the digest of the exact prior window, the replacement messages, and compaction metadata. Matching retries return the original receipt without resetting later messages. Conflicting identities and stale windows fail before writing. Inbox acceptance and unrelated controls do not invalidate a checkpoint; newly committed context does.

Session compaction calculates a replacement using the existing summary and review policy, then awaits the instance's serialized writer before updating the model handle, message projection, cache epoch, or completion frame. An accepted write survives caller cancellation. A failed or unavailable writer leaves the window unchanged and reports the failure. The weak writer binding does not retain the storage owner.

The storage projection retains only the latest complete replacement window. `context_checkpoints()` lists identities and commit receipts, `latest_context_checkpoint()` borrows the current replacement, and `context_checkpoint(id)` reads a complete historical record from its verified journal position. Historical retries use this same read path; unavailable or damaged records fail without changing the current window. Earlier replacement bodies remain in the journal instead of accumulating in memory.

Reopening seeds the model window and full history separately, preserves messages appended after the checkpoint, and restores the cache epoch from the checkpoint itself. An incomplete checkpoint retains the previous committed window and its tail. Compaction does not publish another final answer or create another notification. Persistent spawned peers use the same path as other instances; isolated inline fanout contexts remain invocation-local and are not resumable instances.

## Persistent goals

Each instance journal retains goal creation, text edits, pause, resume, and clearing as `GoalUpdated` facts. Requests carry an authenticated sender, a request UUID, and the expected goal identity and revision; an absent expected version explicitly means that no goal may exist. The shared `memory::goal::GoalEdit` operations validate changes. Committed timestamps and generated identities replay exactly, including clearing the current record, without a separate authoritative goal file.

`FlowWorker::edit_goal` serializes the write, updates the live goal projection and subscribers after commitment, and returns the recorded goal with its commit receipt. Matching request retries return the original result without replacing newer projected state. Conflicting requests, stale revisions, and new edits after close fail. Accepted writes survive caller cancellation. Restoration retains the saved goal status; interrupted execution is represented by the instance lifecycle instead of rewriting the objective.

`GoalRequest.start_turn` is valid only for an authenticated user's explicit resume of a paused objective. Its `GoalUpdated` fact contains the exact `GoalResume` envelope, so objective restoration and next-turn acceptance share one receipt. Replay validates that envelope against the recorded edit and resulting goal; direct inbox acceptance cannot manufacture a resume input. Partial journal writes retain neither change. Retries retain the original command even after its input has been consumed or superseded. A later objective change cancels an unread resume, while cancellation or execution pause retains it behind the execution gate. The shared entry adapter consumes it through ordinary invocation admission, retains the last arguments and invocation settings, and records it as internal context rather than another human message.

`FlowClient::read_goal` requires context-read or goal-management access; editing another instance requires an explicit goal-management grant. Checks run again inside the target owner, and peer callers cannot impersonate user or runtime actors. Creation relationships grant no additional authority. Goal changes do not remove execution pauses, invalidate unrelated inbox messages, or control peers. Automatic continuation remains an entry policy admitted by the host scheduler.

## Input acceptance

`FlowStore::inbox_entry(id)` reads an accepted message from its verified journal batch and applies its latest recorded content replacement. Historical received-message pages use the same reader. Acceptance, content replacement, and queue revision have separate positions: moving or cancelling an item cannot replace its edited body with an ordering record. Startup, Goal, watcher, and timer inputs are read from their original atomic producer facts. A missing or damaged body returns a read error rather than a cached message.

`inbox_entries`, `pending_inputs`, and `pending_input_entries` expose body-free control records. These retain identity, sender, delivery mode, scope, Goal continuation identity, and consumption state; message text, attachments, arguments, and command source bundles remain in the journal. Writers prepare this metadata and request fingerprints before committing acceptance, and recovery uses the same preparation. Input reservations read eligible bodies explicitly, excluding replies owned by a waiter; read failures do not consume input. Execution snapshots and view snapshots load their requested pending bodies through `inbox_entry`.

`GoalContinuation` is an entry-authored next-turn input tied to the active turn lease and an exact active goal version. `FlowStore::schedule_goal` creates one stable request identity for that pair; retries retain the original receipt and conflicting text is rejected. A goal changed or paused after preparation returns no acceptance without failing the entry; invalid identity, authorization, or storage still returns an error. The proposal shares the ordinary inbox and cannot enter an active model context. It does not start execution until the proposing turn has completed and ordinary execution gates permit admission.

Goal edits, pauses, replacement, or clearing cancel proposals whose acknowledged goal is no longer active and current. Cancellation, failed execution, and host loss invalidate the proposing turn's continuation without discarding unrelated messages. Admitting another invocation consumes its selected input and cancels unselected continuation proposals in the same commit. Original request bodies and cancelled receipts remain available after reopening. Execution pause alone retains proposals; resume does not change goal state or authorize interrupted work.

`memory.goal.schedule` uses the caller-bound `FlowClient` to submit this proposal. The shared entry adapter selects ordinary eligible input first, or one continuation when none is available. A continuation uses the source turn's committed entry arguments and invocation configuration rather than creation defaults. `last_invocation_input` and the scheduling snapshot expose that exact admitted configuration through an index rebuilt during journal replay. Continuation text has internal origin and user protocol role; it is neither a new user request nor new authorization. The scheduler only admits prepared inbox input and never infers another turn from an active goal.

`FlowStore::accept_input` persists a typed delivery request before returning `Acceptance`. User submissions retain text, images, invocation configuration, and presentation data. Interjections, flow events, watcher notifications, timers, and internal controls remain distinct payload variants with sender, recipient, correlation, cause, scope, and delivery mode. A protocol message role is not used as a provenance label.

The host authenticates the sender before calling storage. A matching sender/request ID retry returns the original acceptance receipt and current disposition, including after restart, revocation, or closure. Reusing that identity with different content fails. New inputs additionally require an open instance, consistent source/payload categories, and a successful `authorize_new` callback. Host-only delivery types cannot be accepted as user or peer-authored controls.

Paused and interrupted flows retain accepted inputs in FIFO order. A new authenticated, unscoped user submission, authored command, invocation, or interjection atomically recovers an interrupted Flow without releasing pause keys or resuming its Goal. Input accepted after cancellation begins can recover the Flow when that invocation finishes cleanup; earlier queued input, accepted retries, host notifications, and peer messages cannot. Completion retains the cancelled outcome even when the same commit recovers execution for the new request. A durable close transition cancels pending inputs in the same replayable state change, preserving their bodies and original acceptance receipts. New requests to a closing or closed instance fail; already accepted requests remain accepted facts with a cancelled disposition. Acceptance does not mean an input has reached a model or completed business work.

## Atomic input admission

Input scope discovery reads distinct pending `TaskScopeRef` values inside the storage owner. Turn admission and model-boundary checks resolve these references without copying queued message bodies, command sources, or previous invocation arguments. The admission transaction still validates selected messages and source state before committing input; outgoing reply dependencies remain separate from incoming input dependencies.

`FlowStore::edit_input` persists edits to pending human input as one `InboxEdited` fact. Requests carry an authenticated sender, stable edit UUID, message UUID, and expected message revision. Replacement preserves invocation configuration and command source; movement exchanges adjacent entries in that user's next-turn lane after validating its observed order. Cancellation retains the original input and acceptance receipt. Peer messages, watcher notifications, and internal controls cannot be rewritten through this interface. An outstanding reservation excludes editing, and consumed or cancelled input rejects new changes.

Each message exposes its latest edit receipt as `InboxEntry.revision`. Delivery retries still compare against the original request and return the original acceptance receipt with current disposition. Exact edit retries return their committed receipt even after input consumption or restart; conflicting reuse fails. Authorization runs for retries as well as new edits. Writers and read-only replay share validation, and stream subscribers receive the committed edit without an extra transcript message. The edit does not consume input, interrupt work, or release an execution pause.

Retry indexes retain fixed-size request fingerprints and receipts instead of additional copies of edited message bodies. Original acceptance and edit facts remain complete in the journal. Fingerprints are prepared before committing and rebuilt during replay; deletion retains the same evidence. Object key order and floating-point signed zero do not change JSON request identity. This index does not impose message limits or discard pending input.

`FlowWorker::edit_input` serializes authorization, receipt lookup, and mutation through the instance owner. Promoting next-turn input to `AtBoundary` checks its requested configuration against the active lease's durably admitted invocation; idle, finishing, or incompatible invocations retain the queued input. A model's actual image capability is checked when that shared general call receives input, so attachments remain pending through text-only calls. Promotion and receipt retries never start a separate execution path. `FlowViewSnapshot.pending` contains ordered `InboxEntry` values with both original acceptance and current edit revision at the same cursor as the transcript, execution, and planning snapshot.

Conversation views display these entries through a source-typed queue model. Persistent controls carry the original flow address, message revision, and edit identity through the bound view mailbox. A successful send does not clear an edit draft: the matching durable receipt closes that editor, while failure retains its contents. Retrying an unchanged request preserves its edit UUID; late replies cannot close a replacement draft. Editing authored text preserves its quote, images, and invocation configuration. Background notifications remain read-only, and inserting or removing pending input does not synthesize transcript content.

`SessionInspection::inspect_inbox` and `SessionCatalog::inbox_page` expose read-only delivery history for one Flow. `InboxSide::Received` returns accepted envelopes with their current disposition and edit revision; `InboxSide::Sent` returns outgoing intents and receiver acknowledgements. Both reuse the complete validated Flow replay without opening a writer, recovering execution, repairing an incomplete tail, or consuming input. Each page contains at most 50 records, a journal receipt, trailing-byte count, and a continuation cursor bound to the Flow, direction, and original acceptance or send receipt. Records are ordered newest first by original journal insertion, independent of later queue reordering. A continuation reads current dispositions while excluding records newer than its anchor; refresh from the first page to see new arrivals. Changed, unknown, or foreign cursors fail instead of silently restarting pagination. Catalog authorization runs before reading and again before returning records or counts. `PendingDelivery`, receiver `Accepted`, and receiver `InputCommitted` remain distinct facts; none alone proves completion of the requested work.

`reserve_context_input` reserves eligible `AtBoundary` messages for a running turn. `reserve_invocation_input` reserves an idle instance's inputs against a candidate turn lease without starting that turn. Both use the same inbox ownership primitive. The host chooses compatible submission configurations and prepares the actual input; storage does not infer model settings, user authority, or agent policy from message text.

`commit_input` validates reservation ownership, state revision, turn lease, target, and FIFO membership. A context commit records the exact messages and consumed envelope IDs together. An invocation commit additionally records `TurnStarted`, entry arguments, and invocation configuration in that same journal batch. An entry or model request must not execute before this commit succeeds. Context messages must belong to the admitted turn, and `NextTurn` messages cannot be consumed at an active-turn boundary.

Execution state changes revoke outstanding reservations. Releasing or dropping a receipt retains pending messages; late commits and releases cannot consume or release a newer batch. Finishing, cancelling, paused, interrupted, and closed instances cannot admit ordinary context input. A failed validation leaves the queue and journal unchanged; a failed journal write requires reopening and reconciliation.

`committed_inputs` exposes `InputRecordRef` metadata: turn lease, consumed IDs, target, command identity, message count, and original receipt. It retains neither chat bodies nor entry arguments, invocation settings, or reply values. `committed_input(receipt)` validates the complete receipt and reads the original journal batch; `last_invocation_ref` checks identity without I/O, while `last_invocation_input` reads the admitted configuration. History and model-window readers load required input batches in journal order, skipping inputs preceding the current checkpoint when restoring its window. Required reads propagate I/O errors without changing consumption or execution. Replay restores the exact input instead of preparing it again, and committed messages do not return to the pending queue after interruption or closure. Acceptance retries retain their original receipt and report `InputCommitted` once consumed. This state does not assert model inclusion or business completion. Incomplete invocation batches restore neither a turn nor consumption; accepted inputs remain pending.

## Correlated continuation input

`register_reply_waiter` durably binds a correlation ID to a turn lease and expected authenticated sender before the corresponding request is sent. Identical registration retries return the existing record; conflicting reuse and registration after matching replies have arrived fail. Multiple independent waits can belong to one turn. Correlation IDs are not authorization credentials.

`reserve_reply_input` selects the oldest matching `AtBoundary` reply from the existing inbox while the turn is running or waiting for replies or effects and all execution pauses are released. Reply ownership belongs to the registered continuation, so other branches need not stop running. Execution-gate waits, finishing, cancellation, and closure prevent delivery. Ordinary context and invocation reservations exclude replies owned by live waiters. Every consumer uses the same opaque batch ownership; there is no parallel reply queue. `commit_input` with `WaitingContinuation` persists the actual continuation value, consumed message ID, and delivered waiter status in one fact. It does not change other branches' progress, create a turn, wake a Rust future, or claim that the continuation executed; the host resumes execution only after successful commit and execution admission.

Pausing retains registrations and accepted replies while revoking reservations. `cancel_reply_waiter` releases unconsumed replies to ordinary input without discarding them or releasing execution pauses. Finishing, cancelling, ending, closing, and lost turns cancel their outstanding waits as part of the same durable lifecycle transition. Restart does not reconstruct suspended Rust futures: uncommitted replies remain pending behind interruption recovery, while delivered replies retain their committed input and are not delivered twice. Reply records remain available through `reply_waiters`, including cancelled and delivered states. A retry reads delivered input directly from its recorded receipt and checks the original lease and correlation, without scanning historical bodies or consuming another reply.

`FlowClient::prepare_reply` establishes an owned `ReplyWait` before a request is published. Its completion wait subscribes to committed changes before inspecting the inbox, validates the source turn, and commits consumption through the recipient owner. Concurrent continuations retain independent ownership without changing the whole flow's phase. Dropping the last unfinished guard cancels only that waiter; lifecycle recovery also releases abandoned waits. Retrying a delivered wait reads the committed continuation value without consuming another envelope.

Identical `prepare_reply` retries on a live worker share one local continuation claim. Dropping one handle leaves other handles valid; dropping the last handle cancels only a still-pending waiter. Cleanup checks the claim identity inside the journal owner, so a delayed release cannot cancel a replacement claim. Delivered input remains committed, and a repeated completion read returns its recorded value without consuming another envelope. Local claims do not survive host loss; durable waiter and input facts determine recovery.

## Durable sends

`queue_send` records a flow-owned delivery request before contacting its recipient. New sends require execution admission, consistent sender provenance, and successful host authorization. Matching request ID retries return the original record before applying new-send gates; conflicting reuse fails. An optional reply waiter must name the same correlation, current turn, and target flow. A new waiter and its send intent are committed together; an identical pending registration may also be reused.

The transport copies a recorded request to the addressed flow's `accept_input`, then passes its authenticated `DeliveryReceipt` to the sender's `confirm_delivery`. Same-session and cross-session delivery use these same storage APIs. Recipient acceptance and sender confirmation are separate commits; no cross-journal atomicity is implied. Delivery does not wait for recipient execution, and a scheduler must not hold a session-wide lock while contacting another flow.

`sends` and `pending_sends` expose `SendSummary` records containing identity, recipient, scope, authorization, reply correlation, queued receipt, and delivery status. Complete intent bodies remain in their original journal batches; `send_record` loads one `SendRecord` and reports read or integrity errors. Replay retains summaries without accumulating send bodies. Lost acknowledgements remain pending across restart and closure until reconciled against the recipient's idempotent acceptance. A retry can therefore recover an existing receipt after revocation or closure without authorizing a new delivery. The host must still enforce current delivery scope for previously unaccepted requests; storage does not automatically resend or bypass authorization. `confirm_delivery` accepts reconciliation after the sender has stopped, rejects conflicting confirmations, and validates the recipient journal identity. The transport authenticates the peer and binds the acknowledgement to the full address and request; a journal digest is not a signature.

Writer reads and historical inspection use the journal's validated batch-position index. A historical reader retains its opened file and inspected prefix; it neither follows a replacement path nor accepts receipts from later appends. Each body read verifies the requested receipt and batch integrity without rescanning preceding history. Sent-history pagination selects summaries before loading page bodies. Missing or damaged bodies produce errors rather than empty records or delivery failures; pending state remains recorded.

An accepted send records receiver acceptance only. It does not assert that a model read the input, that a continuation executed, or that business work completed. Sender history retains the send intent, queued receipt, and receiver acknowledgement, while receiver history retains the accepted envelope and subsequent input disposition.

`DeliveryFailed` records a definitive receiver rejection in the same commit that cancels any still-pending reply waiter. A closing or closed receiver first checks its acceptance ledger: existing requests retain their original acknowledgement, while never-accepted requests return a typed rejection with the observed receiver receipt. The sender stores `Failed { failure, by }`, removes the intent from pending delivery, and preserves its original content and request identity. Later observations of the same closed receiver return the first failure record. Acceptance cannot be overwritten by failure, and failure cannot be overwritten by acceptance. Writer recovery, read-only inbox history, typed updates, and TUI delivery status use this same fact.

Session and project deletion reject closed instances with pending sends. `FlowInspection.pending_sends` derives the count from the same replayed outbox used for delivery reconciliation. Closure does not prove that outgoing work was delivered; removal requires every recorded send to have acceptance or a definitive failure. Rejected deletion preserves journals and creates no deletion receipt.

## Instance execution bindings

`Executor::run_linked_with_invocation` accepts `RootInvocation.instance`, an `InstanceInvocation` containing the host-admitted turn lease, explicit authority ceiling, and cancellation token. The executor registers an instance identity in the existing permission pipeline and uses the recorded turn and run IDs. It does not derive an authority ceiling from root status. Entry capability declarations may narrow the supplied ceiling but cannot broaden it. Inline calls retain the instance address and inherited restrictions.

`Session::open_instance_context(address)` creates an isolated in-memory execution context for one instance, with its own messages, Goal controller, watcher state, and interaction services. Its session ID identifies the container; its flow address identifies the context owner. Passing this context without an explicit matching instance binding fails before execution. A mismatched context, turn, or initial run also fails. Clones of an execution binding share one consumption flag, preventing reuse of the same binding for another execution attempt.

The host compiles the recorded source bundle, commits invocation input, and constructs a binding only after durable admission. It then runs the existing executor and commits the lifecycle outcome after invocation cleanup. These APIs do not themselves schedule pending inputs or revalidate pause changes during a running invocation; those responsibilities remain with the owning host. Creating a context does not create another on-disk session or replay unknown effects.

Persistent turn execution includes configured `on turn.start`, `on turn.end`, and queued `on session.context_compact` hooks within that same binding. Hooks share the instance context, authority ceiling, cancellation, and trace scope, with independent run identities. The visible entry remains bound to the admitted entry run. Ordinary hook failures are reported without replacing the entry result; cancellation stops further hooks. Hook execution is non-reentrant. `AtmanRuntime::build` loads configuration hooks in filename and declaration order; peers inherit that immutable graph, and rebuilding the host can reload it. Session start and end hooks remain separate from turn boundaries.

A host can explicitly record `EntryBinding.session_start` for the container's initial host-created entry. Its first admitted invocation executes `on session.start` before turn hooks. Input commitment owns that startup attempt, including cancellation or interruption; retry, rebind, and subsequent invocations do not replay it. Peer creation cannot request container startup. CLI batch execution records this binding when creating its session. Entry return leaves the session open, and host shutdown detaches execution; neither triggers `on session.end`.

## Instance storage worker

Journal history supports bounded `read_after` pages using a complete `CommitReceipt`. Cursor validation checks the journal identity, sequence, and digest; foreign, altered, and ahead-of-history cursors are rejected. Pages preserve whole commit batches and resume after the last returned receipt. A metadata index rebuilt during recovery locates each committed file range without rescanning earlier records or cloning cumulative history. Reading a page does not move the next append position or consume flow input.

`FlowStore::read_updates` projects these batches into typed `FlowUpdate` records. Conversation publications preserve message origins and isolated context identities; input acceptance, input consumption, final answers, execution diagnostics, and turn completion remain separate facts. Creation updates omit retained source bundles, and activation updates omit execution authority. Readers receive complete committed batches in their original order rather than reconstructing history from display diagnostics.

`FlowWorker::read_updates` and `subscribe_updates` share the same cursor and projection. Subscription registration and initial cursor validation finish before the stream is returned. Committed changes between registration and the first consumer poll are recovered through paged history; coalesced notifications never substitute for reading that history. Idle streams wait for commits without polling or emitting empty pages. Reconnection resumes after the last applied batch, and dropping a view does not pause or cancel execution. This feed contains committed state, not speculative streaming text.

`FlowWorker::subscribe_view` supplies a `FlowViewReader` for a complete conversation and state view. The owner captures execution, Goal, planning, the recorded workspace request, pending input, and their commit cursor atomically. The workspace request describes acquisition intent and shared ownership; it does not assert that the checkout is currently available. `FlowViewSnapshot.pending_order` contains complete body-free queue metadata; `pending` contains at most 32 message bodies starting at `pending_offset`. `set_pending_offset` changes the reader's page independently of journal updates, and queue shrinkage clamps the offset to the last page. Main and floating views retain independent page positions while sharing queue counts, reorder preconditions, and draft identity checks. This view page size does not limit input acceptance or model-boundary consumption. History catches up in bounded pages to that exact cursor before the view is exposed; later writes remain available for the next read. Cancelling a read retains its observed notification and partial progress, while repeated refreshes preserve record identities. The persistent terminal uses this reader for focus changes, live output, and final catch-up after host quiescence. Reading or dropping it never consumes input or changes execution. Live resources and unsent drafts remain separate from durable state.

`flow_runtime::FlowWorker::start` takes exclusive ownership of a `FlowStore` and restores its conversation through the existing message projection. Commands are serialized per instance; blocking journal work runs on the blocking pool, and an idle worker does not occupy a thread. Accepted commands complete even when their awaiting caller is cancelled. `shutdown` drains accepted work and hands the store back without changing the recorded execution lifecycle. Hosts stop active execution before handing off storage; an unexpected loss of storage cancels bound execution and leaves recovery to reconcile the recorded lifecycle.

`InstanceInvocation::with_storage` binds the executor to the worker's exact context and validates its admitted lease. `session.push`, `final.answer`, recorded model responses, and context records commit before updating context or publishing complete-message frames. The worker performs projection before acknowledging, so losing the acknowledgement does not suppress a committed reply. The same final-answer normalization and publication path serves stored and ephemeral execution. Draft streaming remains transient.

Inline calls share the instance context. Fanout calls retain isolated invocation contexts: their publications remain in the owning instance journal with `context_run`, and recovery does not merge them into the shared conversation. Message scheduling claims use the instance address rather than serializing every flow in a session.

Worker binding covers message publication, model-window checkpoints, persistent spawn execution, and process resources. Process and flow watcher tools deliver through the instance inbox. CLI batch execution, persistent REPL attachments, and instance-addressed daemon operations use the persistent host; explicitly ephemeral execution and published legacy history retain separate entrypoints.

### Runnable peer host

The [peer host example](../crates/atman-runtime/examples/peer_flows.rs) executes [a shared `.at` entry](../crates/atman-runtime/examples/peer_flows.at) in two independent instances without model credentials or external tools:

```sh
cargo run -p atman-runtime --example peer_flows -- /tmp/atman-peer-demo
```

Each run creates a separate Session in the supplied data directory. Both peers register one-shot watches on the other's final answers. A completes while B is paused; B retains that notification and another input across host shutdown. Reopening preserves the original message IDs and pause key. Explicitly reinstalling the scheduling policy and resuming B consumes its two inputs in one turn, and its final answer starts another turn on A. Closing B leaves A available. Assertions verify the final-answer counts, pending input, recovered history, and closed state; the example prints the retained Session directory and instance IDs.

The example's trusted local host supplies input preparation and authorization callbacks. It uses the production journal, scheduler, watcher, publication, and shutdown paths. Its ten-second waits bound the demonstration only; they do not configure instance execution budgets. Restoring an execution binding remains explicit, and the example does not replay interrupted external effects.

### Flow process resources

`WorkspaceManager::create_instance` records a typed `FlowRef` before allocating a managed Git worktree. `share_instance` adds another instance reference using a live sponsor. The resulting `bound` record has no process lease; host generation changes do not orphan it. Generic release, finalization, and pruning cannot remove a live instance reference. `validate_instance` checks recorded ownership, paths, and Git registration without recreating missing checkouts. Registry queries remain available when a checkout is missing.

The owning host calls `release_instance` after stopping execution and process resources. Releasing a reference returns `Referenced` while other instances still use the worktree. Only the last release cleans up: clean automatic worktrees at their recorded allocation commit are removed; dirty and retained worktrees keep their data. A changed commit or an unknown allocation base retains the checkout even when its index is clean. Cleanup retries preserve the recorded result; sharing retries cannot revive released references. Incomplete allocation can be released only by its exact owner, with existing Git state verified before removal. Registry updates synchronize file contents and directory entries before returning.

Explicit `WorkspaceManager::release` records a `WorkspaceRelease` identity and force option in `Releasing` before removing the checkout, then commits `Released`. A pending retry must use the recorded force option and owner; live instance references always reject release. The deletion step shares registration and path validation with automatic cleanup. A pending release with neither filesystem path nor Git registration can finish after a previous deletion, while one surviving side requires explicit recovery. Dirty worktrees remain protected without force. Completed explicit releases return their recorded result without touching a replacement path. Read-only inspection never resumes removal, and retention changes cannot overwrite a pending release.

`release_observed` and `retain_observed` share one locked snapshot check before invoking the resource mutation. Both validate recorded roots and registry identities, compare the complete expected record, and reject invocation leases. Release additionally rejects live instance references and applies the existing durable removal protocol. A stale or uncertain result requires refreshing the resource before submitting another operation; the caller must not silently replace the expected snapshot.

The release identity is also synchronized into an `atman-release` marker in the checkout's Git administrative directory before the registry intent is committed. A retry against a surviving checkout must match that marker, preventing an old forced request from deleting a newly registered checkout at the same path. Git removes the marker with the original worktree registration. A marker left before a failed intent write can be reused after current ownership and checkout validation; it does not independently authorize deletion.

`LaunchInput.workspace` declares an immutable allocation or sharing request. The instance journal commits `WorkspaceRequested` before acquiring the registry reference and activating the entry. Failed allocation retains its prepared instance and request for inspection and explicit cleanup. Request retries cannot change resource identity or acquire resources after instance closure. Restoring history reads the request without executing Git operations.

`FlowInspection.workspace` exposes this recorded intent through the same validated read-only replay. `WorkspaceManager::inspect` reads a known repository and storage location without creating a registry, taking an execution lease, reconciling hosts, or releasing references. Use the persisted root identities when the original directories are unavailable. The snapshot retains registered owners, released references, retention policy, and lifecycle state separately from each checkout's observed HEAD, branch, and dirty flag. A missing path is `Missing`; a surviving path that cannot be verified against Git is `Unavailable` with a reason. Missing registries are distinguished from empty registries, and malformed or unreadable registries return errors. Registry records are one recorded snapshot; checkout observations are independent and do not authorize cleanup. Callers authorize both locations before inspection and keep mutations on the resource owner's existing control path.

`WorkspaceManager::retain_observed` accepts the expected resource record and an explicit retention value. It validates the same recorded roots and resource paths, locks the registry, and rejects changed records or invocation leases before using the existing retention transition. Bound references remain intact; automatic cleanup still occurs only when the last reference closes. This operation provides optimistic concurrency, not a request receipt ledger: an unknown result requires reading current state before issuing another change. The TUI uses the requesting view's control ticket and refreshes details after persistence; a post-commit read failure is reported as saved rather than as an uncommitted mutation.

`SessionCatalog::workspace_page` discovers recorded acquisition and sharing requests across Sessions, including external storage and missing checkout paths. It shares `FlowCatalogCursor` and the bounded, authorized traversal used by `watch_page`; empty Sessions and unreadable records advance the cursor, and revoked access rejects the entire page. Each successful Flow entry includes its project root and journal receipt. Discovery does not open execution owners, run Git, or create missing directories. A recorded request is historical intent, not proof of a live resource reference; use the resource registry to inspect current ownership. Newly created records appear when discovery restarts from the first page.

Entry binding checks the current host's repository authority; each turn validates the live reference before consuming input and binds the same directory to filesystem tools, inline calls, and further peer spawns. `FlowWorker::transition(Closed)` checks revision, inactive execution, and stopped process resources before releasing the reference and committing closure. Cleanup failure leaves the instance closing and retryable. Host shutdown retains the workspace reference for instances without an accepted close request; an explicit scheduler binding after restart validates the existing worktree without recreating it.

Each persistent `FlowWorker` owns an `InstanceResources` group containing its `BgRegistry`, `TermRegistry`, and `TaskRegistry`. Bound executor invocations use that group across turns; inline calls share it, and persistent peers use their own worker's group. Handles and task operations cannot access a sibling's registry, even within the same session. Instance invocations without storage do not inherit a runtime's process registries implicitly.

Background processes use the resource owner's cancellation lifetime. Completing or cancelling a turn and pausing execution do not close that group. Explicit process/task termination still stops the selected process. `CloseRequested` commits before closing process admission and requesting cleanup; the worker publishes the state and acknowledgement only after admission is closed. A terminal created concurrently with closure is terminated before it can be registered. `Closed` rejects unfinished process cleanup.

`FlowWorker::shutdown` drains accepted storage commands, stops process resources, waits for their output readers to finish, and returns the journal. Retained context or resource readers do not keep those processes alive. Unexpected owner loss requests cleanup without inventing a durable terminal state. Reopening creates empty live registries and does not recreate processes from history.

Host shutdown tracks physical execution separately from durable turn state. Execution claims and admission closure are serialized by the instance owner; cancellation reaches paused invocations through the same resource lifetime. The host waits for executor bodies and their completion attempts before releasing storage, including when the cancellation or terminal record cannot be written. A failed journal or missing durable completion remains an error. Reopening retains pending input and pause keys and records interrupted execution without replaying unknown effects.

Process logs, attachments, and large tool output use the owning `FlowStore` directory under `sessions/<session>/flows/<flow>`. Legacy Plan/Todo refresh entry points leave journal-backed projections intact. Legacy invocations retain their existing turn cancellation behavior and process registration APIs.

### Invocation-owned interactions

`ToolCtx::prompt_resolver()` binds the configured host transport to the calling invocation. `PromptResolver::register_in_context` receives the original event sink, owning context, run identity, and tool-call identity. The daemon bridge retains only shared transport state; it no longer captures one session or event sink at construction. Inline and fanout calls retain their owning instance even when a branch isolates its model context.

`ToolCtx::form_resolver()` selects that transport or the attached form registry through `FormPromptResolver`. The TUI uses the same runtime adapter. VM entry binds interaction context for language intrinsics and registered tools, so parallel context isolation does not bypass confirmation. Both paths share prompt wait ownership: cancelling or dropping execution removes waiting forms; `form.ask` retains a reply route after a normal timeout, while `user_confirm` closes its confirmation request.

Form, approval, and compaction-review registries publish their current records within a serialized snapshot update. Snapshots retain changes while views are detached, so reopening a view shows pending interactions without restoring cancelled records. This live-view contract does not persist unresolved prompts across process restarts.

Pending and resolved daemon events use the same captured sink, including cancellation and late responses. Registration publishes the pending event before concurrent resolution can publish its answer. Prompt waits release their registration when their future is dropped, even if their own cancellation branch never runs. Expired forms intentionally retain their late-answer route.

The TUI can display forms from multiple flows through one registry. Each record retains its originating run, tool call, and deferred-answer inbox independently of the current view. `FormRegistry::request_with_inbox` makes that destination explicit; ordinary `request` uses the registry's default inbox.

For persistent instances, late answers use the owning flow's durable inbox as `FormReply` envelopes. The host validates the original form and destination before submitting; prompt identity determines a stable request ID. Matching retries reuse acceptance, including after consumption, while conflicting answers are rejected. Accepted answers survive reopening, obey execution pauses, and use the same input reservation and commit path as other boundary messages. Their model-facing role is `user`, with `Interjection` origin; they do not grant permission or resume paused work. Legacy sessions retain their deferred-form event path.

`FormRegistry::submit`, `DeferredFormInbox::record`, and daemon prompt resolution are asynchronous and return storage errors. Late-answer routes remain available until acceptance succeeds. Concurrent submissions serialize per prompt without holding the registry lock during storage I/O. The TUI retains drafts until acknowledgement, reports failures in the form, and ignores receipts from earlier submission attempts. Configuration forms follow the same acknowledgement contract. Accepted-answer recovery does not restore unanswered prompt registrations or suspended tool futures across process restarts.

Registered transports return `FormSubmission` for both `form.ask` and language-level `user_confirm`. The latter shares its decision check with the in-process registry: one positive confirmation returns `true`; rejection, malformed submissions, and transport failure return `false`.

## Execution diagnostics

Persistent instance execution sends node, tool, model-usage, and resource diagnostics to the owning flow's event sink. Inline calls and fanout retain that instance binding; peer instances use separate sinks. Concurrent producers allocate sequence positions, forward, and update the live projection in one order.

`ExecutionEvent` records an `ExecutionScope`, instance-local sequence, timestamp, and typed event. Invocation scope retains the producing turn lease. Instance scope accepts permission-service diagnostics independently of the active turn; audit payloads retain their original requesting run, group, and decision identities. `FlowStore::execution_events` and `FlowWorker::execution_events` return both scopes through the same batches and journal receipts. Conversation messages, Goal changes, lifecycle transitions, and model-window checkpoints remain in their existing facts; execution batches cannot substitute for those records. Sequence positions identify local event order, while journal receipts identify durable commit order.

`RuntimeHost::with_redactor` or standalone `FlowWorker::start_with_redactor` binds diagnostic redaction for the writer's lifetime. `RuntimeHost::attach_session_with_redactor` binds a separate policy to each Session when one host serves multiple configuration sources. That policy applies to service events during execution and idle periods. An invocation can supply a separate execution policy through its source event sink; otherwise it retains the writer's policy. Audit capture is installed before context services are constructed and never switches to a newly active turn. Reading saved audit events does not restore pending approvals or replay permission decisions.

The existing flow writer drains captured diagnostics before applying commands, including message publication and turn completion. Redaction and disk writes run on the storage worker. Diagnostics from a completed turn's retained resources keep their original lease and can arrive during a later turn. Storage handoff drains resources and remaining diagnostics before returning ownership. Reopening restores the committed batches and advances new event positions beyond their recorded high-water mark without reexecuting work. A failed journal write stops that writer and prevents acknowledgement of later commands.

Diagnostic backlog applies backpressure at invocation suspension boundaries. The executor waits for the writer when a transport batch is pending, while pause and cancellation remain observable. This preserves diagnostics without allowing a CPU loop to continually grow pending writes; it does not set an operation budget or drop events. A cooperative quantum and independently running resource callbacks can still emit events before reaching that boundary.

## Owned instance turns

General model calls using shared session context claim compatible `AtBoundary` inbox messages before reading that context. The storage worker reserves, commits consumption and exact messages, and updates the conversation projection as one owned command. Auxiliary extraction, explicit message overrides, context-free calls, and isolated fanout branches do not claim shared input. Inline calls use the same instance inbox.

Submission settings must match the current invocation snapshot, and image submissions remain pending when the selected model cannot accept images. `NextTurn` input and replies owned by continuation waiters stay queued. Scoped input requires active source scopes at the consumption boundary; unavailable sources retain their input without blocking unrelated messages. Paused and finishing turns do not claim new input. Peer deliveries retain sender metadata and a non-user origin even though the model protocol role is user. Committing context does not certify that a model received or handled it; model failures and process recovery retain the committed context without requeuing those envelopes.

`FlowWorker::start_turn` receives an explicit `TurnRequest`: ordered accepted envelope IDs, turn/run IDs, arguments, invocation configuration, context messages, authority ceiling, and cooperative yield interval. It compiles the recorded source bundle before admission, validates the selection, and commits input consumption and turn startup together. Invalid source or stale selection leaves input pending. Actual entry execution uses the existing executor and never holds the journal owner across a model call or tool wait.

The worker starts and owns the execution task before returning a `TurnTicket`. Dropping the ticket or its waiter does not cancel the task or its terminal commit. The worker permits only one execution claim for a live lease, including when callers construct separate execution bindings. Completion is acknowledged after invocation cleanup and one durable fact containing the exact entry result and terminal state. Failure and cancellation become explicit interruptions; cancellation cannot be reported as successful completion. Unknown effects are not retried.

`FlowStore::finish_turn` retains a `CommittedCompletion` with the turn lease, finish timestamp, execution outcome, typed result, and commit receipt. Identical retries return that receipt, including after reopening; a different result for the same lease is rejected. Execution controls can force a cancelled outcome even when the entry returned a value. Recovered host loss and explicit lifecycle completion without a return are recorded as `unobserved`, never as an invented value. An incomplete terminal write restores neither its result nor a successful terminal state; normal abandoned-turn recovery records the interruption.

`StoredValue` preserves primitive types, field order and duplicate field names, list nesting, floating-point bits, supported host payloads, and returned error values. Floating-point bits use eight big-endian bytes so JSON adapters preserve negative values, signed zero, and NaN payloads without converting an unsigned 64-bit integer to an imprecise number. A returned error value remains distinct from a failed invocation. Process-local closures and pending calls are marked unavailable for restoration, as are host payloads that cannot be serialized; they are not replaced with null or executed during recovery. A direct `TurnTicket` observer can receive the original in-memory value; persistent synchronous spawning restores the recorded value and reports unavailable results explicitly. Reading a saved return does not append it to conversation history or publish `final.answer`.

`FlowWorker::completion` reads a saved result by turn, or the latest completion when the turn is omitted. `FlowClient::read_result` applies current output-read grants at the target owner. The shared `flow.result(handle, turn?)` tool returns `{ completion: ... }`, with null for an absent record. Its stored result uses tagged types, such as `{ kind: "returned", value: { type: "int", value: 42 } }`; the completion also identifies the producing lease and outcome. Reading the latest completion does not imply that the currently active turn has finished. This tool requires a persistent instance binding and does not fabricate results for legacy run handles.

`subscribe_state` provides the committed lifecycle snapshot, updated before a command acknowledgement. After the entry returns, the executor commits `Finishing` before running deferred compaction and turn-end hooks. The turn retains its lease until cleanup completes; hook model calls cannot consume new inbox input. A `final.answer` publication alone does not enter this phase or end the entry. The executor waits at suspension boundaries while independent execution pauses remain, continues cleanup during cancellation, and permits finishing work to settle. Resuming one pause key does not remove others. Host-selected `yield_interval` makes CPU-only code reach suspension boundaries without an operation limit or a language-level default budget. A closing instance cancels its active turn and remains closing until the host completes resource cleanup.

`subscribe_commits` also observes inbox delivery and other durable changes that leave lifecycle state unchanged. Subscribe first, call `borrow_and_update` before `snapshot`, and await `changed` only after finding no admissible work. This order retains arrivals between an empty scan and the wait. `snapshot` reads lifecycle, journal cursor, and pending input in one serialized command. Commit notifications coalesce and wake all subscribers; readers must recheck eligibility rather than treating a notification as an execution grant. Reads, rejected writes, and idempotent retries do not emit notifications. Reopened workers expose their restored cursor and pending input immediately.

`FlowWorker::schedule` owns one event-driven admission loop per instance. A host preparation callback chooses the ordered input IDs, invocation arguments, context, and authority from a committed snapshot; it can decline input without consuming it. The callback performs local preparation, not external I/O. Admission verifies that the snapshot cursor is still current before compiling and committing the turn. A concurrent input or control change causes a fresh scan. Idle, paused, active, or interrupted instances wait for committed changes instead of polling.

Preparation consumes its body-bearing snapshot in a synchronous scope. Only the committed cursor and selected turn request leave that scope; admission, execution, and idle waits do not retain copies of unselected inbox bodies or prior invocation arguments. This does not cap the selected batch, change input order, or turn the public complete snapshot into a paginated read.

After a completed turn, the scheduler rechecks pending input and can start another turn on the same instance. Interrupted execution requires explicit recovery. Preparation or storage failures stop the scheduler and remain observable through `FlowScheduler::wait`. `stop` or dropping the scheduler handle prevents further scheduling; already queued admission commands settle, and admitted turns retain their execution and terminal commit obligations. Explicit execution controls pause or cancel a turn. A stopped scheduler releases its ownership so another host controller can attach.

`SessionHandle::schedule_flow` installs this same controller under catalog ownership. Views and requesting invocations receive a status stream; dropping it does not stop admission. `scheduling_status` reports Running, Stopped, or Failed independently of the flow's execution state. Preparation panics become observable scheduling failures and retain unconsumed input. A live controller rejects replacement; `stop_scheduling` relinquishes admission without cancelling an admitted turn. A failed controller can be explicitly replaced, and reopening a stopped storage worker releases its previous controller before binding another writer. Catalog shutdown stops owned controllers. Recovered instances require a fresh trusted executor and preparation policy; reading history does not grant execution authority.

Input policy, instance directory ownership, management authorization, and CLI/daemon integration remain host responsibilities. Automatic admission does not assign root privileges or infer a goal from message text.

## Host directory

`flow_store::profile::ProfileStore` owns `runtime-v1/host/identity.json` and its fact journal under an exclusive profile lock. The identity records the schema version and profile UUID. The journal records a management Session binding and explicit per-flow grants in one replacement transaction; display names and Session membership confer no management authority.

Renaming a Session or selecting its default flow leaves management grants unchanged. Pausing or closing a management flow does not pause its siblings or flows in other Sessions, replace the management binding, or create another flow. Closed callers cannot use an earlier invocation's grants; the authenticated operator retains the host's management interfaces.

`bootstrap` prepares a stable Session descriptor before creating its projectless container. Recovery completes that same creation across either crash boundary. Bootstrap does not create flows or schedule work. Once bound, a missing, corrupt, or mismatched Session is an error and requires explicit repair or replacement. Existing catalog writers may remain active during profile validation.

`replace` requires a request UUID, the current profile receipt, and a binding whose grantees are registered in that Session. Binding and grants change atomically. Identical retries return the original receipt even after subsequent replacements; conflicting reuse and stale new requests fail. Replacing management does not close either Session or delete history. The store is a trusted-host primitive; frontends must authenticate management commands before calling it.

`RuntimeHost::attach_profile` takes ownership through a serialized `ProfileHandle`. Initial validation completes before management grants become usable. `snapshot` exposes the committed profile and any availability error; an invalid binding can be explicitly replaced without starting work. Accepted bootstrap and replacement operations survive a disconnected waiter. Storage writes run on the blocking pool, and an idle profile owner does not occupy a thread. Host shutdown releases profile ownership after stopping its attached execution owners.

The persistent TUI's **Atman Session** action (`:atman`) resolves that profile binding and focuses its default flow through ordinary view navigation. First use prepares the missing default entry with the shared Session initializer in deferred mode; no scheduler, model call, or management grant is installed by navigation. The recorded configuration remains authoritative on subsequent visits. Concurrent requests reuse the same Session and entry, including recovery after preparation. Paused and closed instances retain their execution gates. Target resolution and focus carry the originating request identity; closing navigation prevents late focus changes, and revisiting an existing view preserves its draft.

The authenticated daemon operator uses `management.get`, `management.open`, and `management.select`. Opening creates an ordinary projectless Session on first use and opens the recorded container thereafter; it creates no flows and starts no model. Selection records the binding and grants without activating the selected Session. Each grant supplies an `id`, an `instance_id` registered in that Session, a `target` (`flow`, `session`, or `all_sessions`), and explicit `actions` (`discover`, `read_output`, `read_context`, `send`, `watch`, `control`, `manage_goal`, `delegate`). The host resolves the selected Session descriptor; callers cannot replace its configuration through this request. `expected` is the profile's `{ journal_id, sequence, digest }` receipt. Retries return their original receipt and the current profile view, including when an older selected Session is no longer available.

Daemon Session attachment loads profile grants before admitting execution. A corrupt or unavailable profile disables management authority and remains visible through the management endpoint; unrelated Session execution remains available. Damaged profile identity or journal files require repair and host restart, while a missing management Session can be explicitly replaced using the retained profile receipt. Closing an RPC connection or completing a management flow does not shut down the daemon or other Sessions.

The persistent TUI's Management directory reads the same profile owner without opening a Session or admitting execution. Grant removal submits a frozen `ReplaceManagement` containing the observed receipt, a stable request UUID, and the binding with only the selected grant removed. The original view receives the result; successful retries return the current directory without reinstalling earlier grants. A stale receipt fails without writing. Profile availability diagnostics remain visible, and unavailable authority disables grant removal in the directory.

Flow clients and event observers consult the same current management grants in addition to their Session grants. Replacement wakes observers to recheck authority. Revocation prevents new reads, controls, subscriptions, and delivery admission while retaining previously accepted input and subscription cursors. Renewed authority can continue from those cursors. Pausing the manager affects its own execution; other Sessions keep running. Closing, selecting, or naming a flow never assigns management authority. An uncertain profile write disables its grants until storage is reopened and reconciled.

Session journals retain explicit peer access grants and revocations. Grants name a registered source flow, a target flow/session or all sessions in the same host, and a set of actions. Same-session discovery, sending, watching public output, and reading public output are default capabilities. Full context reads, peer execution control, Goal management, and delegation require explicit authority; default-view selection and creation provenance do not supply it.

`SessionStore::grant_access` and `revoke_access` require the expected catalog cursor for new changes. Repeating an unchanged grant or revocation does not write another fact. A revoked grant identity cannot be reused to restore permission; renewed authority uses a new grant identity. Recovery rebuilds policy from the journal, ignoring disposable metadata. These storage operations are trusted-host primitives, not direct peer commands; callers still authenticate sources and enforce the resulting policy at operation admission.

`flow_runtime::host::RuntimeHost` attaches exclusively owned session catalogs. Each `SessionHandle` serializes catalog creation and default-view changes on a bounded command queue. Accepted catalog operations finish even if their waiting caller disappears. Disk work runs on the blocking pool; idle catalog owners do not occupy threads.

`SessionHandle::set_title` updates the session's display name under the same catalog owner. It requires the expected catalog receipt; a stale request cannot replace a different current title. Repeating the current value is a no-op, and `None` clears the name. The journal stores name changes separately from the immutable creation descriptor, preserving creation retries and project/configuration bindings. `subscribe_title` publishes committed names to attached views, including subscribers that reconnect later. Renaming does not load flows, start execution, or modify their histories. Catalog inspection, CLI listings, the monitor, and daemon session summaries read the current projected name.

The auto-name palette action and `:name-session` use the same asynchronous operation in main views, floating views, and the plain REPL. The built-in naming flow receives captured Goal and recent messages from the requesting flow. Title generation is separate from storage: the persistent host captures a catalog receipt before calling the model and commits through `set_title` afterward. A concurrent catalog change rejects a stale result; failures return to the original view without changing its execution, transcript, or legacy metadata files. Generated titles are trimmed, flattened to one line, and limited to 60 characters; empty output is rejected.

`RuntimeStore::delete_session` accepts a `SessionRemoval` containing the Session UUID and confirmed catalog receipt. Under the catalog lock, it rejects an attached owner, changed catalog, management binding, incomplete journal, or flow that is not closed. It shares full replay validation with project deletion and never stops execution, repairs journals, releases worktrees, or deletes shared project data.

`RuntimeHost::delete_session` also supports loaded Sessions. Its catalog owner checks the confirmed receipt, storage identity, management protection, and closed or archived instance states before releasing any owner. Release shares the existing shutdown path and rejects queued catalog work; old handles cannot create or resume instances. The opening gate serializes release with local opens and global shutdown. Storage rechecks ownership and the receipt before deleting, so an external owner or new catalog entry acquired between release and removal prevents deletion. Accepted removal continues after the requesting client disconnects. Other Sessions remain attached and runnable.

Deletion atomically publishes its receipt under `runtime-v1/.deletions/sessions/<session UUID>/receipt.json` together with `deliveries.json` before moving the Session directory into that directory's `data` entry for cleanup. The receipt permanently retires the identity: directory discovery, inspection, opening, creation, and migration publication cannot restore it. Retrying the identical request completes cleanup after interruption; a different receipt is rejected. Cleanup removes Session histories and artifacts while retaining the deletion receipt and minimal delivery evidence: authenticated sender identity, request ID, canonical request digest, and original acceptance with its final disposition. Edited inputs retain the digest of their original submitted request; no message body is retained in the tombstone. Blocking storage work belongs on the host's storage worker.

`RuntimeStore::inspect_deleted_delivery` authenticates no caller itself; the routing host must authenticate the sender before querying it, as for live acceptance. The runtime retains known Session storage bindings after owner release and uses the sender's storage root for an unknown same-storage recipient. It does not search unrelated data directories. A matching accepted request recovers its original receipt; changed data under the same request identity is rejected, and a never-accepted request records `RecipientDeleted` using the Session deletion receipt. Missing or unreadable evidence remains a reconciliation error rather than a fabricated rejection. These checks neither restore a deleted Flow nor invoke its execution services.

`pending_session_removals` discovers unfinished cleanup, and `inspect_session_removal` reads its retained request without opening writers or changing data. FlowHub includes these records in its paged Session directory; opening one reviews the original cleanup request. Completed cleanup records do not appear in the directory.

In persistent TUI views, Delete Session opens that shared directory. Select a Session and press Del or click Delete to review its identity and effects; only the explicit confirmation record sends removal. Ctrl+O does not confirm deletion, and a hidden confirmation cannot execute in a terminal too small to display it. Errors preserve the reviewed receipt; successful replies refresh the directory through the originating view's tracked request. Main and floating views share the same presentation and host operation. The shared host operation releases loaded owners only after confirming that every instance is closed or archived; closing a view alone does not stop execution. Cached scopes are evicted after release even if filesystem cleanup fails or the requesting view disconnects.

Original flat histories use `LegacySessionRemoval`: review records the canonical directory and a digest of all filenames, file contents, empty directories, and symbolic links. Deletion requires explicit confirmation that the old executor stopped; historical binaries do not honor the persistent runtime owner lock. A changed directory is rejected before removal. Receipts under `runtime-v1/.deletions/legacy-sessions/<UUID>` retain the original request and support cleanup before or after the directory move. Original and migrated copies remain independent; deleting one does not delete the other. Link targets and shared project files remain intact. FlowHub uses the same review rows and tracked replies for original histories, with an explicit stopped-executor confirmation on the deletion action. Unfinished original-history cleanup remains listed independently of any persistent Session with the same UUID.

Repeated `open_flow` and matching `create_flow` calls return the same live `FlowWorker` and conversation context. Opening another view does not reopen its journal or interrupt execution. Creation payload conflicts fail. After explicit worker handoff, reopening still requires exclusive journal ownership and reconciles an unfinished recorded turn as `HostLost`; it does not replay execution.

The host routes both same-session and cross-session delivery by complete `FlowRef`. Known instance handles are looked up without entering the catalog command queue, so unrelated catalog writes do not serialize their input or execution. Callers authenticate senders before routing, including retries, and provide authorization for new deliveries at the receiver's commit boundary. Routing does not grant authority, start a flow, or couple the recipient to its creator's lifecycle. Accepted retries retain their original receipts.

`select_default` changes only the session's view binding. It does not change execution state or permissions. Dropping catalog handles does not cancel instance handles held elsewhere. Host policies prepare eligible input using `flow_runtime::input::context_message` to retain message provenance; projection itself does not authenticate, consume, or authorize input.

`RuntimeHost::bind_invocation` issues an opaque `FlowClient` for an authenticated admitted turn. Its operations derive the sender from that binding and check current grants before target lookup and again inside the target worker. Stale, paused, finishing, or unavailable source invocations cannot initiate peer operations. Finishing hooks can still read their own conversation and save their own Goal and planning state under the active lease, including while an execution pause blocks later work. Cancellation, closure, or lease expiry removes that cleanup access. Catalog grant changes become visible only after their journal commit; already queued reads and controls recheck revocation before acting.

The client exposes execution inspection, public final-answer reads, authorized private context reads, reliable interjections, and revision-checked execution controls. Public output excludes isolated branch publications. Each controller owns a distinct persistent pause key, so its resume cannot remove a user pause or another flow's pause. Cancellation requests cleanup without forging completion. A committed send may finish delivery after its source turn ends, but new receiver admission still checks current grants.

Host-owned workers automatically bind this client into the executor's `ToolCtx`; inline calls and fanout branches retain the originating instance identity. Separate spawned agents cannot inherit that client as their own identity. Workers hold a weak directory reference, avoiding an ownership cycle. A persistent invocation without its host binding fails peer operations instead of consulting the legacy run registry.

The shared `flow.status`, `flow.output`, `flow.interject`, and `flow.kill` tools use the invocation's instance binding. A target handle is an instance UUID within the same session, or `session-uuid/instance-uuid` across sessions. Status returns execution state, revision, and pause state separately. Output retains character-based cursor pagination over committed public answers. Interjection returns a durable delivery status and supports `at_boundary` or `next_turn`; an optional stable UUID `request_id` reconciles identical sends without duplicate input. Cancellation requires `expected_revision` from status and explicit control authority; it requests turn cleanup and preserves the instance. `flow.close(handle, expected_revision)` requires persistent ownership and the same control authority, accepts permanent closure, and returns before cleanup finishes. Use `flow.status` or an `instance_closed` watch to observe completion. Persistent interjection rejects legacy L2/L3 redirect controls. Embedded legacy Session invocations retain run handles; they do not supply the execution path for CLI or daemon persistent instances.

`flow.sessions` pages authorized Session metadata through the bound invocation. Same-session discovery is implicit; foreign inventory requires a Session-wide or all-Session `Discover` grant. A grant to one flow does not expose its Session inventory. Results contain title, project path, default flow, counts, catalog receipt, and availability; conversation, Goal bodies, and configuration are excluded. Rows use descending UUID order, and `next_cursor` is passed as `before`. Counts include only authorized Sessions. Permissions and source admission are checked again after reading, so revocation or a paused/finished turn cannot publish an earlier sampled page. The host's attached profile supplies the on-disk catalog location; without it, only attached Sessions are discoverable.

`flow.instances` uses the bound client's session catalog rather than the transient execution registry. An optional `session_id` selects a foreign Session under the same discovery grant. It includes the default flow and prepared, idle, interrupted, paused, and closed peers. `limit` bounds a page to 1–50 entries; `next_cursor` can be passed as `before` for older registrations. Registrations added between pages do not repeat previously listed instances. A missing cursor is rejected instead of silently restarting pagination. State fields share the `flow.status` projection, and the response identifies the catalog revision; individual execution states are read independently, not as a cross-flow atomic snapshot. Foreign handles use `session-uuid/instance-uuid` and return no spawn token.

Discovery reads only summaries and does not grant context or control access. Unavailable journals remain listed with an explicit error. `SessionHandle::describe_flow` reuses live writers; inactive journals are inspected without acquiring a writer, recovering execution, repairing tails, or rewriting caches. `SessionStore::inspect_flow` and `SessionInspection::inspect_flow` share the complete fact validation and projection used by writer recovery. A recorded active turn does not prove a live owner; explicit writer recovery still marks an abandoned turn interrupted. Persistent instance listing requires a live host binding and cannot fall back to the legacy run registry. Existing session invocations also support bounded cursor pagination over their registered run handles.

Instance discovery includes `loaded` and `trailing_bytes`. Unloaded entries expose their recorded execution state; `flow.instances` labels them `detached` and includes `recorded_status`. This separates journal facts from acknowledged state supplied by an attached worker. Truncated trailing bytes remain untouched until explicit writer recovery.

`flow_runtime::catalog::SessionCatalog` supplies the same live/detached projection to daemon listing, peer discovery, and TUI navigation without opening execution owners or initializing storage. Its paged API filters Session identities before loading metadata and rechecks authorization before returning rows and counts. An invalid individual catalog remains an unavailable row. A live owner supersedes a detached read when it attaches during inspection. The daemon's trusted operator overview can additionally read the default loaded flow's Goal. Discovery of the caller's own Session retains its caller-bound spawn permit and catalog cursor; that permit alone is neither a durable instance creation request nor an execution grant.

`SessionCatalog::relations` and `SessionInspection::relations` expose a deterministic read-only relation projection. `Created` points from the creator to the created flow; subscription `Watch` points from the observing flow to the observed flow. Active session grants contribute `Read`, `Watch`, and `Interject` permissions from the grantee to its authorized target. Revoked grants and result-only subscriptions are excluded. Inspection reads journals without opening writers, schedulers, or model providers; asynchronous catalog queries perform journal scanning on blocking workers. Each journal is a recorded snapshot, not an atomic snapshot of every flow's current execution.

`SessionCatalog::overview_page` traverses Sessions and their Flows with the same bounded cursor used by watcher and workspace directories. Each Flow snapshot contains its recorded execution state, Goal, pending-input count, relations, and journal receipt. Separate execution observations identify an acknowledged loaded writer, a detached record, or an unavailable owner; they never replace the recorded state or imply a global atomic snapshot. Inactive journals are read once without recovery. Session grants belong to their actual grantee; current management grants supplement that source without expanding Session-wide targets into synthetic Flow nodes. Callers must authorize Goal-content inspection, not only metadata discovery. Authorization is checked again after host observations and before returning the page; corrupt records remain explicit errors and do not prevent cursor progress.

## Flow event subscriptions

Flow event subscriptions belong to the receiving flow's journal. Registration records a source-owner cursor, an event filter, one-shot behavior, the notification purpose, and registration time. Watchers may specify an absolute deadline; internal result routes and correlated reply subscriptions cannot expire. A source can remain Prepared while a creator records its result subscription; activation is a separate authorized operation. Repeating an identical registration is idempotent, and cancellation never reactivates its identity. Closing a recipient cancels active subscriptions while preserving their history.

`FlowSubscription` selects events with `FlowEventFilter`: all final answers, answers containing text, answers outside a specified turn, entry completions for all turns or one exact turn, or instance closure. `events_after` merges committed final answers, entry completions, and closure in source journal order and returns bounded pages; private branch output is excluded. Completion notifications carry the saved typed result, execution outcome, lease, and receipt. An entry completion is distinct from a final answer; observing an ordinary return or interruption does not publish a reply.

The closure event uses the receipt of the committed `Closed` transition, rebuilt from that transition on reopening. Capturing an anchor from a closed source rejects new registrations; a closure after anchor capture remains observable. After observing closure, matching subscriptions become `Matched` even in persistent mode, and other unexpired active subscriptions become `SourceClosed`. Only selected event types enter the inbox. Accepted replies remain queued; pending correlated waits without an accepted reply or an active route are cancelled in the same observation commit. A deadline that elapsed before observation still produces its expiry notification.

`observe_events` evaluates all active subscriptions to that source together and commits cursor updates and inbox acceptance in one receiver transaction. A source fact matching multiple subscriptions produces one inbox item with all matching reasons. Delivery identity derives from the source address and journal position, independently of subscription IDs. A repeated page cannot create another input, including after that item has been consumed or the process has restarted. A page containing only unmatched event types still advances its cursor so later matching events remain reachable. Cancellation before observation excludes the cancelled subscription; cancellation after acceptance does not remove queued work.

Only observable event positions advance the cursor. Unrelated commits do not generate cursor-only work, including for self-subscriptions. A page that skips an unobserved source position is rejected. Torn receiver transactions recover neither consumption position nor accepted input; the original source page can be observed again. These storage operations require trusted source handles and host authorization.

An exact one-shot completion subscription can carry a `ReplyWaiter`. A new waiter and subscription commit together; an existing identical pending waiter can also be bound. Conflicting correlations for the same source completion are rejected. All subscriptions matching one completion share its reply ownership. Cancelling the last active subscription for a pending correlation cancels its waiter in the same commit if no accepted reply remains; cancelling an already matched subscription preserves the queued reply.

Each opened host-owned worker has an observation task owned by its session catalog. `FlowClient::watch_events` records registration before acknowledgement; an identical retry preserves the original position and never reactivates a cancelled or matched subscription. `unwatch_events` cancels the caller's subscription without removing previously accepted input. These operations require an admitted invocation; existing subscriptions continue after its turn ends and while execution is paused. Answer and completion subscriptions use the same observer, authorization checks, commit notifications, cursor recovery, and inbox.

Watcher creation and replacement retain the captured source receipt in `started_after`. Their initial consumption cursor is the greater of that position and the recipient's already committed observation position for the same source. This resolves observation progress during registration without replaying earlier notifications or rejecting a valid future watcher. Journal replay validates the same cursor calculation. Internal result routes retain their exact source anchor; registration cannot skip a result required by a pending caller.

The observer establishes change receivers before scanning source events and advances bounded pages through the receiving worker's single writer. Watch authority is checked before source reads and again at receiver admission. Revocation retains the subscription and cursor without delivering new content; granting access again wakes observation and permits catch-up. Source commits, recipient commits, session attachment, and access changes drive scans without a polling timer. A newly attached source session also wakes retained subscriptions. Catalog ownership uses weak host references, so idle observers do not keep the directory alive.

`FlowWorker::subscribe_observation_issues` exposes blocked sources and their reasons. Storage failures retain progress and can be retried with `retry_observations`; no empty turn is started to retry delivery. Reopening a worker restores its subscriptions, while a catalog attachment alone does not eagerly open every recorded flow.

`expire_flow_watches` commits expiry and its timer notification together. Matching uses the receiver's observation time: an answer accepted before the deadline remains queued, and an answer observed at or after the deadline does not match that registration. The host observer handles deadlines independently of source access, source availability, or execution pauses. Expired, matched one-shot, and cancelled registrations do not produce another deadline notification after reopening. Flow and process watchers share one identity namespace within their owner.

## Process watch storage

`FlowStore::register_process_watch` records a process incarnation, handle, pattern, source position, one-shot behavior, and optional absolute expiry. Bash and terminal sources have distinct types. Reusing a handle for a different process requires a new incarnation. Identical registration retries preserve the original position and terminal status; they do not restart observation or extend the deadline.

The trusted resource owner establishes the source stream before registration and submits one `ProcessReport` containing all matches at a source position. `observe_process` rechecks active registrations and commits their status changes with a single `ProcessEvent` inbox envelope. An identical report returns its original receipt, including after consumption or closure; a conflicting report at that position is rejected. Source positions are monotonic within an incarnation. Matching belongs to the resource adapter, while acceptance, cancellation, expiry, and consumption belong to the receiving journal.

`expire_process_watches` commits expiration and timer input together. No timeout is imposed when `expires_at` is absent. The resource owner serializes source reports and expiry commands; an accepted expiry or cancellation excludes a subsequently submitted match. Cancelling a registration preserves already accepted input. Closing the instance cancels outstanding registrations and pending input through the existing lifecycle transition while retaining both in history.

Starting a new `FlowWorker` creates a new process-resource owner. Outstanding registrations for old process incarnations become `SourceLost`, or `Expired` if their recorded deadline has passed, and their notifications enter the same durable inbox. Reopening does not restart a process or generate a second loss notification. Execution pauses retain those inputs without granting permission to run. Storage-only inspection and recovery do not declare source loss; ownership startup does.

## Instance watcher tools

For persistent invocations, `watch`, `watcher.list`, and `watcher.unwatch` address process registrations owned by the invoking instance. Resource identities come from the actual Bash or Terminal task, and registration rechecks the invocation's authority at the journal owner. Each process has one observer holding its source subscription and match cursors across turns. Registration captures the initial source state before acknowledgement. Bash output changes and terminal screen revisions drive matching without polling; all matching registrations at one observed position share one inbox input. An optional `timeout_ms` becomes an absolute deadline without a default limit. A Bash output cursor that falls behind retained history produces `HistoryGap` and retires its registrations; a fresh registration can observe the same live process.

The same tools accept a persistent flow instance UUID, or `session UUID/instance UUID` across sessions. For Flow sources, `event` selects `final_answer` (default), `turn_completed`, or `instance_closed`. An optional `pattern` filters final-answer text; an optional `turn_id` selects one completion. Invalid combinations are rejected. Structured events require a persistent Flow source, while process and legacy task output require a pattern. Peer invocations use `FlowClient::watch_events` in either direction with the same source cursor and grants as native subscriptions. A final answer matching both a spawn-result route and watchers produces one input with all reasons. `watcher.list` returns active process and Flow watcher registrations in registration order, including filters, deadlines, and source identities. Internal result routes are excluded from the list and cannot be cancelled through `watcher.unwatch`.

The `watch` tool requires a flow contract with `capabilities { shell: true }`. A persistent invocation can register these independent observations:

```at
answer = watch(handle: peer)
completion = watch(handle: peer, event: "turn_completed")
closure = watch(handle: peer, event: "instance_closed")
```

`wait_for_watcher` and the next general model call consume the same durable inbox. Explicit waiting takes the context compaction lock before reservation, commits accepted notifications and their context representation together, and returns a count acknowledgement without duplicating the body in a tool result. Timeout, cancellation before pickup, execution pause, and turn finishing leave unread input pending. Once queued at the owner, context commit and projection retain lock ownership even if the waiting caller disappears. Notification messages preserve watcher provenance and do not grant user authority.

Unwatch cancels the owned Flow or process registration while retaining accepted input, and refreshes the process observer at the successful storage commit independently of the caller awaiting its reply. Instance shutdown cancels and joins observers together with process resources. Legacy invocations retain their existing watcher hub.

`FlowWorker::unwatch` is the shared host control for Flow and process registrations. It authorizes the actual owner inside the serialized storage request, rejects internal result routes, and returns the durable receipt. It works while execution is paused or idle without claiming a turn or changing execution state. Repeated cancellation does not append another cancellation fact. `FlowClient::unwatch` uses this operation with lease authentication, so tool calls and operator controls preserve the same pending notifications and producer cleanup.

`RuntimeHost::watch_events` registers a Flow subscription without claiming an execution turn. The host-supplied owner authorization runs before lookup and at storage boundaries; new registrations also check the recipient's current watch grants before capturing a source anchor and committing it. Identical retries return the recorded registration without advancing its original anchor or reviving a cancelled registration, even if source access has since been revoked. Conflicting reuse of a registration ID is rejected. Source and recipient storage operations are sequential, so self-subscriptions and reciprocal registrations do not hold both owners together. `FlowClient::watch_events` uses the same path with invocation authentication.

`FlowWorker::watch_process` provides the corresponding host operation for a live process owned by the instance. Authorization runs before resource lookup and at the registration commit. The existing producer captures the process incarnation, source subscription, and initial snapshot before acknowledgement; it continues to own matching and inbox delivery. Paused or idle hosts and executing agents use the same registration mechanism without changing execution gates.

Hosts selecting a process from a directory use `SessionHandle::process_watch_sources` or `FlowWorker::process_watch_sources`. Entries retain the resource kind, handle, incarnation, label, and execution status. Session reads inspect only already loaded resources; recorded instances are not opened, recovered, or scheduled. `FlowWorker::watch_process_source` accepts the selected `ProcessWatch` and rejects a replaced incarnation before registering with the shared producer. Authorization is rechecked inside storage requests. Identical retries preserve the original registration even after cancellation, resource loss, or host restart; changed parameters under the same ID are rejected.

WatchHub carries this identity from its process directory through the shared watcher draft and `RegisterWatcher` control. The typed registration distinguishes Flow subscriptions from process observations; both return updates to the captured view ticket. Process discovery does not attach an execution owner. Creation uses the existing resource producer and durable inbox, preserves failed drafts, and requires a nonempty output pattern. Changing a selection or condition creates a new registration identity, while retries retain the original ID and absolute deadline.

`SessionCatalog::watch_page` scans committed watcher records across Sessions without opening execution owners. Pages are bounded by Flow inspections; empty or unavailable Sessions consume the same budget and advance the cursor. Each Flow retains its full address, Session title, journal receipt, incomplete-tail count, and watcher delivery projection. Unreadable records remain visible as errors without hiding other records. Session visibility and Flow authorization are rechecked before returning a page. Entries are independently sampled, so the directory does not claim a shared global commit boundary; refreshing starts a new scan for newly created records.

WatchHub uses this catalog through the same `WatchDirectory` and details renderer as the current-Flow view. Appended batches must match the original recipient and next scan cursor. Row identity includes both the owning `FlowRef` and subscription UUID. Cancellation replies replace only the corresponding owner's snapshot and retain the directory filter; replies still require the original view ticket. Source selection and creation keep the original recipient independently of the selected catalog row.

`FlowStore::replace_flow_watch` and `replace_process_watch` replace a user subscription with one `WatcherReplaced` journal fact. The fact carries the expected original configuration and a new registration identity with its source position. Validation rejects stale configurations, inactive or expired originals, internal result routes, invalid replacements, and identity collisions before cancelling anything. Flow and process registrations can replace either kind. Previously accepted notifications and execution pause state remain unchanged; the new registration starts at its supplied source boundary without backfilling earlier output. An identical retry returns the original commit receipt, including after recovery, source loss, or later cancellation. Inspection and writer recovery validate the same replacement fact, and `FlowUpdate::WatcherReplaced` exposes its relation to consumers.

`RuntimeHost::replace_watcher` authorizes the recipient before reading its retry receipt and again at commit. Flow replacements capture their source anchor through the registration path and recheck watch grants before committing. Process replacements use the existing resource producer, verify the selected incarnation, and initialize matching at the captured live state rather than replaying retained output. Successful commits refresh retired process matchers even if the caller drops the acknowledgement. Editing does not claim a turn, resume execution, or consume accepted notifications.

WatchHub creation and editing share `WatchDefinition` and one form. An edit retains the original owner and expected definition while source selection uses the existing directory. Changing another field preserves the original absolute expiry; editing the expiry starts a new duration at submission. Save retries retain the replacement identity until draft content changes. The original view ticket owns the result, and only an acknowledged owner snapshot exits the form. Global edits update that owner's snapshot and retain the directory filter and loaded records, including after source selection. Source-session attachment shares the registration path and does not install a scheduler or load models.

Bash output publishes bounded fragments as reads complete, including text without a newline. Only an incomplete UTF-8 character waits for more bytes; EOF preserves any unfinished bytes. Stateful stdout/stderr framing keeps adjacent fragments contiguous, so watcher patterns can span reads without synthetic labels or newlines between them. Log queue admission precedes the shared output lock; logging, retained bytes, watcher revisions, and UI fragments use the same publication order. The complete log remains independent of the retained-output budget. `BashChunk.start` identifies a new line, continuation, or stream switch for all TUI consumers; frames without that field retain their existing line interpretation.

## Owned send attempts

`RuntimeHost::send` uses the sender's admitted lease to commit an outbox intent, routes its recorded request to the receiver, and commits the authenticated acceptance receipt back to the sender. A reply waiter, when supplied, is registered with the intent before receiver contact. Send admission and new receiver delivery have separate authorization callbacks. The caller authenticates the invoking flow before entering this host API.

The host owns the delivery task once started. Cancelling its waiting caller does not discard the intent or stop that attempt. Same-session, cross-session, reverse, and self-directed sends release each storage owner before contacting the other endpoint. Concurrent retries use the same sender request ID and receiver acceptance identity, so they do not create additional input or confirmation records.

`SendAttempt` returns the authoritative sender record and an optional pending reason. Uncertain transport, authorization, or storage errors leave `PendingDelivery`; this may include an accepted receiver message whose sender acknowledgement could not be committed. A typed rejection from a closing or closed receiver records `Failed` only after receiver deduplication confirms that the request was never accepted. Failure to persist that rejection still leaves the send pending. `retry_send` reads the original intent from the sender journal and reconciles that request. It can confirm prior receiver acceptance after interruption, revocation, or closure without treating the retry as new work. Accepted and failed sends return their existing records without contacting the receiver again. Accepted means received, not executed or successfully handled.

`FlowWorker::pending_sends` returns lightweight summaries; `send_record` reads a complete intent on demand. `FlowClient::send` records `PeerGrants` authorization, and the storage owner's delivery driver reconciles these intents when the owner opens, journals advance, grants or loaded Sessions change, or `retry_deliveries` requests a scan after an external repair. The driver loads one pending body at a time, checks current Send grants at new receiver admission, and uses the same idempotent acceptance and acknowledgement path as the original call. It remains available after the sender closes, does not start a model turn, and stops with its storage owner. Unchanged failures wait for notifications rather than polling. `subscribe_delivery_issues` reports transient failures without replacing durable delivery status.

`RuntimeHost::send` and `FlowWorker::queue_send` retain `Host` authorization: their caller supplies the delivery policy explicitly, so automatic reconciliation cannot substitute peer grants for an external authorization callback. `retry_send` supplies that callback for a recorded intent. A repeated request cannot change its authorization contract. Task-scoped sends retain source subscriptions and revalidate at receiver admission; an already accepted request can recover its original acknowledgement without admitting new work.

## Scoped model directories

`model_registry::ModelRegistry` owns model configuration, aliases, provider catalogs, transaction serialization, and catalog notifications. Separate registries can use the same model and provider names without sharing protocol selection, capabilities, budgets, or revisions. Request snapshots remain unchanged after later directory updates. Auth-aware projections take explicit auth data and optional cache sources; management views do not install callable models.

Prepared configuration and catalog updates retain a borrow of their originating registry and hold its transaction until commit or drop. Commit uses that owner, and dropping an update leaves the published state unchanged. Existing module-level model functions delegate to the process-default registry. Product callers using those functions still share the default directory; explicit directory isolation requires retaining and using a scoped registry.

`ProviderRegistry::with_models(Arc<ModelRegistry>)` binds connections to their directory. LLM tools retain the requested alias until dispatch creates one scope-bound `ModelCallConfig`; provider resolution rejects snapshots from a different registry. Direct calls, structured extraction, compaction, MCP sampling, suggestions, and model connection tests obtain snapshots from the connection registry. Disabled configured providers cannot resolve through either direct or prefixed connection names.

Executor entry binds its Session context to the same directory. Repeated binding to the same owner is valid; replacing it with another owner fails before executing the entry. Model-list context records and budget projections use this binding. Unbound persistent contexts do not read the default directory; unbound legacy contexts retain their existing default behavior.

`ConfigHub::models()` identifies the directory for its normalized configuration and authentication source paths. Hubs for the same source pair share ownership; different authentication files keep separate dynamic catalogs even when they share `config.toml`. Configuration reload and edits validate all live directories for that configuration source before publishing any update. Validation or write failure preserves the previous projections. The process default source uses the default registry; constructing a hub does not read its configuration until reload or lifecycle attachment.

`AtmanRuntime::build` creates provider connections with the selected hub's directory. Embedded hosts construct `ProviderRegistry::with_models(hub.models().clone())` before calling `ProviderLifecycle::new(hub, providers)` or attaching the lifecycle to an executor. These constructors return `ProviderLifecycleError` for mismatched scopes, repeated executor attachment, or configuration errors. Lifecycle setup loads configuration and registers connections; catalog refresh, removal, and notifications remain within the same authentication scope. Provider reconciliation and replaced-adapter destruction run outside the lifecycle owner lock.

`SessionDescriptor::configuration` records either `HostProvided` effects or an `Atman(ConfigSource)` binding in the session creation journal. `ConfigSource` contains normalized configuration and authentication paths, without credentials. Each flow inherits this immutable session binding when its context is restored. History replay validates the recorded shape without opening the configuration or project directory. Reopening an execution source through `ConfigHub::from_source` rejects changed filesystem aliases instead of selecting another directory.

Installed user commands and `user:` imports use the recorded Session configuration or the bound provider lifecycle's configuration directory. `flow_source` distinguishes the current creation catalog from an existing flow's execution source roots. A persistent instance with host-provided services has no implicit user command directory; its permitted project sources remain available. Legacy unbound calls retain their global configuration lookup.

`AtmanRuntimeOptions::config` takes an explicit `ConfigHub`; CLI and daemon entry points resolve their default before constructing the runtime. A restored host can pass `ConfigHub::from_source` to retain a selected authentication file. Scheduling, direct turn admission, executor entry, and model-context operations share the context's provider binding check. A source mismatch fails before pending input is consumed or execution ownership is claimed. Custom embedded executors use `HostProvided`; attaching an Atman lifecycle requires a matching recorded source. Attaching a correct host does not resume paused work or create a turn.

`SessionDescriptor::project` explicitly records an optional `ProjectContext`. The binding retains a normalized project root, local/global scope, and knowledge storage root. `ProjectContext::resolve` reads the selected hub and project preferences without creating directories; invalid or unreadable preferences fail instead of selecting a different store. Session and flow journals remain under the runtime data root. Changing storage preferences does not rewrite an existing session binding, and reading history does not require the original directories.

`AtmanRuntimeOptions::project` receives that binding, including explicit `None` for a projectless runtime. `Session::bind_executor` checks project identity before model binding, scheduling ownership, or input consumption. CLI and daemon memory setup use the same resolved storage root as runtime construction. This resource binding does not grant filesystem access: persistent execution uses its invocation authority and may select a permitted worktree independently. Restoring a runtime validates directory aliases without recomputing storage preferences.

`Executor::validate_session_binding` checks project and provider configuration identity without mutating a context or journal. Entry launch uses this same check before creating a catalog registration, so mismatched services cannot leave a new Prepared instance. Existing Prepared entries validate against their captured project. A matching retry of an accepted activation returns its original receipt without replacing services or starting execution again.

`ToolCtx::for_project` creates a fresh resource context with an explicit project binding before attaching services; it does not relabel an existing context containing workspace, sandbox, or index references. An explicit projectless host cannot resolve a relative path from the process directory. Rule discovery scans only the supplied project and home sources; omitting a project keeps global rules available without loading rules from the current directory. `SandboxExec::without_project` renders project placeholders from each operation's supplied working directory, preserving configured sandbox restrictions without adding an unrelated checkout.

## MCP resource ownership

`AtmanRuntime::build` attaches an `McpService` to the executor's resource context. Cloned executors, inline calls, and spawned flows retain that owner. Separately constructed runtimes use independent connection groups, even when servers have identical names. Stdio connections use the bound project root or, for a projectless runtime, its configuration directory. Sampling uses the owner's provider registry and model directory.

The service retains configuration, tool and provider registries, and connection tasks without retaining a Session. `Session::bind_executor` installs a weakly held status projection; dropping a view does not close connections, and retaining a view does not keep the service alive. A live projection cannot be rebound to another service. After its service closes, a context can bind a replacement with the same validated project and provider scope. MCP readiness and status tools read the service directly, including when no Session view is attached.

Reload serializes generation changes with adapter and status publication. Removed adapters disappear before reload returns, cancelled initialization and refresh tasks release their clients, and stale producers cannot publish into a later generation. Explicit server waits retain the requested server identity and fail if it is removed. `McpService::shutdown` waits for its worker runtime to release resources; dropping the last owner requests the same cleanup without blocking. Connection status is a live resource projection, not durable flow execution state.

## Durable timers

`FlowStore::schedule_timer` persists an absolute UTC deadline, a stable timer UUID, and JSON notification content. `cancel_timer` prevents pending delivery without retracting input already accepted by the Flow. Reusing an identity with different content fails; retrying an unchanged registration retains its fired or cancelled state. `next_timer_deadline` exposes the earliest outstanding deadline.

`fire_due_timers(at)` commits all due registrations and their inbox messages atomically, ordered by deadline and identity. Delivery is independent of execution pause; normal inbox admission controls consumption. Closing cancels outstanding timers. Reopening storage and `SessionStore::inspect_flow` only replay facts and never trigger deadlines. `FlowInspection.timers` and typed journal updates expose recorded status without acquiring an execution owner. These storage APIs require an authorized host to register and trigger timers.

`RuntimeHost` observes timer deadlines alongside Flow subscriptions. Owner commits refresh the nearest deadline; idle instances and execution-paused instances can receive due notifications without a model invocation. Reattaching an owner catches up overdue registrations once. `FlowWorker` exposes authorized scheduling, cancellation, and listing; invocation-bound `FlowClient` methods restrict these operations to the current instance and reject expired leases. A bare worker without a RuntimeHost has no automatic deadline observer. Storage failures remain visible through observation diagnostics and await a commit, directory change, or explicit `retry_observations` request.

The shared watch tool group registers `timer.schedule(id, due_at, content)`, `timer.cancel(id)`, and `timer.list()`. These tools address only the invoking persistent Flow, require unique named arguments, and accept RFC 3339 timestamps with a timezone. Managed agent and sub-agent tool declarations include them. Timer notification content is data; the producer assigns `TimerPurpose::Notification` or `WatchExpiry` independently of that content. Ordinary reminders enter internal context and cannot impersonate watcher expiry by supplying a `kind` field.

```text
timer.schedule(id: "d7827f6f-240f-4c3c-8e02-f2f58d786bfd", due_at: "2027-01-15T10:30:00+08:00", content: "Review the deployment status")
timer.list()
timer.cancel(id: "d7827f6f-240f-4c3c-8e02-f2f58d786bfd")
```

## Task scope records

`FlowStore::create_task_scope` records a named cancellation group owned by an open Flow. `TaskScopeRef` contains the owner address and scope UUID. A new instance can record one immutable membership through `bind_task_scope` while Prepared; activation prevents new or replacement bindings. The host must authenticate membership and verify that the referenced owner and scope are available before binding. These storage methods do not attach observers or close other instances.

An optional `ScopeGoal` binds the group to the current Goal ID and objective text. Goal replacement, objective changes, and clearing cancel associated groups in the same journal commit; pause and resume leave them active. Owner closure cancels its remaining groups, while unbound groups survive Goal changes. `cancel_task_scope` is terminal and preserves the original cancellation receipt on retry. `FlowInspection.task_scopes`, `task_scope_binding`, and typed updates use the same replay validation as writer recovery.

`RuntimeHost::bind_task_scope` authenticates both endpoints through its supplied callback and checks the registered source before committing membership. `FlowWorker::create_task_scope`, `cancel_task_scope`, and `task_scopes` serialize authenticated operations through the owner. Activation, turn admission, execution claims, and execution recovery validate the complete immutable scope ancestry. Source changes and admission share writer gates, so a committed cancellation cannot admit a new member turn while asynchronous cleanup catches up.

Storage transactions resolve source dependencies before entering the writer queue. The writer acquires its own exclusive gate and deduplicated source read gates in full Session/Flow address order, then validates an immutable snapshot while retaining those gates through commit and projection. Self references use the writer's existing gate. Execution claims use the same ordering. An unavailable source rejects the dependent operation without stopping the recipient's journal owner or unrelated operations.

The host observer closes explicitly bound members through the existing lifecycle, including active execution and process cleanup. It subscribes to source commits before checking status and restores observation when a member is reopened. Closing one member does not close its owner or unrelated peers. Missing sources and cross-journal cycles block new execution and remain diagnostic; they do not silently discard member history. A standalone worker may read bound history but requires its runtime host to execute it.

`DeliveryRequest.scope` identifies a message's task scope with a complete `TaskScopeRef`. It does not make the recipient a member of that scope. After verifying a source cancellation, the host can record `FlowStore::invalidate_input_scope`: one `InputScopeInvalidated` fact cancels that scope's unread messages and invalidates outstanding input reservations. Already committed input, unrelated pending messages, and the recipient's execution state remain unchanged.

The invalidation retains its source cancellation and recipient commit receipt. Identical retries reuse that receipt; a different cancellation for the same scope is rejected. Previously accepted requests retain their original acceptance receipt and updated disposition, while new requests for an invalidated scope are rejected. Writer recovery, read-only inspection, and typed updates share the same replay validation; inspection does not consult another Flow or infer cancellation from an unavailable source.

`FlowWorker::accept_input` and `RuntimeHost::deliver` validate new scoped requests against the source group and its immutable membership ancestry under the shared transaction gates. The sender must be authenticated before calling; the authorization callback runs only for new delivery. Accepted retries return the original receipt without requiring the source to remain available. Self references and reciprocal peer references do not create membership edges. A standalone writer may reconcile an existing receipt but cannot accept new scoped input without its RuntimeHost.

The existing host observer subscribes to scope sources before reading them and records confirmed input invalidation independently of recipient pause or idle state. Only a direct source's cancellation receipt invalidates its input references; ancestor cancellation blocks new admission until member cleanup records that source's own cancellation. Missing sources retain pending input and produce observation diagnostics. Attaching the missing Session, a source commit, or `retry_observations` rechecks them. This observation does not close the recipient or change its execution gates.

Turn admission, model-context pickup, and explicit watcher/reply waits share source resolution and transaction-bound eligibility. Source subscriptions are established before reads and remain in the wait set alongside directory changes and explicit retries. The scheduler captures scope references and the recipient cursor without reading message bodies, then rechecks that cursor, source eligibility, and execution gates before loading input for preparation. Paused, active, interrupted, and closed instances do not read pending bodies for scheduling. Unavailable scoped messages remain visible in the public snapshot but are excluded before body reads; restoring their source wakes preparation without new recipient input. Eligible messages retain batch preparation without a UI page limit. Admission rechecks the selected IDs under the source gates, so cancellation after preparation cannot start that work. Conditional admission resamples changed input, while an explicit invalid `start_turn` returns an error. The entry recipe handles parameter preparation independently of source validation.

`reserve_reply_input` accepts an eligibility predicate for the same queue used by ordinary input. An ineligible reply remains unconsumed, and explicit waits wake on source recovery without requiring a new recipient message. Context pickup batches all compatible eligible input; a scoped message arriving after source resolution waits for a later boundary. Failed source read gates are unavailable entries in the transaction snapshot, so mandatory membership still fails closed while unrelated input can proceed.

Scheduler idle checkpoints include the source subscriptions observed during preparation. Batch quiescence and permission-review availability check that checkpoint as well as the recipient cursor, so source recovery cannot be mistaken for settled work. Checkpoints retain notification receivers without retaining source workers.

Scoped send intents use the same source validation as scoped inbox admission. New intents require active source scopes; identical requests return their existing send record before consulting those sources. A reply correlation belongs to one send request, so cancellation cannot alias an unrelated intent. Scope cancellation records the existing reply-cancellation facts for matching pending waits in one commit, including while the sending turn is paused. Delivered results and unrelated waits remain unchanged. The shared message observer watches both unread inputs and pending send waits.

An explicit reply wait checks the original send scope as well as the incoming message scope. An unscoped reply therefore cannot bypass a missing or cancelled source group. Unknown sources retain the reply until source or directory changes wake the wait; confirmed cancellation ends the wait without manufacturing a completion. Cancellation does not erase send intents or mark delivery successful. `PendingDelivery` retains uncertainty about receiver acceptance, and retrying the same request may reconcile an earlier acceptance after source cancellation; the receiver still rejects new scoped acceptance.

### Task scope tools

`flow.scope.create(id, name, goal?)`, `flow.scope.list()`, and `flow.scope.cancel(id)` operate on the invoking persistent Flow. Create and list return each complete `reference` (`owner.session_id`, `owner.instance_id`, and `id`) alongside its durable `record`. Reuse a stable UUID and identical definition for creation retries. An optional goal binding contains the current goal id and objective; a mismatch is rejected. Cancelling a group requires the normal approval policy for a Tier Two tool. Creation and listing are Tier Zero. A closed invocation cannot use its previous client to manage groups.

`flow.interject(scope: reference)` records the scope in both the send intent and recipient inbox. Omitting it keeps the message independent. Malformed references, unknown fields, and nil identities are rejected; legacy Session invocation and L4 execution cancellation do not accept message scopes. The managed main agent, all four subagent roles, and the agent example declare the scope tools.

```at
group = flow.scope.create(id: "1d2e1d89-30fb-4573-8d95-d81429758d36", name: "Review changes")
flow.interject(handle: peer, text: "Review the changes", scope: group.reference, request_id: "169b699f-2688-4694-9826-f8fce8606f38")
flow.scope.cancel(id: group.reference.id)
```

`flow.spawn(scope: reference)` binds a new persistent instance to the group before acquiring launch resources or activating its entry. Both synchronous and asynchronous calls use the same binding; omitting `scope` creates an independent instance even when the caller belongs to a group. The referenced group and its ancestors must remain active at execution admission. Cancellation closes bound members through normal resource cleanup without closing independent peers.

Host callers supply the same reference in `LaunchInput.scope`. The activation record must match the immutable Prepared membership, and journal replay validates that invariant. A retry of an already committed activation returns its original receipt after cancellation without restarting execution. A different scope, or an omitted scope for a bound Prepared instance, is rejected. Legacy Session spawn rejects explicit scope arguments.

```at
group = flow.scope.create(id: "b0608322-5e7c-4769-ad37-568dfc9c1c5f", name: "Review task")
catalog = flow.instances()
peer = flow.spawn(flow: "review.at@review", spawn_token: catalog.spawn_token, scope: group.reference)
```
